# 什么够格搬进 revenant：判据只写一处

这条判据被立过、复述过、又改过一次，散在三个地方（`CONTEXT.md` 开头、`revenant/contrib/__init__.py` 的 docstring、`docs/playbooks/README.md` 各写一份），而且三份说的还不完全是一件事。它是每一次「这段代码该进来吗」都要引用的东西，所以它应该有一个落点。这份 ADR 就是那个落点。

## 判据

**这段代码里有没有游戏事实。** 没有就搬，有就留在项目脚本里。

游戏事实指这些东西：密钥；URL 与构造它的规则；项目 / 环境 / 桶 id；具体的类名与命名空间清单；目录约定；文件命名约定；按名字推语义的规则。

构件要用到其中任何一样，就把它**作为参数吃进来**，或者干脆不搬。这一条是可执行的：`[tables] luban_container` 指向项目里的一个 Python 文件、`contrib.fetch` 把 HTTP 调用注入、`contrib.decrypt` 把 Unicorn 实例注入，都是同一个手法的实例。

**重复不是前提，只是通用性的一种证据。**

## 它是怎么变成这样的

**#32 立下的旧判据**：同一段代码在两款以上真实项目里逐字出现才搬。**#47 沿用**了它。

**#50 改掉了它**。旧判据把「被抄过第二遍」当成准入前提，代价是一件明明通用的东西只要还没被抄第二遍就得在项目里等——而这恰好是它本来要终结的循环。最清楚的一个例子：某一款的 FlatBuffers reader 从头到尾没有一处游戏事实，却因为没有第二份副本，在那个项目的 `_tools/` 里躺了整整一轮。

**#48 提过一版两分支判据**，主张改成「两款以上逐字出现」**或**「只有一款、但没有它就读不出该款的整个数值层」。这一版**不采纳**，因为它开出来的口子比现有判据小：它把 #50 删掉的重复前提又装回去当第一分支，再开一个窄口子放行例外。现有判据不需要那个口子——#48 举的三样东西（FlatBuffers schema 恢复、BestHTTP 缓存剥头、A/B 实验名册解析）本来就全部合格，因为三样里一处游戏事实都没有：

- FlatBuffers 的**格式**是通用的；哪个 `.bin` 装的是哪个 root、CMS 的泛型容器名是游戏事实，走 `[tables] fb_roots` / `fb_containers`。
- BestHTTP 的响应缓存是一个被广泛使用的 HTTP 库的落盘格式，剥头就是剥头；缓存在设备上的哪个路径是游戏事实，留项目。
- A/B 名册的结构（`m_variants` / `m_itemGuid` / `m_jsonPatch`）是 CMS 中台的形状；哪个 guid 对应哪个条目是游戏事实，留项目。

也就是说 #48 的第二分支是现有判据的一个特例，而它的第一分支是已经被删掉的东西。

## 被滥用的风险，换了一种形状

#48 担心第二分支「没有它就读不出整个数值层」是主观的、写宽了 `contrib` 会变成杂物间。这条担心成立，但现有判据下它换了一种形状：**风险不在「重要不重要」，而在「这真的没有游戏事实吗」**。一段代码看着通用，实际上把某一款的目录布局或者命名规则焊在里面，是最容易发生的误判——本仓已经踩过：`table` 的自动发现一度想按目录名认语料，`cs-refs` 的两个源码根里有一个是项目自己起的名字。

缓解办法是同一个：把那一样东西**指出来**，然后决定它是作为参数吃进来还是留在项目。写得出「它需要的游戏事实是 X，X 通过 Y 传进来」这句话，就合格；写不出，说明还没想清楚。

## 各部分放哪

不在这里重抄。落点清单（构件 / 命令 / 测试 / 项目里留什么 / 映射表）在 `CONTEXT.md` 的「搬一样东西进来时，各部分放哪」，它是每次开工都要读的那一份。本文第一稿把它抄了一遍，而抄件在写下的同一个 commit 里就已经和原件不一致——这份 ADR 自己的「后果」那一节说的就是这件事。

## Playbook 是另一条线，不要混用

`docs/playbooks/` 收的是**方法**，不是代码，判据不同：**一个方法要在两款以上真实游戏上用过才写下来。**

两条线不一样，是因为它们各自在赌什么不一样。一份构件是否通用，看代码里有没有游戏事实就能判断，不需要第二款游戏来背书。一篇 playbook 断言的是「这个方法可以迁移」，而方法的迁移性没有别的检验手段——只在一款游戏上成立的做法，很可能是在描述那一款的特性。所以 playbook 那边保留两个数据点的要求，而构件这边不保留。

一个窄例外（随 `luban-table-format` 加的）：**从上游开源项目转录的格式参考**可以在没有任何实包确认之前落地，因为它断言的对象是那个上游、在那里可查。它必须在「Verified on」行里说清楚——【源码确认】而无【实包确认】——并写明第一次真实解码能坐实什么。

## 后果

判据的完整叙述只在这里。`CONTEXT.md` 开头保留一句话判据与那份清单（它是每次开工都要读的方向文档，让人跳到 ADR 去看清单是更差的交易），并指向这里；`revenant/contrib/__init__.py` 与 `docs/playbooks/README.md` 引用这里，不再各抄一份。CONTEXT.md 与本文的清单由一条测试钉死，两处必须逐项相同——留两份可读的副本、用测试防漂移，与本仓 `describe.CORE_TERMS` 镜像 CONTEXT.md 术语表是同一个手法。

`revenant status` 报出项目里、以及同级项目共用的上一级 `_tools/` 里已被内置构件取代的脚本。这是报告不是闸门，与 ADR-0002 的代理告警一致。
