# `lint` 引入否定式规则：某些措辞出现时，同行的标识符不再算作源

`revenant lint` 的证据检测通篇是**肯定式**的：`_cites_something()` 把 RVA、符号、文件、标识符、note 引用五个正则或起来，命中任意一个就算「有源」。这条设计有一个系统性漏洞，而 `merge-games-re` 一直在用一份 6.3 KB 的自然语言清单给它打补丁。我们决定给 `lint` 加一条否定式规则，先以 warning 上线。

## 漏洞的形状

实测 `_cites_something`：

| 写法 | 判定 |
|---|---|
| `- 竞速分是普通分的 47%  [坐实]：出处见第一节` | 无源 ✓ |
| `- 竞速分是普通分的 47%  [坐实]：出处见第一节，\`merge_score_race\` 那一列` | **有源** ✗ |
| `- 九款都没有工会  [结构推断]：依据是上表` | 无源 ✓ |
| `- 该值由上两行推得  [结构推断]，见 \`RewardEconomyValueConf\`` | **有源** ✗ |

**篇内回指只要挂上任何一个反引号标识符就能过关。** 而回指恰恰是这个语料里最高频的 lint error 形态——`extract-economy` 的记忆文件自己写着：「第三十轮的对比 note 与第三十一轮的单格 note 各踩三次」。踩得少不是因为规则严，是因为 agent 每轮写完手动跑一遍 `grep -n '同上\|见第.*节\|依据是上'` 兜底。而那份手动兜底也漏过——记忆第 165 条记录了一次：「唯一漏网的是『依据是第 1.4 节那五处各自的判据行』，它既不含『同上』也不匹配『见第.*节』」。

## 自然语言补丁不是补丁

`extract-economy` SKILL.md 第 5 步有一张「写不得 / 改成」表，四行，声称「`revenant lint` 一律判为无源」。逐行实测：

| 写法 | SKILL.md 说 | 实测 |
|---|---|---|
| `res/conf-json/`（目录） | 无源 | 无源 ✓ |
| `res/conf-json/*.json`（通配符） | 无源 | 无源 ✓ |
| 「由上两行推得」 | 无源 | 无源 ✓ |
| `ObjCoinConf`（表名不带后缀） | 无源 | **有源** ✗ |

`ObjCoinConf` 走 `CAMEL_IDENT` 被当成符号收下，最多出一个 `symbol-not-found` warning，不是 error。**一份用来描述工具行为的自然语言副本，四条里错一条，而且没有任何机制会发现它错了。** 这就是不该用文档去补规则漏洞的理由：规则改了文档不会跟着改，文档写错了工具不会报。

## 为什么这是方向上的改变，值得记一笔

`lint.py` 里已经有一次明确的、写进注释的退让：裸 `（T1）` 那套退休标注不被要求带源，理由是「asking for one after the fact flags 114 sentences across eight real projects -- the same worthless-lint failure in the other direction」。这个仓库对误报有过教训，也因此选择了纯肯定式检测。

加黑名单是往回走一步。未来的人看到 `_cites_something` 旁边多出一个措辞黑名单，一定会问「当初为什么破这个例」。答案是：**这两处的失败方向相反。**裸 T1 那次是规则太宽、把正常散文判成违规；这次是规则太松、把回指判成合规，而回指恰恰是这个语料里最常见的失败形态。前者的代价是 114 条噪音，后者的代价是结论看起来有源、实际上悬空。

## 规则的形状与上线方式

判据不是「出现回指措辞就判无源」，而是「**回指措辞出现时，同一行的标识符不能只是这个回指的宾语**」——`见第一节，\`merge_score_race\` 那一列` 该拦，`见第一节；另见 \`Foo.lua:12\`` 不该拦。

**落地的判据比这句话粗，要说清楚。**实现没有做位置判断，而是分类判断：出现回指措辞时，**裸标识符（反引号里的名字、正文里的 CamelCase）一律不算源**，只有 RVA、带点的符号、带扩展名的文件、另一篇 note 算。这挡住了 ADR 要挡的两个形状，但也会误伤「回指 + 另一个真的是补充来源的裸标识符」，例如「同上；另见 `RewardEconomyValueConf` 里另有定义」。

之所以接受这个粗版本：位置判断要断句，而这是中文散文加 Markdown 表格，断错的代价比现在这条大。误伤的兜底是 severity——它是 warning，不是 error。要收窄时先量一遍误伤占比，别凭感觉改。

**先以 warning 上线，观察一轮再决定要不要提成 error。** 黑名单式规则最容易误伤，而这个仓库在误伤上栽过。

**存量不追溯、不豁免。** 53 篇 econ note 加各款笔记会报出一批历史回指，挂着就挂着——这条规则的价值在写的时候拦住，不在事后统计；warning 列表正好是一份待修清单，谁下次动那篇 note 谁顺手修。**不做起算日期或版本豁免**：豁免机制会固化成永久的例外，而 `lint.py` 已经为「不追溯」写过一整段注释解释理由（裸 T1 那处），同一条道理这里照用。

## 上线后量到的第一组数

真实语料（`merge-games-re`，138 篇 note）跑下来 **236 条 warning，落在 44 个文件里**，平均每篇 1.7 条。成分高度集中：

| 触发词 | 条数 |
|---|---|
| `同上` | 213 |
| `依据是上` | 14 |
| 「见第 N 节」一族 | 8 |
| 其余 | 1 |

**199 条在表格行内**，散文里只有 37 条。也就是说这条规则实际上量到的是同一个形状：数值摘要表的源列写着 `同上`。

这是不是误报，取决于站在哪条标准上。按这个语料自己写下的规矩——「数值摘要表的每一行都要有源列，指向文件路径加键名」——它就是那条规矩说的违规，不是误报。按「表格里 `同上` 人类读得懂」的标准，它是噪音。**本 ADR 按前者定，并且不追溯**：236 条挂着当待修清单，谁下次动那篇表谁顺手改。如果后来发现这个判断错了，收窄的方式是明确的——把表格行里紧邻上一行带源的 `同上` 放行——但那要等有人真的被它烦到，而不是现在先猜。

## Consequences

- `extract-economy` SKILL.md 第 5 步那张表里 `ObjCoinConf` 那一行删掉，不改成「会过但只出 warning」——它给的是错的心智模型，删了比改对更省。规则上线后，那张表剩下的三行也可以删：工具会报，不需要文档复述。
- 记忆里 6.3 KB 的「写法要求」小节随之清空，这是 ADR-0005 那份预算的一部分来源。
- agent 每轮写完手动 grep 的动作可以取消。
- 与 ADR-0005 的 `cited-note-missing` 是两回事，别混：那条是「引用的目标要真的存在」（存在性），这条是「这句话里的标识符算不算引用」（语义）。两条都补上之后，「有源」这个判定才既不认空头支票，也不认借来的抵押物。
