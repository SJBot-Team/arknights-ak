### 2.2 三条可直接复用的结论
1. **"时停" = 发送按键 `158`**（Every宏的公共动作；对应返回/ESC 语义）
2. **"暂停按钮" 相对坐标 rel≈(0.9406, 0.0744)** ⇒ 帧 **≈(1806, 80)**
   —— **与 MAA 的 `BattleHasStarted` roi 换算 (1807,79) 完全一致**（两条独立来源互相印证）
3. **"划火柴"的时序**：`按住左键 → 曲线移动到目标格 → 松开`，且**期间/之后发送时停键**

## 三、本方的关键实测（2026-09-15）

- **`adb shell input keyevent`（ESC=111 / BACK=4）无法触发 MuMu 的键鼠宏** —— 宏运行在**模拟器软件层**，
  必须用 **Windows 层**的键盘/鼠标注入（如 SendInput / SendKeys）才能触发；
- 因此**本方实现路线**：**Windows 层注入鼠标拖拽 + 键盘宏键**，而不是继续拼 `adb motionevent`；
- 副作用提醒：MuMu 被遮挡时会停止渲染 ⇒ 注入前需**确保窗口在前台**（`EmuWindowCapture.bring_to_front()` 或激活窗口）。

## 四、本方"划火柴"实现设计（下一步落地）

```
deploy_huochai(card_rel_xy, grid_frame_xy, direction):
  1. 确保 MuMu 窗口在前台（否则渲染停止、注入无效）
  2. 暂停（两种可选）：
     a) Windows 层发 F 键（时停宏）—— 官方推荐
     b) 或点击暂停按钮 帧(1806,80)  【已多次验证可用】
  3. 选中卡片：Windows 层"移动到卡片 → 按下左键"（或发送 S 宏做 0 帧选取）
  4. 划火柴：保持左键，**曲线移动**到目标格（可分若干中间点模拟 curve），松开
  5. 期间/结束后发送时停键（158 对应键），确保游戏停在暂停态
  6. 校验：读"剩余可放置角色"计数（8→7）、卡片消失、费用扣除
```

**注意**：本方的目标是"**把轴表里的操作精确落到指定帧**"，因此最终形态应当是
**"暂停 →（在暂停态完成全部操作）→ 按相位对齐恢复"**，即
**一次暂停内完成同帧多操作**（这正是"同帧多操作"需求的实现路径）。

## 十、★★★决定性突破：PostMessage 通道（2026-09-15，用户提示"换不被干扰的输入方式"）

### 10.1 用户提示
> "我可以手动按 F 触发时停，云迹方案正常。但你的操作看起来被我其他层级的操作屏蔽了，
> 尝试不被我干扰的输入方式。"

⇒ 即：改用**不经过系统输入队列**的注入方式。

### 10.2 三种注入方式的实测对比

| 通道 | 结果 |
|---|---|
| `adb shell input keyevent` | ❌ 不触发宏（宏在模拟器软件层） |
| Windows **SendInput**（含扫描码） | ❌ 不触发（会被用户的前台输入抢占/屏蔽） |
| **Windows `PostMessage` 直接投递到渲染窗口** | ✅✅ **成功触发宏** |

**关键实现**（`plugins/action/win_input.py::post_key / post_click`）：
```python
hwnd = FindWindowExW(主窗口, None, 'nemuwin', None) or 主窗口   # 渲染子窗口
scan = MapVirtualKeyW(vk, 0)                                   # ★ 必须带扫描码
PostMessageW(hwnd, WM_KEYDOWN=0x0100, vk, 1 | (scan << 16))
PostMessageW(hwnd, WM_KEYUP  =0x0101, vk, 1 | (scan<<16) | (1<<30) | (1<<31))
```

### 10.3 实测结果（1-1 演习，云迹方案）

| 宏 | 键 | 实测效果 |
|---|---|---|
| **时停** | **F** | cost 20→22（运行中）→ **cost 23 恒定** ⇒ **★暂停生效** |
| **过帧 33ms** | **T** | fill_px **13 → 19**（+6px = **+1 帧**） |
| **过帧 12ms** | **R** | fill_px **19 → 25**（+6px = **+1 帧**） |
| 过帧 166ms | Y | 无变化（待排查：可能键位冲突或 VK 映射） |

**换算校验**：费用条 180px = 30 帧 ⇒ **6px = 1 帧**；
且 **30fps 下 1 帧 = 33.3ms**，与宏的 `sleep:22`/`sleep:12` 设计吻合 ⇒ **宏与帧率精确对应**。

### 10.4 另一处必须修正的问题：窗口渲染区标定
- MuMu 窗口实际为 **1296×791**（不是 1920×1080）⇒ **游戏画面被缩放显示（缩放 0.675）**；
- 之前**硬编码客户区原点 (2,63) 且按 1:1 映射**，导致所有"帧坐标→屏幕坐标"的点击整体偏移、全部落空；
- 现改为 **`resolve_render_rect()` 动态标定**：`GetClientRect + ClientToScreen`，
  换算 `screen = origin + frame × (client_size / 1920×1080)`；
- 注意：MuMu 的标题栏为**自绘**（客户区含标题栏约 63px），必要时按 UIA 的 `RenderWidget` 矩形再校正。

### 10.5 意义
⇒ **"精确到帧"的操作链路已打通**：**F 时停 + R/T/Y 过帧 + 右键划火柴** 全部可用，
且**通过 PostMessage 后台输入，与用户的真实键鼠互不干扰**（用户可同时使用电脑做别的事）。

## 十一、输入通道的最终分工与"时停"语义（2026-09-15 续）

### 11.1 通道分工（实测结论）
| 用途 | 通道 | 原因 |
|---|---|---|
| **键盘宏（F 时停 / R·T·Y 过帧 / W 暂停选中 / Z 子弹时间…）** | **`PostMessage` 后台投递** | 键盘宏**生效**（已实测），且**不干扰用户的真实键鼠** |
| **鼠标划火柴（右键按住滑动）** | **真实鼠标**（`SetCursorPos` + `SendInput`） | 划火柴宏依据 `curve_rel:mouse;(3.406,6.053)`，读的是**真实鼠标位移**；`WM_MOUSEMOVE` 消息**无效**（已实测） |

### 11.2 "时停"的语义（重要修正）
云迹方案的 F 宏定义为：
```
press  : ['keyboard_press:158']
release: ['keyboard_release:158']
```
⇒ **按下 F 进入时停、松开 F 恢复** ⇒ **F 不是"切换"，而是"按住期间保持"**。

由此解释了两轮实测现象：
- 上一轮"发一次 F（down+up）后 cost 恒定" ⇒ 实际是**那一次恰好把"运行"变成了"暂停"**（切换式观感）；
- 本轮"在已暂停状态下再发一次 F" ⇒ **恢复运行**（cost 23→26）⇒ 与"按住/松开"语义一致
  （快速 down+up 等价于"瞬间暂停后再恢复"，但游戏侧表现为状态翻转）。

**⇒ 正确用法：`keydown F`（保持按下）→ 完成操作 → `keyup F`**，
这样整个"划火柴 + 定位 + 执行"过程都停在暂停态 —— **正是"操作前先步进、定位到帧后再执行"的实现方式**。

### 11.3 坐标标定（★根因修正）
- MuMu 窗口实际 **1296×791**（游戏画面被缩放，**缩放系数 0.675**）；
- 且其**标题栏为自绘**（客户区包含顶部约 **63px** 的非画面区域）；
- ⇒ 渲染区 = **屏幕原点 (5, 84)、尺寸 1296×728**；
- 换算：`screen = origin + frame × (rendered_size / 1920×1080)`。
- **此前硬编码 (2,63) 且按 1:1 映射 ⇒ 所有坐标点击整体偏移、全部落空**（这是多轮"点了没反应"的另一半根因）。

### 11.4 本轮实测

|---|---|
| PostMessage 发 **F**（1-1 演习，运行中） | ✅ **cost 20→22 停在 23 恒定 ⇒ 暂停** |
| PostMessage 发 **T(33ms)** | ✅ fill_px 13→19（**+6px = +1 帧**） |
| PostMessage 发 **R(12ms)** | ✅ fill_px 19→25（+1 帧） |
| PostMessage 发 Y(166ms) | ❌ 无变化（待查，可能键位冲突/VK 映射） |
