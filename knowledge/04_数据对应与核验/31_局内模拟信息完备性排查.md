## 二、数值精度（需求项 1）

### 2.1 已确认的三条事实（T1，证据见 `29` 号文档）

1. **局内数学是 Q32.32 定点**（`FP`，`ONE = 2³²`，64 位整数存储）。
2. **逻辑步长 1/30 秒**（`Time.fixedDeltaTime = 0.03333330154418945`，Unity TimeManager 实读）。
3. **浮点→定点是「单精度乘 2³² 后向零截断」**（`mulss` + `cvttss2si`）。

### 2.2 这对模拟的四条硬性影响

| 影响 | 说明 |
|---|---|
| **不能直接用 float/double 模拟** | 同一条公式在 double 下算到第 16 位有效数字，在 Q32.32 下到第 9~10 位就不同；长时间累积后位置/时间会漂移 |
| **每帧时间是「N × FP.FromFloat(0.03333330154418945f)」** | 不是精确 1/30，也不是浮点累加。累加必须在定点下做 |
| **三角函数必须复刻查表** | `Sin/Cos/Tan/Asin/Acos/Atan2` 走 `SinLut`/`TanLut`/`AcosLut`（`LUT_SIZE=205887`，格点约 2⁻¹⁷），与 libm **不相等** |
| **配置数值进入局内要先过 `FromFloat`** | excel 里的十进制/浮点在加载时被单精度截断并定点化 |

### 2.3 唯一未决点

`FP.FastMul`（= `op_Multiply`，RVA 0x54E2200）是 32×32 部分积展开实现，**低位部分积是否参与舍入尚未逐条核对**。这是"逐位一致"的最后一关。

> 建议：把 `FastMul` 完整函数体（约 20 条指令）反汇编出来后，用 Python 实现同一算法，与本机 Q32.32 参考实现对比一万组随机输入，即可判定舍入方式。

### 2.4 可用的验证判据（重要）

`BattleController` 含 `HashCodeBuilder m_hashCodeBuilder` + `ClientAntiCheatChecker m_antiCheatChecker`，且 `PlayerOperationQueue` + `SnapshotBuilder` + `ReplayController` 齐备 —— 说明**客户端会逐步/定点评状态哈希**。
**这意味着：我们的模拟器只要复刻哈希函数（同一 RVA 可反汇编得到），就能用"哈希是否一致"作为正确性的客观判据**，而不必靠肉眼比对录像。这条应作为模拟器开发的第一优先。

## 三、动画 - 伪代码 - cpp 三层交互（需求项 2、7）

### 3.1 三层的真实构成（本次 cpp 层确认）

```
┌─ 配置层（excel / anon bin）
│    character_table / skill_table / buff_template_data / level_xxx.json
│    ↑ 纯数据；加载后转成 C# 对象，数值经 FP.FromFloat 定点化
│
├─ 伪代码层（Lua / xLua）★ 本次确认存在
│    LuaManager(Singleton) → LuaEnv m_env + IConverter m_decrypter(脚本加密) + ILoadAsset m_assetLoader
│    Torappu.Lua.* 共 26 个类，含 LuaBattleMgr（战斗）、LuaSender、Util
│    Torappu.Battle.Abilities.LuaAbilityBehaviourStub ← 技能行为可由 Lua 实现
│    Torappu.UI.LuaSimpleLayoutAdapter / LuaVirtualViewAdapter / DataBind.LuaDataBinder
│    ↑↓ 双向桥：XLua.CSObjectWrap（290 个导出包装类）
│
├─ cpp 层（IL2CPP 原生）
│    BattleController(isDeterministic / s_fixedFrameCnt / FP s_fixedPlayTime)
│      → Map / Tile / Unit / Enemy / Character / Ability / Buff / Projectile / Scheduler
│    IHotfixable + __Hotfix0_<方法>() DelegateBridge ← iFix 热更钩子（每个可热更方法一个委托桥）
│    ↑↓ 表现同步
│
└─ 表现层（动画）
     UnitAnimator(abstract, MonoBehaviour) → SpineAnimator → CharacterAnimator
     另有 AnimationWrapper（Legacy Animation 包装，UI 用，ILuaCallCSharp）
```

**两条本次新确认的事实**（修正此前知识库中"AK 是否用 xLua / iFix 未确认"的记录）：

1. **Lua 层真实存在且深入战斗**：`LuaManager` 持有 `LuaEnv`，并用 `IConverter m_decrypter` **解密脚本**、用 `ILoadAsset m_assetLoader` 从资源系统加载；`LuaBattleMgr` 与 `LuaAbilityBehaviourStub` 表明**战斗管理与技能行为都有 Lua 实现路径**。
2. **iFix 热更在用**：`IHotfixable` 接口与 `__Hotfix0_*` / `_c__Hotfix0_ctor` 形式的 `DelegateBridge` 字段遍布 `BattleController`、`SpineAnimator`、`LuaManager`、`AnimationWrapper` 等核心类。运行时这些方法会先查热更委托。

### 3.2 交互方向与"谁决定逻辑"

| 方向 | 通道 | 证据 |
|---|---|---|
| Lua → C# | `XLua.CSObjectWrap` 导出包装（290 类）+ 类上的 `[ILuaCallCSharp]` | `BattleController : …, ILuaCallCSharp, IHotfixable, …` |
| C# → Lua | `LuaEnv` / `LuaTable` / `LuaManager.luaEnv` | `LuaManager` 字段与方法 |
| C# → 动画 | `SpineAnimator.PlayAnimation` / `UpdateTimeScale` / `GetAnimationTimeInternal` | dump.cs 316879-316899 |
| 动画 → C# | Spine 事件（`_RegisterSkeletonEvents`），但用途是**音效/特效** | `_PreloadSpineEventSignal(string signal, string id, Unit unit)` 属音频预加载体系；`TryHookAudio` |
| **逻辑时点** | 由 **FP 定点量**决定，不由动画进度决定 | `Entity.attackTime` 是 `FP` 属性（dump.cs 331266）；`EasyToStartAbility.preDelay` 是 `abstract FP`（448120）；`AbstractAnimatedAbility` 同时持有 `FP m_preDelay` 与 `FP m_attackTime` |

**关键判据**：`SpineAnimator` 持有 `private FP m_skipTickTime; // 0x90`，并有 `OnTick` / `_TickSpineManually` / `Update` —— 说明**动画是被手动 tick 的，其时间源是战斗的定点时间轴**，而不是 Unity 的自动播放。

**结论（推断，高置信）**：
> 动画是**表现层**，由定点逻辑时间驱动；逻辑结算时点（攻击何时出伤害、技能何时生效）由 `attackTime` / `preDelay` 等 **FP 逻辑量**决定。
> 换言之：**模拟器不需要动画资源也能算出正确的局内过程**；动画资源用于还原"看得见的表现"和提取碰撞体/枪口位置等少量几何量。

另有一条支撑：`SpineAnimator` 含 `bakeMuzzleController` / `ConstMuzzle[] m_constMuzzles` —— **枪口位置是预烘焙的常量**，弹道起点不实时依赖动画骨骼，进一步说明表现与逻辑解耦。

### 3.3 但 Lua 层是真实缺口

若某技能的机制写在 Lua 里（`LuaAbilityBehaviourStub` 的存在说明这条路径存在），那么**只看 C# 会看到空壳**，机制永远对不上。

**待查清单 → 已于 2026-09-13 全部查清（详见 `35_Lua层定位与解密链路.md`）**：

1. ✅ **脚本位置**：285 个脚本，逻辑路径 `gamedata/[uc]lua/**`，属**初始安装包**（这就是 `hot_update_list.json` 里没有 lua 条目的原因——`gamedata/` 前缀根本不在热更顶层目录里）。入口 `gamedata/[uc]lua/entry.lua`。
2. ✅ **加载器**：`_CustomLoader` = `FileUtil.Combine(m_folder, path)` → `ReplaceExtension(".lua")` → `+ ".M"` → `ResourceManager.CheckExists` → `DirectAssetLoader.LoadAsset<TextAsset>` → `m_decrypter.DeserializeBytes`；`m_folder` 来自 `LuaOptions.luaFolder`。
3. ✅ **解密算法**：`CrypticConverter_A`，`KEY_LENGTH = IV_LENGTH = 16` → **AES-128**；**密钥材料 `PlayerData.chatMask` 的默认值硬编码在二进制里** = `UITpAi82pHAWwnzqHRMCwPonJLIB3WCl`（32 字符 = key16 + IV16）。
4. ✅ **接管范围**：`LuaBattleMgr.RunActions(actionName, blackboard, sourceType, **ref** Context.Snapshot)` 接管 **ActionNode 执行**（且 Lua 能改写战斗上下文快照）；`LuaAbilityBehaviourStub` 把**技能 7 个生命周期回调**整体下发给 Lua。客户端 `HOTFIX_ENABLE = true`。

> **剩余唯一障碍**：脚本本体**不在日服本地客户端**（实测：StreamingAssets 无 `gamedata` 目录，全客户端 0 个 `.lua` 文件）。需另找承载包（国服客户端 / 安装包 / 其他地区包）。**但密钥与算法已就位，拿到即能解。**

> 定位技巧（**已跑通**）：反汇编里 `lea rcx, [rip + X]` 的目标地址是一个 **IL2CPP metadata usage slot**；`stringliteral.json` 的 **`address` 字段就是这个 slot 地址**，可直接按地址命中取 `value`（该名单**不按 usage index 排序**，用 `(usage<<29)|index` 去反查是错的）。`read_cpp.py` 的反汇编注释现已自动显示命中的字符串字面量。

## 八、结论与建议顺序

**结论**：静态配置与资源层已足够支撑"算出正确数值"；**真正的短板集中在代码层的三个点**——执行顺序、Lua 层、状态哈希——这三个不解决，模拟可以做"数值推演"，但做不了"过程复现"。（随机一项已于 2026-09-13 攻克，见 `34` 号文档。）

**建议开工顺序**（每项都已有可用工具 `read_cpp.py`）：

1. **状态哈希函数**（判据先行，后面每一步都能自动验证）
2. ~~**随机算法与种子派生**~~ —— ✅ **已完成**（`34_随机数与确定性复刻.md`：`.NET Framework System.Random`，已复刻 + 逐值验证；种子链已打通）
3. **定长 tick 执行顺序**（`BattleController` 的 tick 与 `m_modules` 遍历）
4. **Lua 脚本载体定位**（决定"伪代码层"能否拿到）
5. 阻挡判定/偏移（K-003/004，解开后可批量收口 K 清单）
