## Ⅰ、碰撞（玩家语义）的物理基础——为什么它只在推拉失衡时出现

> 来源：B 站专栏 **cv6454536**（等--等灯等灯《迫害也需要指导理论：推拉机制及物理引擎详解》，2020-06-17；原文另载 NGA tid=22221080）
> 本地存档：`ak\_raw\bilibili\等等灯等灯\6454536_迫害也需要指导理论：推拉机制及物理引擎详解.md`

### Ⅰ.1 核心：**只有失衡（unbalance）状态下敌人才有物理碰撞箱**

原文："成功的推拉本质上是对敌人施加力并使其进入 unbalance 状态。**只有在这个状态下，敌人才会拥有物理碰撞箱**，且每帧会更新速度并检测状态。"

这解释了为什么玩家口中的"碰撞"（敌人与高台/墙体）**通常只在推拉失衡时被观察到**——平时敌人根本没有激活碰撞箱。

代码印证：物理宿主是 **`Enemy.States.UnbalanceState : …, IPhysicObject`**（dump 379767），方法 `OnPhysicObjectInit` 0x752260 / `OnAfterPhysicSimulate` 0x751BE0 / `OnPhysicObjectRecycle` 0x7522F0 / `_UpdateFriction` 0x752C60 / **`_CheckCollideWithHighLand` 0x7527C0**（与高台碰撞）/ `OnExit` 0x752080。

### Ⅰ.2 底层：Rigidbody2D 与"质量全为 1"

- 敌方单位用 **Rigidbody2D**，**dynamic** 类型
- **所有刚体质量被统一设为 1 kg** ⇒ 相同初态 + 相同力 ⇒ 运动完全一致（这是推拉可预测的前提）
- 两种施力模式：
  - **Force**（持续施力，用于**拉**）
  - **Impulse**（瞬时力，t 默认 1，直接改变动量，用于**推**）
- m = 1 时 Impulse 模式下 **v = F**

### Ⅰ.3 中层：摩擦力与退出条件

```
摩擦力 = g × 质量 × 摩擦系数 = 9.81 × 1 × 0.5 = 4.9
```
- 代码常量：`Consts.FRICTION_FACTOR = 0.5` ✅
- 每帧按摩擦力计算新速度并**重设刚体速度**，然后记录新速度
- **退出 unbalance 的条件**：
  ```
  (新速度 ≤ 0.1 且 已超过 unbalance 保护时间 且 无有效拉力来源)
   或 拥有 UNBALANCE_IMMUNE 效果
  ```
  退出时**清空刚体运动速度**
- 代码常量：`UNBALANCE_MIN_SPEED = 0.1`、`UNBALANCE_PROTECT_TIME = 0.1` ✅

### Ⅰ.4 表层：力量等级与重量等级

| 概念 | 含义 |
|---|---|
| 质量 | Unity 刚体质量，**默认 1 kg**（与"重量等级"无关） |
| 重量等级 | 敌人的重量等级属性，**无上下限** |
| 力量等级 | 游戏中的"小力/中等力度/大力…"档位 |
| **有效力量等级** | **= 来源力量等级 − 目标重量等级**，**值域 [−3, 3]** |

### Ⅰ.5 推（Impulse）

**方向**：
- `relative`：来源 → 目标的向量
- `directional`：一般为来源的朝向
- **directional 会退化为 relative**，当「来源→目标向量与来源朝向夹角 **> 45°**」或「来源与目标坐标距离 **< 0.25**」
- 退化时**有效力量等级减少 2**（默认）

**力度**：
```
力的大小 = 查表(有效力量等级) × 0.02 × MOVE_MULTIPLIER
```
- `0.02` = `Consts.KNOCKBACK_FACTOR` ✅
- `MOVE_MULTIPLIER` = `LevelData.Options.moveMultiplier`（偏移 0x24，关卡可配；原文说默认 0.5）
- **查表**落在 `GameDataConsts.pushForces`（见 K-002 核验：是数组查表 + 双向钳位，**不是多项式**）

**执行**：力 ≠ 0 且目标无 `UNBALANCE_IMMUNE` → 切 unbalance → impulse 施力一次 → **保护时间调至 0.1s**

**位移**：`位移 = 0.5 × 初速度² / 加速度`

### Ⅰ.6 拉（Force）

**方向**：目标 → 来源的向量

**力度**：
```
初始力 = 查表(有效力量等级) × 1          # PULL_FACTOR = 1
某一瞬间的力 = (现距离 / 初始距离)^4 × 初始力      # easeType=6 = easeInQuart，(比值上限 1)
```
- 钩子命中时记录"目标与来源的初始距离"；**力度随距离拉近而急速衰减**（四次方）
- **拉力的解析解不是初等函数** → 原文直接建议"写个模拟器计算大概还快一些"（这正是本项目要造模拟器的一个原始动机）

**执行**：钩中时若力为 0 → 立刻停止钩子；否则切 unbalance + 保护时间 0.1s。
钩子是 projectile，有最大持续时间：**有效力量等级 ≥ −1 → linkDuration（默认 1）**，否则 0.5。
钩住期间持续检查目标是否位于来源的阻挡范围内；**在范围内且只有单个拉力来源时，立刻清空目标速度**（这属于"阻挡"与"拉力"的交互点）。

## 二、阻挡判定与扫描节奏

- **每 3 帧扫描一次**阻挡半径内尚未被阻挡的敌人 → `Character.FIND_BLOCKEE_TICK = 3`（dump 377667）+ `m_findBlockeeTicker`（偏移 0x380）
- 同时有多个可阻挡的敌人时，**优先阻挡距离自身中心最近的**
- 相关方法：`Character.get_blockedEnemies()` RVA 0x705700、`get_blockedTotalVolumn()` 0x705790、`get_canBlockEnemyOnRootTile()` 0x705B00
- 敌人的阻挡体积：`Enemy._blockVolume`（0x2F8）、动态加成 `m_blockVolumeAddition`（0x468）；特殊阻挡条件 `_specialBlockCondition`（0x300）可被 ActionNode 改写

> 与之配套的同族 3 帧常量：避障 `OBSTACLE_AVOID_TICK_PERIOD = 3`、分离 `SEPARATION_TICK_PERIOD = 3`、索敌 `SEARCH_TARGET_TICK = 3`；而**位置更新是每 5 帧**（`Enemy.UPDATE_POS_TICK = 5`）。

## 三、★ 阻挡偏移完整算法

### 3.1 触发前提

**敌人 B 的中点与阻挡它的单位 A 的中点不重合**（距离 **> 0.00001**，代码常量 `1e-05` @0x5D66C44）。若重合则**不产生任何偏移**（例：5-3 开局的术士）。

### 3.2 算法（逐字对应 cv25694535）

```
输入：A = 阻挡者中点，B = 敌人中点

① 长度延长
   AC = AB
   若 |AB| < 0.5 → AC = normalize(AB) * 0.5        # 沿原方向延长到 0.5

② 累加修正向量（仅当「C 点半径 0.1 范围内存在其它已被 A 阻挡的敌人」）
   corr = (0, 0)
   for D in 所有已被 A 阻挡的敌人（不含 B 自己）:
       # 注意：D 取的是该敌人的【稳定阻挡位置】，不是它的当前位置
       d = |D − C|
       if d < 0.1:
           v = rotate90CW(A → D)                   # 把 AD 绕 A 点顺时针旋转 90°
           corr += normalize(v)                    # 标准化后累加
       elif 0.1 <= d < 0.4:
           corr += (0.4 − d) * 50 * normalize(D − C)   # 距离越近，修正越强
       else:                                       # d >= 0.4
           pass                                    # 无事发生

③ 合成
   CE = normalize(corr) * 0.2                      # 累加向量长度固定为 0.2
   AE = AC + CE
   AF = normalize(AE) * |AC|                       # 把 AE 的长度设回 AC 的长度

④ 结果
   F = A + AF                                      # 敌人被阻挡后移动到的位置
   阻挡偏移 = F − B
```

**关键特性**：
- 敌人 B 会在 **0.2s** 内**强制移动**到 F 点（对应 `Enemy.BLOCKING_TWEEN_DURATION = 0.2` 与 `m_blockTween`）
- F 点被记录为该敌人的 **「稳定阻挡位置」**（`Enemy.get_stableBlockPosition()` RVA **0x733D40**，反汇编中在该函数内被调用 3 次）；之后 A 再阻挡其它敌人时，取 B 的位置**取的是 F 而不是 B 的实时位置**
- 若 |AB| 原本 ≥ 0.5，则 AC = AB，此时 |AF| = |AB|：**只改方向、不改距离**

## 四、为什么它决定"敌方单位的精确坐标"

1. **阻挡不是"贴边停住"**：被阻挡的敌人坐标由上述几何算法算出，可能与"沿路径走到干员身边"的位置差出一段（即 BF）。
2. **多敌时互相影响**：修正向量来自**其它已被阻挡敌人**的稳定位置，所以**阻挡顺序会影响最终布局**（先被挡住的敌人先落位，后者的计算以先者的 F 为准）。
3. **会强制改写坐标**：B 在 0.2s 内被 tween 到 F——这是一次**主动位移**，不是"被挡住不动"。
4. **可被利用**：`cv25694535` 给出的实战应用是**把免疫失衡的敌人挤入坑**（蔓德拉入坑的典型案例）；海沫入坑则主要与移动惯性相关，与阻挡偏移关系不大。
5. **入坑判定依赖坐标取整**：偏移后的中点按"四舍六入五成双"取整得到所属地块，进坑格即触发（详见 `composed\阻挡偏移入坑.md` 与 cv31743470）。

## 五、勘误：此前把两套机制混为一谈

2026-09-13 的 K 清单核验（`36_K清单反汇编核验结果.md`）曾给出这样一条"修正"：

> ❌ ~~K-003：`0.4` / `0.2` 不是胶囊碰撞箱尺寸，而是 `BlockBalancer` 的阻挡间距与分离系数~~

**这条修正本身是错的**，原因正是术语混淆：

- **`0.4 × 0.2` 作为物理碰撞箱尺寸（宽 0.2 × 高 0.4，向下偏移 0.1）是正确的** —— 它属于玩家所说的"碰撞"（敌人与高台/墙体），用于推拉失衡时的撞墙，与阻挡无关。
- `BlockBalancer` 的 `CLOSE_DIST_BTW_BLOCKEERS = 0.4` / `MERGE_FACTOR_OF_SEPARATION = 0.2` **确实存在**，但它们属于**阻挡偏移**算法（§三），是另一套东西。两个 0.4 只是**数值巧合**。

**正确表述**：

| 数值 | 所属机制 | 含义 |
|---|---|---|
| 0.2 × 0.4，下偏 0.1 | **碰撞**（敌人↔墙/高台） | 物理碰撞箱（胶囊），在 prefab 序列化 |
| 0.005 / 0.01 | **碰撞** | 停靠距离 / contactOffset（`Consts.TILE_COLLIDE_DISTANCE`） |
| 0.7071 | **阻挡** | 阻挡半径（干员↔敌人） |
| 0.1² / 0.4² / ×50 / 0.2 | **阻挡偏移** | 修正向量计算参数（§三） |
| 0.25 / 0.1 | 受击判定 | 干员 / 敌人的受击圆半径 |
