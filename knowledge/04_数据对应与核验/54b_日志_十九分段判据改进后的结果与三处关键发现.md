### 19.3 ★三处关键发现

**(1) 帧 436~737 是"连续暂停 302 帧"**
段 5 与段 6 的相位**都是 11.14**（无变化）⇒ 合并后是**一段长达 302 帧（≈10 秒）的暂停**。
而**帧 620 的费用已是 2**（10 − 8，芬 8 费，**已部署**）
⇒ **说明"部署动作是在帧 435 前后的暂停中完成的"**
⇒ **完全吻合用户所述**：「**游戏开始时 0 帧暂停**」与「**0 帧选中**」需宏实现 ——
本段正是"**开局暂停 → 立即部署 → 保持暂停很久**"的实机过程。

**(2) 帧 810~862 是"正常运行段"**
53 帧内相位从 9.88 走到 30.0（+20.1 tick）⇒ **≈0.38 tick/帧**… 等等：
若按"跨秒"计（9.88→30 后归零再累加），实际推进约 **20.1 tick / 53 帧 = 0.38**
⇒ 该段**并非 1:1**，而是约为 **1/2.6 速度**（介于 1X 与子弹时间之间）。
**⇒ 需在段内用"相位归零点"精确拟合**（本段可能包含一次跨秒，故先按跨秒修正再算）。

**(3) ★帧 863~1288（426 帧）相位仅 0.9 → 30.18**
426 帧走了约 29.3 tick ⇒ **比例 ≈ 14.5 视频帧/游戏帧**
⇒ **该段游戏以约 1/14.5 的速度运行**（疑似**子弹时间**，或"暂停后 HUD 的缓慢动画"）。
**⇒ 这是"慢速段"，与"1 视频帧 ≈ 1 游戏帧"的正常段形成鲜明对比**，
说明**视频内确实存在多种"游戏速度状态"**（暂停 / 正常 / 极慢）。

### 19.4 结论：映射必须"分段 + 段内拟合"
视频不是"单一时间轴"，而是由**多种速度状态交替**组成 ⇒
必须：①先切段；②在每段内用"**相位归零点**"作为硬锚点拟合 `视频帧 → 游戏帧` 的线性关系；
③段与段之间用"**相位连续性**"（若非跨秒则相位应连续）拼接。

## 二十一、★周期量核实：模拟器攻击周期完全准确，偏差实为"相位偏移"

### 21.1 由标定表反推的实机周期（目标③的最强判据）

|---|---|---|---|
| **芬 命中敌** | 221 / 253 / 285 / 317 / 349 | **32, 32, 32, 32（恒定）** | **32.0 帧 = 1.067 s** |
| **猎狗pro 命中芬** | 255 / 298 / 340 | 43, 42 | **42.5 帧 = 1.417 s** |

⇒ **标定表给出的"周期量"极其干净**（芬的间隔四次全为 32），
**这是校验模拟器最有力的量**。

### 21.2 模拟器侧（同一次复刻）

```

    atk_interval_frames=32  block_cnt=2  df=330  res=0  max_hp=1325

```

### 21.3 ★对比结论

**（1）✅ 攻击周期完全准确**
- **实机周期 32.0 帧** vs **模拟器 `atk_interval_frames` = 32.00 帧** ⇒ **差 +0.00 帧**；
- 模拟器的"芬→敌"伤害序列 **234 / 266 / 298 / 330** ⇒ **间隔恒为 32**，
  与实机的 **221 / 253 / 285 / 317 / 349**（间隔 32）**周期完全一致**。

**（2）⚠️ 真正的偏差是"相位偏移 13 帧"**
- 实机首次命中 **221**，模拟器 **234** ⇒ **偏 +13 帧**；
- 后续逐次对应（253↔266、285↔298、317↔330、349↔362）⇒ **始终偏 13 帧**；
- ⇒ **不是"周期不准"，而是"首次攻击的起始相位"整体后移 13 帧**。

**（3）⇒ 否证上一轮的推测**
上一轮据"后段偏差累积"推测"**周期量（攻击间隔/攻速）不准**"；
本轮实测证明**周期完全正确** ⇒ **该推测被否证**，
偏差来源应转向"**首次攻击的起始时机**"。

### 21.4 新方向：13 帧相位偏移的可能来源
1. **敌人进入攻击范围的时刻**（寻路/移动速度）——若模拟器敌人到位稍晚，攻击自然整体后移；
2. **首次攻击的"前摇"处理**：实机可能是"进入范围即起手"，模拟器可能多了初始冷却；
3. **部署生效时刻**：本方在"帧 10"调 `deploy`，实机在"帧 10"落地；
   若模拟器把"部署生效"算在帧 10 之后若干帧，也会产生固定偏移；
4. **SP/技能初始值**或**首个攻击间隔的取整方式**（32 帧是 1.05 s×30 = 31.5 取整的结果，
   取整方向不同会带来 1 帧级差异，但不足以解释 13 帧）。

## 二十二、★★★核心偏差定位：模拟器缺"攻击前摇"

### 22.1 模拟器实测（复刻：帧10 部署芬(8费)@(3,5)朝左）

### 22.2 与标定表对比

| 实机（标定表） | 帧 | 模拟器 | 帧 | 差 |
|---|---|---|---|---|
| 芬 **进入攻击前摇** | **207** | —（无此阶段） | — | — |

### 22.3 结论（★这是本轮最重要的判定）

| 项 | 模拟器 | 实机（标定） | 判定 |
|---|---|---|---|
| **攻击周期** | **32.00 帧** | **32.0 帧** | ✅ **完全一致（差 0）** |
| **攻击前摇** | **0 帧** | **≈14 帧** | ❌ **缺失，导致整体提前** |
| 敌人侧前摇 | 0 帧（与芬同时） | 较芬出手晚约 48 帧 | ❌ **缺失** |

⇒ **"周期对、相位错"的成因已定位为「缺少攻击前摇（wind-up）」**：
- 模拟器把"进入攻击范围"与"造成伤害"放在同一帧；
- 实机则有 **≈14 帧前摇**（帧 207 前摇 → 帧 221 命中）。

### 22.4 修正方向
1. **在模拟器中引入"攻击前摇"**：
   - 从 `attack_speed`/`base_attack_time` 推导前摇（通常前摇是攻击动画的一部分，
     可用 `atk_interval_frames` 的固定比例，或从数据的 `attackPreDelay` 类字段取）；
   - 语义：单位进入攻击状态后，**经过前摇帧数才结算伤害**，随后进入冷却；
2. **数据侧核对**：查 `character_table.json` / 敌人表的**攻击前摇字段**
   （如 `attackPreDelay`、`attackAnimationTime` 等），并把普攻前摇纳入模拟；
3. **复测**：修正后 `replay_verify.py` 的前段偏差应从 −19 收敛到 ≤2 帧。

### 22.5 附带发现（供参考）
- 模拟器切片中已具备 `cd`（冷却）字段，以及 `state`（MOVE 等）；
  ⇒ 实现前摇只需在"进入攻击"时先置一个 `atk_windup` 计时，到点再结算伤害；

## 二十三、★★攻击前摇修正生效（平均偏差 14.50 → 9.06 帧）

### 23.1 数据层核查结果
- **干员表 `character_table.json`**：**没有攻击前摇字段**（只有 `phases`/`skills`/`talents`/`favorKeyFrames` 等）；
- **敌人表 `enemy_database.json`（1718 键）**：命中 `enemy_1000_gopro`，但**只有 `stats`（属性）**，
  同样**没有前摇字段**；
- ⇒ **前摇应源自动画资源**，数据表不提供 ⇒ 本方改用「**攻击周期比例**」参数化。

### 23.2 引擎修改（`ak_sim/engine.py`）
`_operator_tick` 原逻辑：**冷却归零即 `_do_attack` 结算**（前摇 0）。
改为：
```python
if u.attack_cd_frames <= 0:
    tgt = self.pick_operator_target(u)
    if tgt is None:
        u.attack_windup_left = None          # 目标丢失 ⇒ 前摇重置
    else:
        wl = getattr(u, 'attack_windup_left', None)
        if wl is None:
            u.attack_windup_left = self._windup_frames(u)     # 起手
        if u.attack_windup_left > 0:
            u.attack_windup_left -= 1
        if u.attack_windup_left > 0:
            pass                              # 仍在前摇，本帧不结算
        else:
            self._do_attack(u, tgt)           # 前摇结束 ⇒ 结算伤害
            u.attack_cd_frames = u.attack_interval_frames
            u.attack_windup_left = None

@staticmethod
def _windup_frames(u) -> int:
    ratio = float(getattr(u, '_windup_ratio', 0.4375))   # 由 1-1 标定反推：14/32
    return max(0, int(round(float(u.attack_interval_frames) * ratio)))
```
- **参数来源**：标定「帧207 芬 进入攻击前摇」→「帧221 芬首次命中」⇒ **前摇 14 帧**，
  攻击周期 32 帧 ⇒ **比例 0.4375**；
- 可用 `u._windup_ratio` 覆盖以便做敏感性验证；
- **注**：`Unit` 类定义不在 `engine.py` 中，故用 `getattr` 容错，避免依赖类属性初始化。

### 23.3 ★复测结果（`replay_verify.py`，同一复刻）

## 二十七、★用户补充的机制：远程攻击的"弹道"必须建模

### 27.1 用户原话（2026-09-15）
> 「远程攻击需要考虑**是否为存在弹道的远程攻击**。如果为弹道，
> **子弹出现的位置（同干员不同皮肤可能不同）**、**子弹和敌人的追击过程**均需要被考虑。」

### 27.2 对模拟器的直接含义
| 类型 | 时序 |
|---|---|
| **近战**（如芬） | 出手 →（**前摇**）→ **立即命中** |
| **远程·无弹道** | 出手 →（前摇）→ 立即命中 |
| **远程·有弹道**（如月见夜可能属此类） | 出手 →（前摇）→ **生成子弹**（**起始位置依干员/皮肤**）→ **子弹飞向目标（追击过程，含飞行时间）** → **到达才结算命中** |

⇒ 因此 **"远程命中"的时刻 ≠ "出手时刻"**，而是**晚一个飞行时间**，
且该时间**与距离相关**（敌人移动时还需**追踪**）。

### 27.3 标定表里的直接证据
| 标定帧 | 事件 |
|---|---|
| 432 | 猎狗pro 2 ｜ **芬 命中**（近战） |
| **438** | 猎狗pro 2 ｜ **月见夜 远程命中** |

⇒ 同一次交战中，**"远程命中"比"近战命中"晚 6 帧**。
若两者出手时刻相近，则 **6 帧 ≈ 弹道飞行时间**（可作为弹道速度的标定锚点）。

### 27.4 数据层调查结果（`sim/draft/probe_projectile.py`）
| 检查项 | 结果 |
|---|---|
| 干员表直接字段 | ❌ **无 `projectileId`**（仅有 `rangeId`＝攻击范围） |
| **`skill_table.json`** | ✅ **含 `projectile` 738 处**（如 `projectile_delay_time:0`、弹道 id） |
| **`character_table.json`** | ✅ 含 20 处，形如 `{"key": "projectile", "value": "projectile_chr_orchd2_t"}` ⇒ **弹道挂在技能/天赋的 blackboard** |
| 皮肤表 | ⚠️ `skin_table.json` 不在 `gamedata/`（文件名/位置待查） |
| **模拟器** | ❌ **完全未处理弹道**（`projectile`/`bullet`/`pending_damage` 均 0 处） |

⇒ **结论**：**普攻弹道（若存在）与前摇一样，数据表不直接提供** ⇒ 必须按用户提示建模；
技能弹道则可通过 `blackboard.projectile` 关联到弹道 id。

### 27.5 建模方案（下一轮实施）
1. **新增"投射物"实体**：`{src, dst, pos, speed, born_frame, payload}`
   - **起始位置**：由"发射点偏移"决定（**依干员与皮肤** ⇒ 以配置表建模，默认取干员中心/攻击点）；
   - **飞行**：每帧朝"目标当前位置"推进（**追踪**）；
   - **到达**：`dist ≤ 阈值` 时**结算伤害**并从场上移除；
2. **接入点**：`_do_attack` 中判断"本次攻击是否带弹道"：
   - 带弹道 ⇒ **生成投射物**（伤害延后到到达帧结算）；
   - 不带 ⇒ 立即结算（现状）；
3. **参数来源**：
   - **弹道速度/延迟**：优先取 `blackboard.projectile_delay_time` / 弹道表；
     普攻若查不到 ⇒ 由标定反推（**当前锚点：6 帧**）；
   - **发射点偏移**：按干员/皮肤配置（默认 0，后续按素材校准）；
4. **对轴验证**：用"帧 438 月见夜远程命中"与"帧 432 芬命中"的 6 帧差校准飞行时间，
   再用其它远程事件交叉验证。

## 二十八、★★弹道（投射物）建模实现 —— 远程命中偏差 −23 → −1

### 28.1 实现（`ak_sim/engine.py`）
```python
# ① __init__
self.projectile_enabled = bool(opts.get('projectile', True))   # 可关闭以回退旧行为
self.pending_hits = []                                          # 延迟结算队列

# ② _do_attack：远程且开启弹道 ⇒ 伤害入队延迟结算（否则立即结算）
if self.projectile_enabled and self._is_ranged(src):
    n = self._projectile_frames(src, t)                         # 飞行帧数
    self.pending_hits.append({'f': self.frame + n, 'tgt': t, 'dmg': dmg,
                              'src': src, 'born': self.frame})
    self.logs.append(OpLog(self.frame, 'projectile', {...}))
    continue

# ③ tick：到期结算
self._tick_pending_hits()

# ④ 关键参数与方法
PROJECTILE_SPEED_CELLS_PER_FRAME = 0.1667      # ≈1 格 / 6 帧（由 1-1 标定反推）
_is_ranged(u)      # 按 rangeId 判定（芬 1-1 近战；月见夜 2-3 远程）
_projectile_frames(src, tgt)   # round(格距 / 速度) ⇒ 随距离变化，体现"追击"的时序后果
_tick_pending_hits()           # 目标已死则子弹消散（不结算）
```

- **飞行时间依距离**：用发射时刻的格距计算，**体现了"距离越远、命中越晚"**；
- **目标死亡**：子弹消散、不结算（避免"打死后再补伤害"）；
