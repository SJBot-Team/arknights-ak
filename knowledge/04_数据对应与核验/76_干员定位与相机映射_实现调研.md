## §1 一句话结论（相机偏移到底怎么处理）

> **prts+ 与 MAA 都既不"回正视角"、也不"按当前相机参数重算"——它们把相机当作"由关卡数据决定的常量"，
> 用关卡 JSON 的 `view` 字段做一次 3D 透视投影算好整张格点表，之后整局照表查坐标。**

具体三条（逐条证据见 §2~§6）：

| # | 结论 | 判据 |
|---|---|---|
| 1 | **投影是"一次性"的**：`main()` 在进入主循环**之前**调两次 `transform_map_to_view`，把 `view_data_front` / `view_data_side` 两张常量表算好；部署时**查表**取格点 | ✅ prts+ `main` 反汇编（§3.3） |
| 2 | **没有任何"相机重算/回正"代码**：prts+ 全 21 个 `src*.pyc` 内**无** camera / 视角 / 重投影相关名字；MAA `MaaCore.dll` **有** `BattleHelper::move_camera` 与 `calc_tiles_info`，但**没有任何 `ResetView`/回正任务**（`resource/tasks/*.json` 全表 0 命中） | ✅（§4） |
| 3 | **它们的立场是"假设镜头不动"**：prts+ 只在"部署=侧视 / 技能·撤退=正视"之间切换**投影表**；MAA 的 `MoveCamera` 是**抄作业动作**（用户显式要求平移镜头），不是偏移补偿 | ✅ + 🟡 |

⇒ **给本次实机事故的定性**：这不是"prts+/MAA 有而我们没实现"的缺口，而是**两家的实现都建立在"相机不因操作而改变"的前提上**。
我们的翻车来自**我们自己的额外自由度**（`deploy.py` 直接拖到写死的像素坐标），而不是抄漏了它们的补偿逻辑。
真正的解法见 §7。

```python
def locate_avatar(action) -> None:          # 就地修改 action
    avatars = get_avatars(action.oper)      # 该干员的头像模板（resource/avatar/）
    oper_area_img = capture_game_window(ratioconfig.OPERATOR_AREA_RATIO)
    max_val, max_pos, max_avatar = (0, None, None)
    for avatar in avatars:
        matched = cv2.matchTemplate(oper_area_img, avatar, cv2.TM_CCOEFF_NORMED)
        _, val, _, pos = cv2.minMaxLoc(matched)

    if max_val < imgconfig.TEMPLATE_MATCH_THRESHOLD:
        logger.error(f'Could not find a good matching avatar for {action.oper}, with max_val: {max_val}')
        raise ErrorToLog('未在待部署区找到干员。')
    if len(avatars) > 1:
        replace_avatar(action.oper, max_avatar)          # 多皮肤时回写命中的那张
    # ★ 把 ROI 内坐标还原为**全屏比例坐标**
    action.avatar_pos = ((OPERATOR_AREA_RATIO[0] + max_pos[0] + max_avatar.shape[1] / 2)
                         / SCREEN_STANDARD_SIZE[0],
                         (OPERATOR_AREA_RATIO[1] + max_pos[1] + max_avatar.shape[0] / 2)
                         / SCREEN_STANDARD_SIZE[1])
```

## §3 prts+ 的"格子 → 屏幕"映射（`calc_view` 细节）

模块：`src/logic/calc_view.py::transform_map_to_view(level, side)`（✅ 3.9 反汇编**全文**）

### 3.1 输入与字段来源（回答"输入是什么 / `view` 从哪取"）

- **输入单位 = 格子下标 (i=行, j=列)**，不是世界坐标；函数内换算成"以地图中心为原点"的世界系（✅ `map_point=[j-(width-1)/2, (height-1)/2-i, heightType*-0.4, 1]`）。
- `height`/`width` ← `level['height']`/`level['width']`（✅ `consts` 含这两个键名）。
- **★`view` ← `level['view'][1 if side else 0]`**：关卡 JSON 的 `view` 是 **2×3 数组**，`[0]`=正视(front)相机、`[1]`=侧视(side)相机（✅ 反汇编 + 两家关卡 JSON 双证）。
- 格高偏移 ← `level['tiles'][i][j]['heightType'] * (-0.4)`（✅ `consts` 含 `'tiles'`/`'heightType'`/`-0.4`）。
- 分辨率/视口：**函数内没有**（输出直接就是 0~1 比例坐标）。
- **有没有"相机位移/缩放补偿项" ⇒ 没有**：矩阵只由 `view` + 常量构成，全函数无第二次取 `view`，一旦建表整局不再变。

### 3.2 变换链（逐条对齐反汇编）

```python
DEGREE = 180 / math.pi                      # ★= 57.2957795（度/弧度）；源码常量 180 与 names['pi']
height, width = level['height'], level['width']
x, y, z = level['view'][1 if side else 0]   # side=True → 用第 2 个相机
T = [[1,0,0,-x],[0,1,0,-y],[0,0,1,-z],[0,0,0,1]]                     # 平移
P = [[FROM_RATIO/tan(20*DEG),0,0,0],[0,1/tan(20*DEG),0,0],
     [0,0,-(FAR+NEAR)/(FAR-NEAR),-(FAR*NEAR*2)/(FAR-NEAR)],[0,0,-1,0]] # 透视 20°
Rx = [[1,0,0,0],[0,cos(30*DEG),-sin(30*DEG),0],
      [0,-sin(30*DEG),-cos(30*DEG),0],[0,0,0,1]]                     # 俯视 30°
Ry = [[cos(10*DEG),0,sin(10*DEG),0],[0,1,0,0],
      [-sin(10*DEG),0,cos(10*DEG),0],[0,0,0,1]]                      # ★仅 side 用
final = P @ Rx @ ([Ry] if side else I) @ T
out_pos = []
for i in range(height):                      # i = 行
    for j in range(width):                   # j = 列
        mp = np.array([j-(width-1)/2, (height-1)/2-i,
                       level['tiles'][i][j]['heightType'] * -0.4, 1])
        vp = (final @ mp); vp = vp / vp[3]; vp = (vp + 1) / 2   # 透视除法 → NDC → 0~1
        tmp_pos.append((vp[0], 1 - vp[1]))   # ★ y 反转 = 屏幕比例
    out_pos.append(tmp_pos)
return out_pos                               # [row][col] = (rx, ry)
```

**与 `04/53 §六` 对照**：`53` 的矩阵形式**基本正确**，两处修正/确认：
① `53` 写 `DEGREE = math.pi/180`，**打包版实际是 `180 / math.pi`**（✅ 反汇编 `LOAD_CONST 1(=180) / LOAD_GLOBAL 0(math.pi)`）；
因随后一律写 `tan(20*DEGREE)`，**数值结果相同**，只是变量名易误导。
② `53` 猜的"20° 透视 / 30° 俯视 / 10° 侧旋"**数值与方向都对**，且本轮确证 `rotate_y` **只在 `side=True` 时乘**，
乘法顺序为 `P @ Rx @ Ry @ T`（side）/ `P @ Rx @ T`（front）✅。

## §4 ★相机偏移的三种可能：证据与结论

> 三种可能：① 动态重算 ② 回正视角 ③ 不管（依赖"不动视线就不偏"）

### 4.1 prts+（判定：**③ 不管**）

| 可能 | 证据 | 判定 |
|---|---|---|
| ① 动态重算 | `transform_map_to_view` **只在 `main` 里被调用 2 次**（进关时）；`perform_deploy`/`perform_skill_or_retreat` 的 `co_names` **无** `transform_map_to_view`、无任何重投影；`main` 的 `view_data_front/side` 是普通局部变量，主循环内无重赋值 | **否** ✅ |
| ② 回正视角 | 21 个 `src*.pyc` 的 `co_names`/`co_consts` 中 `camera`/`视角`/`reset`/`居中`/`回正` **零命中**；`mumu_controller.__all__` 只有 `handle_coordinates, pause, esc, mouseclick, mousedown, mouseup, mousemove` ⇒ **可用键只有 ESC**，无 Tab/视角键注入 | **否** ✅ |
| ③ 不管 | 部署序列里唯一的修正是固定 `DEPLOY_DELTA_RATIO=0.02`；`view` 来自关卡数据（静态）；时序上在**暂停态**执行（`pause()`+`esc()`），镜头不再自行漂移 | **是** ✅ |

### 4.2 MAA（判定：**③ 不管**，但额外具备①用于它自己的镜头动作）

| 可能 | 证据 | 判定 |

### 4.3 旁证与总判据

- `04/51`：游戏**本身有**「视角切换（Tab）」、一键撤退 Q / 技能 E / 子弹时间 Z ⇒ 存在"视角类"按键，但 **prts+ 与 MAA 都没用它**。

## §7 给本项目的可执行建议

### 7.1 定性：我们该"重算映射"还是"回正视角"？

| 方案 | 可行性 | 结论 |
|---|---|---|
| **A. 回正视角**（发 Tab/复位键） | 先要**确认游戏确有"视角回正"语义**，且**复位后相机严格等于初始态** 🔴 未实测；且启用 2D 俯视后 `view` 投影（3D 透视）**整张表作废** | **不采用**（风险 > 收益） |
| **B. 动态重算映射**（按当前相机参数重投影） | 需要**实时估计相机位姿**（`view` 三元组或画面→地图的单应矩阵）——可从画面里的棋盘特征或"选中后的绿色可部署格"反解 🔴 未实现 | **中期方向**（最正确的做法，但工作量大） |
| **★C. 每次都"从画面反查格坐标"**（等价于 prts+ 的"关卡 view 一次算好 + 暂停态执行"） | **零新依赖、今天就能用**：我们已有 `find_green_cells()`（选中后绿格）与 `find_diamond()`（吸附后菱形中心） | **★立即采用** |

### 7.2 最小改动方案（今天就能改、直接治 §1 的事故）

> **核心断言：格子屏幕坐标只允许来自当前画面；禁止用"静止画面预计算"的坐标去落格。**

1. **落点只允许来自当帧检测**（改 `code\vision\plugins\action\deploy.py`）
   - `Deployer.deploy()` 在 `preselect=True` 之后、真正拖拽**之前**调用 `find_green_cells(img)`；返回空 ⇒ **立即中止**（`{'ok': False, 'reason': 'no_green_cells'}`），**不回退任何缓存坐标**。
   - "格名 → 屏幕点"改**两级**：① 有 `view` 标定表 ⇒ 用它做**候选**（在同色绿格里挑目标格）；② 候选**就近吸附**到绿格格心（最近邻，阈值 ≤ 0.6×格距）。
   - **停用写死的 `CARD_X`**（`72 §2.2` 已证明会点空）；卡位一律来自 `identify_deploy_row()`，要求 `score ≥ 0.55 且 margin ≥ 0.10`，否则报"卡位不可信"。
2. **提交后的最后一道闸**：`mouseup` 后立刻用 `find_diamond()` 取**吸附后**干员位置，
   与"预期格心"比距离；> `0.8×格距` ⇒ 判 `SEMANTIC` 失败并**撤销**（ESC）。
   ★ 这与 prts+/MAA 一致：**两家都不相信"我算的坐标"，都靠"游戏吸附后的画面"收口**。
3. **暂停态 + 不拖地图**：prts+ 在**暂停态**下拖（`pause()`+`esc()`），MAA 用 `DeploymentWithPause`。
   我们 `ensure_paused()` 已有；**补一条**：拖拽路径**不得进入屏幕边缘 120px**（贴边触发地图平移），
   必要时把落点限制在中央 60% 内，或先平移镜头再重新检测绿格。
4. **（中期）建立"格→屏"可回查链路**（对齐 MAA）：把 `04/59` 的仿射标定升级为完整的
   `transform_map_to_view` 移植（`plugins/action/calc_view.py` 已有，注意 §8-4 的两处），
   并用**绿格实测点在线标定**（`CalcView.calibrate_view` 可换成 3 点解算）；**每局重新标定一次**，不跨局复用。

### 7.3 一句话给主会话
> **别在"静止画面"上算格坐标再拖——prts+ 和 MAA 都不这么干。先点卡片 → 当帧检测绿格（或读网格） → 就近吸附落点 → 松手后用菱形中心复核。**
> `find_green_cells()` + `find_diamond()` 已把两端实现，只是 `deploy()` 的落点参数还在用外部常数。
