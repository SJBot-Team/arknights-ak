## 一、PRTS+ 的格子定位方案（★核心发现）

PRTS+ 是 PyInstaller 打包（`D:\__soft\ak\prts+\prts+.exe` + `_internal\`）。
其 exe 内的引导串里可读到模块名 **`src.logic.calc_view`** ⇒ **格子定位 = 逐关卡的相机标定 + 地图数据做投影**，
**不是**对格子做模板匹配。

### 1.1 逐关卡地图数据（`_internal\resource\map\`，共 **3480** 个关卡）

文件名形如 `main_01-01-obt-main-level_main_01-01.json`，结构：

```json
{"code":"1-1","name":"孤岛","levelId":"obt/main/level_main_01-01","stageId":"main_01-01",
 "width":9,"height":7,
 "view":[[0.0,-4.81,-7.76],[0.5975098586953793,-5.31,-8.642108163374733]],
 "tiles":[[{"buildableType":0,"heightType":1,"isEnd":false,"isStart":false,"tileKey":"tile_forbidden"}, ...], ...]}
```

- **`tiles`**：`height`×`width` 的二维数组，每格给出 `buildableType` / `heightType` / `isStart` / `isEnd`；
- **`view`**：**两个 3 维相机向量**（`view[0]` / `view[1]`）—— 我方 `plugins/action/calc_view.py`
  的 `CalcView(view=(x,y,z))` 正是消费这个量（`side=False/True` 对应是否叠加 `ROTATE_Y`）。

### 1.2 1-1 的可部署格（由 PRTS+ `tiles` 直接读出）

```
可近战部署（buildableType=1, heightType=0）：(1,4) (2,4) (3,1) (3,2) (3,3) (3,4) (3,5) (3,6) (3,7) (4,5) (5,5)
高台（buildableType=2）：14 格
```
即 **r3 一整排 7 连（c1~c7）**，加上竖向通道 **c4 的 r1~r2** 与 **c5 的 r4~r5**。

## 二、★格子定位的"三重互证"（我们的实测 ↔ PRTS+ 数据）

### 2.1 我方实测（第 71 轮，实机暂停+选卡态）

`Deployer.find_green_cells(cell_px=130)` 得 **7 个绿格单元**：
- 一行 6 连：`(807,502) (932,502) (1057,502) (1181,502) (1306,502) (1431,502)`，**x 步长 ≈124.5**
- 另一格：`(1057,364)` —— 恰为"左起第 3 格的**上一行**"（dy=−138）

### 2.2 与 PRTS+ `tiles` 联立 → 判别性检验

把绿格与"可部署格集合"配对时，**方向有两个解**：

| 假设 | 那"多出来的一格"落到哪 | 该格在 PRTS+ 里是 |
|---|---|---|
| x **随 col 递增** | r2c3 / r4c3 | **高台(21)** ✗ |
| **x 随 col 递减** | **r2c4** | **road(10)** ✅ |

⇒ **只有"x 随 col 递减"成立**，唯一确定的映射为：

```
x(col) = 1556 − 124.5 · col
y(row) = 502 + 138 · (row − 3)
```

**校验**：PRTS+ 的可部署列表**包含 (2,4)**，与上表假设一致 ✅

### 2.3 结论

| 轴表格 | (row,col) | 映射像素 | 在 PRTS+ 可部署表 | 实测绿格 |
|---|---|---|---|---|
| **D6**（芬） | (3,5) | **(934, 502)** | ✅ | ✅ (932,502) |
| **D4**（月见夜） | (3,3) | **(1182, 502)** | ✅ | ✅ (1181,502) |

⇒ **实测绿格、PRTS+ tile 数据、仿射拟合三者互证**，D6/D4 的落点坐标可用。

> ⚠️ **注**：直接把 PRTS+ 的 `view` 喂给 `CalcView` 做投影，其输出与实机屏幕**对不上**
> （4 种 `view×side` 组合下 D6.x 均 > D4.x，与实测相反；且格距 162.5px ≠ 实测 124.5px），
> 说明 PRTS+ 内部还有一层**视口/分辨率换算**未在资源里体现。
> ⇒ **本项目采用"实测绿格 + tile 数据反解"的标定**（已三重互证），`view` 仅作交叉参照。

## 三、★实机战斗操作流程（用户给出的 PRTS+ 方案）—— 实现规格

```
① 记绝对时间：统计「费用条满」的**次数**（每条满 = 1 秒 = 30 帧；配合费用条相位得到整帧）
② 操作前 ≈1 s：进入「子弹时间」（选中/拖出干员 → 游戏减速）
③ 操作前 5 帧：在子弹时间内**逐帧过帧**（宏过帧键）
④ 暂停定位：把游戏**暂停**在**预定帧**
⑤ 在该帧**部署干员**（拖出 → 落格 → 提交）
```

### 3.1 与既有结论的衔接

| 步骤 | 既有实现/结论 | 缺口 |
|---|---|---|
| ① 费用条满计数 | 费用条相位识别已有（满条 180px、6px=1 帧）；费用数字识别已有 | **"满条次数"累加计数**未实现（现有轴表用"费用数字 + 相位"） |
| ② 子弹时间 | —— | **未实现**：需在操作前 1s 拖出干员进入减速 |
| ③ 过帧 | MuMu 宏过帧键（云迹 R/T/Y）已记录；`F` 键 = 按下暂停/松开恢复 | 未接入时钟闭环 |
| ④ 暂停定位 | 暂停键 (1810,81) **已实测可用** | 需与"目标帧"闭环 |
| ⑤ 部署提交 | **抓取可用（ADB `motionevent`）**；**提交五种通道全失败**（见 D1 矩阵） | **卡点**：见 §四 |

### 3.2 ★对 D1 的新解释（本流程给出的启发）

既有 D1 矩阵显示：抓取成功、**释放不提交**。结合本流程可给出一个**新的、可检验的解释**：

> **必须在「暂停」状态下、且在正确的帧上提交**；此前失败可能是因为提交时**游戏并未暂停在目标帧**
> （或在暂停态下"释放"事件被吞）。⇒ 下一轮应严格按 §三 的 ①→⑤ 顺序：
> **先建立"帧"（费用条满计数 + 相位）→ 子弹时间 → 过帧 → 暂停 → 再释放**。

## 四、下一轮落地清单（按优先级）

1. **"费用条满次数"计数器**：在既有费用条相位识别上加"满条沿"检测 ⇒ 绝对时间 = 次数×30 + 相位；
2. **子弹时间进入/退出**：操作前 ≈1s 执行"选中/拖出干员"使其减速；验证是否真的减速（对比费用条相位推进速率）；
3. **过帧闭环**：把 MuMu 过帧宏与费用条相位联动，做到"操作前 5 帧开始逐帧"；
4. **暂停定位**：暂停后读相位确认"就是目标帧"，再执行 ⑤；
5. **部署提交**：按 §3.2 的顺序重试 ADB `motionevent`（抓取已知可用）+ 释放；
   仍不通则试"**真实光标 `SetCursorPos` + `PostMessage` 宏键**"（宏动作含 `click_rel:mouse`，读 `GetCursorPos`）。
