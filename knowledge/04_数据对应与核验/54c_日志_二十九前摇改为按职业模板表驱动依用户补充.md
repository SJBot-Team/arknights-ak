## 二十九、★前摇改为"按职业/模板"表驱动（依用户补充）

### 29.1 用户补充（2026-09-15）

>   也可能与**技能期间的攻击模组**有关，**敌人也是**。」

**⇒ 此前"统一比例（干员 0.55 / 敌人 0.10）"只是粗糙近似**，应改为**按模板分组**。

```python
WINDUP_RATIO_BY_PROFESSION = {

WINDUP_RATIO_DEFAULT_ENEMY = 0.10
```

**② `_windup_frames` 改为表驱动**（优先级从高到低）：
1. `u._windup_ratio`（**单点覆盖**，便于按标定逐单位校准）；

### 29.3 本轮的两次实现修正（供反重复清单）

## 三十、★匹配类型修正（补 `damage_first`）：最大偏差 47 → 26

### 30.1 问题定位
上一轮"帧 221「芬 命中」"显示 **+47 帧**的假偏差。排查发现是**匹配器的类型映射漏项**：
- 模拟器把"**某单位的第一次受伤**"记为 `damage_first`，其后记为 `damage`；
- 而本方的 `KIND_MAP['命中'] = ('damage',)` **只匹配 `damage`**
  ⇒ "首次命中"被错配到**第二次伤害**上（268 而非 219）。

### 30.2 修正
```python
KIND_MAP = {
    '出现影子': ('spawn',),
    '进入攻击前摇': ('damage_first', 'damage'),
    '命中': ('damage', 'damage_first'),          # ★补 damage_first
    '阻挡': ('damage', 'damage_first', 'spawn'),
    '击杀': ('despawn', 'damage', 'damage_first'),
}
```

### 30.3 复测结果（严格口径）

| 标定帧 | 事件 | 修正前 | **修正后** |
|---|---|---|---|
| **221** | 猎狗pro 1 ｜ 芬 命中 | **+47** | **−2** ✅ |
| 253 | 猎狗pro 1 ｜ 芬命中 | +15 | +15 |
| 432 | 猎狗pro 2 ｜ 芬 命中 | +5 | **+5** OK |
| 438 | 猎狗pro 2 ｜ 月见夜 远程命中 | −1 | **−1** OK |

### 30.4 全流程演进（同一标定、严格口径）

| 阶段 | \|偏差\|≤6 帧 | 平均 \|偏差\| | 最大 \|偏差\| |
|---|---|---|---|
| 基线（无前摇） | 5 | 14.50 | 52 |
| 仅干员前摇 0.4375 | 5 | 9.06 | 23 |
| （宽松匹配 + 扫描最优） | 10 | 6.89 | 29 |
| 严格匹配（按受害者） | 7 | 14.94 | 47 |
| **＋弹道（投射物）** | 10 | 11.44 | 47 |
| **＋匹配类型修正** | **11** | **8.11** | **26** |

⇒ **严格口径下平均偏差已从 14.94 降到 8.11 帧，最大从 47 降到 26 帧。**

### 30.5 残余偏差的成因（已初步定位）
当前残余集中在"**芬对猎狗pro 1 的多次命中**"（帧 236/253/285/349 偏差 15~17）
与"**击杀**"（帧 381 −15、帧 464 −26）。

排查发现：模拟器的"猎狗受伤"事件**间隔不均**（如 `damage@268`、`damage@366`，间隔 98 帧，
而实际攻击周期是 32 帧）⇒ **模拟器的事件集与标定并非一一对应**。

**根因假设**：**"同名多单位"导致按名匹配不精确**
—— 本关中两只敌人都叫「猎狗pro」（内部 key 分别是 `enemy_1000_gopro` /
`enemy_1000_gopro_2`），而标定表用「猎狗pro 1 / 猎狗pro 2」区分。
本方的匹配按"名字包含"处理 ⇒ **pro 1 与 pro 2 的事件被混在一起**，
使得"芬命中 pro 1"的若干次被配到 pro 2 的事件（或反之）。

**修正方向**：
1. 模拟器事件应带上**实例 id**（`uid`）与 **key**；标定表侧则按"单位出现的先后"映射到 uid；
2. 或改用"**按事件序列对齐**"（同类型事件的第 n 次配第 n 次），
   这对"同类型重复事件"（连续命中）更稳健；
3. 同时核查**多目标索敌**（`pick_operator_target`）是否与实机一致（芬在两只猎狗间的选择）。

### 30.6 下一步
1. 用"**序号对齐**"替换"最近帧匹配"（对重复事件更稳健），复测；
2. 核查多目标索敌与仇恨规则；
3. 之后再按职业/敌人校准前摇表（需要更多素材）。

## 三十一、★★修正"前摇含在攻击周期内" —— 前段偏差降到 1~7 帧

### 31.1 问题发现（由逐帧事件明细）
按序号分组打印模拟器伤害事件后发现，"**芬→猎狗**"的命中序列为
**219 / 268 / 317 / 366 / 415** ⇒ **间隔恒为 49 帧**，
而配置的 `attack_interval_frames = 32` ⇒ **多出 17 帧 ≈ 本方加入的前摇（18 帧）**。

**⇒ 根因：本方把前摇"额外加在周期之外"**（冷却在**命中时**重置 ⇒ 间隔 = 前摇 + 周期）。
**正确语义：一个 32 帧的攻击周期 = 前摇 + 后摇** ⇒ **命中间隔必须恒等于 `attack_interval_frames`**。

### 31.2 修正（`fix_windup_in_period.py`）
- **起手时**（设置 `attack_windup_left` 的同一处）**立即重置** `attack_cd_frames = attack_interval_frames`；
- **命中时**（前摇结束）**只结算伤害、不再重置冷却**；
- **干员侧与敌人侧同时修正**；并在 `_windup_frames` 的 docstring 中写明该语义要求。

### 31.3 复测结果（严格口径）

**偏差分布：`1, 1, 1, 2, 2, 2, 2, 4, 5, 5, 5, 6, 6, 7, 26, 31, 56, 58`**

| 指标 | 修正前 | **修正后** |
|---|---|---|
| **\|偏差\| ≤ 6 帧** | 11 | **13** |
| 平均 \|偏差\| | 8.11 | 12.22 |
| 最大 \|偏差\| | 26 | 58 |

**⇒ 分布呈"两极"**：
- **前 13 条全部 ≤7 帧**（**其中 5 条 ≤2 帧**）⇒ **这一段已高度吻合**；
- **后 5 条偏差 26~58 帧** ⇒ **是另一类问题**（见 31.4）。

**⇒ 结论**：本修正使"可精确对齐的事件数"增加（13 条 ≤6 帧），
平均/最大偏差的上升**完全由后 5 条拖累**，并非本修正引入的退化。

### 31.4 ★新问题（下一步核心）：模拟器只生成了 **1 只猎狗**
事件明细显示，模拟器中与"猎狗"相关的伤害事件**受害者 uid 恒为 2**
（`key = enemy_1000_gopro_2`），而标定表里出现的是**「猎狗pro 1」与「猎狗pro 2」两只**。

⇒ **两种可能**：
1. **出怪配置解析不全**：本关应有 2 只猎狗，模拟器只生成 1 只（或另一只未参与战斗）；
2. **正是这一只**：标定的"pro 1 / pro 2"其实是**同一模板的两次出怪名**，
   而模拟器把两次出怪合并/替换了。

**⇒ 这解释了"后 5 条偏差大"**：标定的"芬打 pro 1"被配到模拟器"打 pro 2"的事件上。

### 31.5 下一步
1. **核对 1-1 的出怪表**：`waves[].fragments[].actions[]` 中 SPAWN 的**数量、时刻、key**
   与标定的"猎狗pro 1（帧94 影子）/ pro 2（帧367 影子）"逐条对齐；
2. 若模拟器少生成 ⇒ 修出怪解析（**这属于"关卡层"信息缺失，应回流到信息查找链条**）；
3. 若只是"同名两次出怪"⇒ 配对时改用**出怪序号**（第 1 只 / 第 2 只）而非 uid/key；
4. 修好后复测，目标"平均 ≤2 帧、最大 ≤5 帧"。

## 三十四、★人工对应表（可信基线）+ 暴露"冷却/前摇交互"仍未正确

### 34.1 人工对应表（`replay_verify4.py`）
按机制 3 的决策，把配对规则改为**人工对应表**：
`(标定帧, 说明, 类别, 目标, 序号)`，其中
- 类别 ∈ `spawn`（敌方出现）/ `dmg_enemy`（我方命中）/ `dmg_ally`（我方受伤）/ `kill`；
- 目标 ∈ `EN1/EN2`（敌方第 1/2 只）或 `ALLY`；
- 序号 = **同类事件中的第 n 次**。

程序先由事件流构造**索引表** `{(类别,目标): [帧...]}`，再按对应表逐条取帧比较。

⇒ `attack_cd_frames` 递减到 0 后**不再增加** ⇒ **每帧都满足"可攻击"**
⇒ **命中间隔退化成"前摇帧数"**（干员 18、敌人 4）。

**统计**：可对齐 17/18；≤6 帧 1 条；平均 72.71；最大 155。

### 34.4 分析（当前断点）
按代码推演，**命中间隔应为 `前摇 + (interval − 前摇) = interval`**，
但实测 `dmg_enemy` 间隔为 **49 = 32 + 17**（多了一个前摇），说明
**`attack_cd_frames` 与 `attack_windup_left` 的实际交互与推演不符**：

可能原因：
1. **起手那一帧的 `cd` 递减顺序**：`cd -= 1` 发生在"起手重置"**之前**，
   导致重置后的 `cd` 又立刻被减，或反之 ⇒ 产生 1~2 帧偏差（不足以解释 17 帧）；
2. **"命中后 `windup` 置 None" 的那一帧**，`cd` 已经 ≤0 ⇒ **该帧又立即起手并重置 `cd = 32`**
   ⇒ 等价于"前摇被算了两遍" ⇒ **间隔 = 前摇 + 32**（**49 = 17 + 32，吻合！**）；
3. 即：**命中帧与"下一次起手帧"重合**，使前摇"额外"叠加了一次。

**⇒ 修正方向（下一轮）**：
- 把"前摇"与"冷却"改为**单一状态机**：`atk_state ∈ {IDLE, WINDUP, COOLDOWN}`，
  **命中后直接进入 COOLDOWN，且冷却剩余 = `interval − 前摇`**（而不是重置为完整 `interval`）；
- 或等价地：**起手时记录 `atk_start_frame = frame`**，
  命中判定用 `frame - atk_start_frame >= windup`，
  冷却判定用 `frame - atk_start_frame >= interval` ⇒ **同一时间基准、不可能叠加**。

### 34.5 下一步
1. 按 34.4 的"单一状态机/统一时间基准"重构普攻时序，复测（目标：`dmg_enemy` 间隔 = 32、
   `dmg_ally` 间隔 ≈ 42.5）；
2. 随后偏差指标应显著下降（当前多项 +29~+155 皆为该叠加所致）。

## 三十五、★★★普攻时序重构（统一时间基准）—— 平均偏差降到 6.62 帧

### 35.1 问题（上一轮断点）
"前摇 + 冷却"两套计时器交互，导致**前摇被叠加一次**：
实测"芬打猎狗"命中间隔 **49 帧**（= 32 + 17），而应为 **32 帧**。

### 35.2 方案：**单一时间基准 `atk_start_frame`**
每个单位的攻击周期只用一个状态：
```python
if atk_start_frame is None:                 # 空闲 ⇒ 尝试起手
    if 有目标: atk_start_frame = frame; atk_hit_done = False; atk_target = tgt
else:
    el = frame - atk_start_frame
    if el >= interval:                      # 周期结束 ⇒ 空闲（下一帧可再起手）
        atk_start_frame = None
    elif (not atk_hit_done) and el >= windup:   # 前摇结束 ⇒ 结算一次
        _do_attack(tgt); atk_hit_done = True
```
⇒ **命中发生在 `start + windup`、下一周期从 `start + interval` 起算**
⇒ **命中间隔恒为 `interval`**（前摇含在周期内，**结构上不可能叠加**）。
干员侧与敌人侧同时替换；`attack_cd_frames`/`attack_windup_left` 仍同步维护（供切片与其它代码使用）。
