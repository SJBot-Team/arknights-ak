## 一、结论（已验证成功）

**部署 ＝ 两段 `motionevent` 拖拽序列**：

```
① 选中并拖到格子
   motionevent DOWN  <卡片中心>
   motionevent MOVE  <中间点…>（至少 2 个中间点）
   motionevent UP    <目标格子>
      ⇒ 进入「朝向选择」状态：出现白色菱形选择框 + 红色「点击取消」

② 定朝向（拖动菱形到目标方向的角）
   motionevent DOWN  <菱形中心>
   motionevent MOVE  <朝目标方向移动>
   motionevent UP    <目标方向的角>
      ⇒ 部署完成
```

**成功判据（三重，实测全部成立）**：
1. 干员出现在战场上；
2. **底部对应卡片消失**（12 张 → 11 张）；
3. **「剩余可放置角色」计数 −1**（8 → 7）。

## 二、关键坑（都踩过）

| 做法 | 结果 |
|---|---|
| `input tap` 点卡片 | ❌ 会被判成**长按**，弹出干员详情面板（但**证明点击被接受**、且地图出现绿色可部署高亮格） |
| `input tap` 点绿色高亮格 | ❌ 不部署 |
| `input swipe` 卡片→格子（600/1000ms） | ❌ 不部署 |
| `motionevent DOWN`+`UP`（快速单击） | ❌ 无反应（太短） |
| **`motionevent DOWN→MOVE→MOVE→MOVE→UP`** | ✅ **成功进入朝向选择** |
| **再对菱形做一次 `DOWN→MOVE→UP`** | ✅ **完成部署** |

⇒ **规律：AK 的部署识别的是"带中间点的拖拽序列"，不是 tap、也不是单段 swipe。**
（`input swipe` 在部分模拟器上只发首末两点，游戏不认；`motionevent` 可精确控制每个点。）

## 六、★最终协议（第二次成功，三重确证）2026-09-15

**成功证据**：费用 15→8（恰好扣掉第一张卡片的 7 费）、「剩余可放置角色」8→7、第一张卡片消失。

**关键修正（两次失败的根因）**：
1. **朝向菱形的中心 = 游戏「吸附后」的干员位置**，**不是拖拽落点**！
   实测拖到 (1200,400)，游戏吸附到格心 **(1063,333)**，必须以菱形中心为起点拖朝向。
2. **费用不足时游戏完全不接受拖拽**（费用 8 < 下一张卡 9 费 ⇒ 无反应、菱形检测返回 None）
   ⇒ 部署前先校验 `费用 ≥ 卡片费用`。

**封闭式协议**：
```
0. 校验：费用 ≥ 卡片费用；游戏处于暂停态
1. motionevent DOWN  <卡片中心>
   motionevent MOVE  <中间点×2>
   motionevent MOVE  <目标格>
   motionevent UP    <目标格>          ⇒ 进入朝向态（白色菱形 + 点击取消）
2. 检测菱形（白框、面积大、近似正方形）得到 (cx,cy,w,h)
3. motionevent DOWN  <(cx,cy)>
   motionevent MOVE  <向目标方向 r/2>
   motionevent UP    <(cx±r, cy) 或 (cx, cy±r)>，r ≈ 0.45h   ⇒ 部署完成
```

**封装**：`plugins/action/deploy.py`（`Deployer`：`motion/pause/resume/read_cost/find_diamond/set_direction/deploy/deploy_timed`）。

## 七、部署复现：问题界定与四步排查法（2026-09-15）

**协议方向已两次成功**（§六 三重判据），**但复现条件未完全锁定**。本轮在 1-1 与 TR-1 上以相同序列多次尝试均未进入朝向态。

**已测试并排除的做法**：`input tap` 点卡片 / `input tap` 点格子 / `input swipe` 拖拽 / `motionevent DOWN+UP` /
不同格子坐标 / 不同关卡 / 费用不足（费用充足时同样失败）。

**待验证的关键假设**：
1. **tap 卡片后弹出的详情面板是否阻挡了随后的拖拽**（成功案例中 tap 与拖拽之间隔了一次截图，面板可能已收起）；
2. **选中态缺少视觉确认** —— 应在 tap 卡片后确认"绿色可部署高亮格"出现，再进行拖拽；
3. 暂停态的"可交互性"是否稳定（本轮多次出现"点了暂停但费用仍在涨"）。

**建议的四步排查法**（每步截图确认后再进行下一步）：

| 步 | 动作 | 确认方式 |
|---|---|---|
| 1 | `ensure_paused()` | 返回 True 且界面为 battle（**已可用**） |
| 2 | 点卡片 | **截图确认"绿色可部署高亮格"出现**（需新增"绿色高亮检测"） |
| 3 | 拖拽卡片到绿格 | **`find_diamond()` 返回菱形** |
| 4 | 拖菱形定朝向 | **费用扣除 / 卡片消失 / 可放置数 −1** |

任一步的截图都能定位失败点，避免再次"整段失败却不知在哪一步"。

**理想练手环境（本轮发现）**：**TR-1「战地医疗」训练关** —— 理智 0、仅 5 敌人、固定编队（巡林者/芙蓉/夜刀），
入口：终端 → 序章 EP00 地图 → TR-1 → 开始行动。

## 八、★遮挡源确认：剧情与敌人面板（2026-09-15，用户提示后核实）

**用户提示**：「训练关有剧情遮挡，这是你操作失败的主要原因」—— 经实测**完全确认**。

### 8.1 剧情遮挡（首要根因）
- TR-1 进入战斗时有**交互式教学剧情**（角色台词框 + 右上角「跳过」）；**剧情期间大部分输入被屏蔽**；
- **跳过方式**：**长按「跳过」** ⇒ 弹出**「是否跳过剧情？」**确认框 ⇒ **点 ✓**（约帧 (1189,540)）⇒ 恢复操作；
- 剧情期间**点对话框可以推进对话**（输入并非完全屏蔽）。

### 8.2 敌人信息面板（第二遮挡源）
- 点战场上的敌人会弹出「敌人信息」面板（关闭按钮 ✕ ≈帧 (1875,261)），**遮挡待部署卡片区**；
- 此前我把"卡片坐标"点成了战场 ⇒ 反复弹出该面板，干扰判断。

### 8.3 ★绿色可部署格检测成功
关掉敌人面板 + 点卡片（帧 **1693,981**）后，`find_green_cells()` 检出 **2 个绿格：(1327,405)、(863,631)**
⇒ **证明"点卡片进入选择态"生效**，四步排查法的**步 2 已打通**。

### 8.4 待部署卡片必须动态检测（`find_cards()`）
卡片**位置随数量变化**：TR-1 仅 2 张时在 **x≈1693 / 1819**（靠右），而非从屏幕左缘开始。
⇒ 硬编码坐标必然点错；已实现按"底部条带列方差"分段检测。

### 8.5 仍缺最后一步
点绿格 (1327,405) 后**绿格消失但未部署**（费用未扣、无菱形、无干员）
⇒ **"点绿格"不是提交方式**；应改为 **"选中卡片后拖拽到绿格"**（落点用检测到的绿格坐标）。

### 8.6 下一轮的固定流程（每步截图确认）
```
① 关掉所有遮挡面板（敌人信息面板 ✕）
```
