## §1 一句话结论

**Q1：用户的说法方向对、表述要改。** 3 帧节拍是 **`SelectorTrigger.Search` 自己的入口闸门**（每次 `Search(false)` 都受它约束，代码里**没有**"已有目标就跳过搜索"的短路）；但**攻击状态机每帧根本不调用 `Search`** —— 它每帧读的是**缓存目标**（`TargetTrigger.get_target`，Slot 8）。⇒ 不是"锁定了就绕过扫描"，而是**"攻击周期压根不经过索敌扫描"**：扫描只在"需要重新取目标"时被调用一次，而**每次调用都照样吃 3 帧闸门**。

**Q2：组/间隔复核通过，相位不存在，`delayToBorn` 符号定稿。** 层级是 `waves[] → fragments[] → actions[]`，**没有第二层"组"**（同一个 `action` 的 `count` 就是组）；组内间隔就是 `timeOffset(i) = 前序 preDelay 链 + i × action.interval`（🟢T1，与 `04/65` 一致）；`_DoSpawn` 里**没有任何 tick/相位判定**；`delayToBorn` 的符号 = **`timeOffset -= delayToBorn`（提前，负值夹 0）**，来源是 **prefab 序列化字段 `Enemy._delayToBorn // 0x2DC`（运行期零写点）**。"影子"在客户端**没有独立实体类**。

## §2 Q1 —— 3 帧扫描到底管哪一层

### 2.0 先定一条口径（本轮新实证，后续所有槽位引用都靠它）🟢T1

`0x56D0`（IL2CPP "按槽号调虚方法" 桩）反汇编：

```
0x0056F1  mov rax,[rbx]            ; rax = 对象 klass
0x0056F7  add rdx,rdx              ; rdx = 2*slot
0x0056FD  mov r8,[rax+rdx*8+0x138] ; methodPtr
0x005705  mov rdx,[rax+rdx*8+0x140] ; methodInfo
0x005717  jmp r8
```
⇒ **`slot S` 的方法指针 = `*(void**)(klass + 0x138 + S*16)`**。
互证：`dump.cs 378219` `Character.get_attack()` 是 **`Slot: 146`**，而 `0x138 + 146*16 = 0xA58`，正是 `_StartAttack 0x71B350` 的 `0x71B46C mov r8,[rdx+0xA58]`。**⇒ 换算口径成立**。故 **`Search`（`Slot: 13`）= `+0x208`**（`TargetTrigger` 家族 24 个 `Search(bool)` 覆写全是 `Slot: 13`）。

### 2.1 闸门长在 `Search` 里，而且**没有"已锁定"短路** 🟢T1

`SelectorTrigger.Search(bool force)` **RVA `0x714210`**（`Slot: 13`）关键指令：

| 地址 | 指令 | 含义 |
|---|---|---|
| `0x7142CF` | `mov rcx,[rbx+0x48]` | `m_findTargetTicker` |
| `0x7142DE` | `call 0x1805CF2F0` | `CompoundPeriodicTicker.get_isReady()` |
| `0x7142E5` | `jne 0x1807142F0` | 就绪 ⇒ 往下走 |
| `0x7142E7` | `test dil,dil` / `je 0x180714515` | **未就绪且 `force==false` ⇒ 直接 `return false`，连选都不选** |
| `0x7142FF` | `call 0x1805CEC10` | `CompoundPeriodicTicker.Next()`（消耗一次节拍） |
| `0x714337` | `call 0x1806DFDD0` | `TargetSelector.FindTargets_DISPOSE` ← 真正的索敌 |
| `0x71436C` | `cmp byte ptr [rbx+0x20], sil` | `_keepTarget // 0x20` |

★ **判据（回答"只在首次生效吗"）**：从 `0x7142CF` 到 `0x714501` 的**整条路径上没有任何"`m_lastTarget` 非空就提前返回"的分支**；`_keepTarget`（`0x71436C`）只决定"新列表里还有旧目标时**是否改写** `m_lastTarget 0x38`"（`0x7143AF` 查在不在新表里 → `0x7143B8 mov bl,1` 保留旧值），**不跳过搜索**。`force` 是唯一的旁路。

### 2.2 节拍器是"限流器"，不是"自主扫描器" 🟢T1

`SelectorTrigger.FixedUpdate()` **RVA `0x713EE0`** 全部指令只有两条出口：
`0x713F1C..0x713F2C` ⇒ `jmp CompoundPeriodicTicker.Tick() 0x5CF010`；`0x713F31` ⇒ Lua hotfix。
**它不调用 `Search`。** ⇒ 3 帧节拍**只限制别人调用 `Search` 的频次**，不会自己定期去搜。

`SelectorTrigger.Reset() 0x714030`：`_overrideSearchTargetTick // 0x28 < 0` ⇒ `CompoundPeriodicTicker.Reset(isDeterministic, waitFirstPeriod=false)`（`+0x18A`），周期保持构造期的 **3**；`>= 0` 才覆盖（`04/67 §2.2` 分支实证，本轮不重复）。⇒ **相位锚点在"触发器 Reset（≈ 单位诞生）"**，不是每帧重排。

### 2.3 子类也没有短路：`SelectorTriggerWithCertainCondition.Search 0x713A30` 🟢T1

它先算"条件"（`_checkContainBuffs // 0x50`、`_isAnd // 0x51`、`_buffKeys // 0x58` 循环查 `Entity.ContainsBuff 0x35F7E20`、`_checkHasSp // 0x60`（`Entity.get_sp 0x360D650 > 0`）、`_checkNotAbnormalFlags // 0x61` + `Attributes.GetAbnormalFlag 0x352A420`），得到 `r15b`，然后：

```
0x00713C48  call 0x180714210   ; SelectorTrigger.Search(force)   ← 无条件
0x00713C52  and  al, r15b      ; return search && conditions
```
⇒ **条件不满足也照样搜**（只是把结果 AND 成 false）。**没有"已锁定 ⇒ 跳过"这一层。**

### 2.4 攻击每帧路径读缓存目标，不搜敌 🟢T1

`Character.States.Blackboard.AttackState.OnTick 0x71AAD0`（`Slot: 12`）关键段：

```
0x0071ACAE  call Character._FetchCombatTarget  0x701D70   ; 走 m_replacement，与选择器无关
0x0071ACD3  call Object.op_Inequality          0x5964E30
0x0071ACE5  test al,al ; jne 0x71AD38                      ; 有战斗目标 ⇒ 切战斗态
0x0071AD09  call 0x1800056D0  (ecx=0x92 → Slot146)         ; Character.get_attack()
0x0071AD1B  call 0x1800056D0  (ecx=0x12 → Slot18)          ; 该能力上的 Slot18() → bool
0x0071AD33  jmp Character.States.Blackboard._NextAttackOrExit 0x71B210
```

`_NextAttackOrExit 0x71B210`：

```
0x0071B29D  call Character._SearchAttackTarget  0x703DE0    ; 每帧都调
0x0071B2A2  test al,al ; je 0x71B2BB
0x0071B2A6  xor r8d,r8d                                     ; ★ firstAttack = false
0x0071B2AE  call Character.States.Blackboard._StartAttack   0x71B350
```

`_GetTarget 0x71B0C0`（攻击态取目标）：`0x71B17E mov r8,[rdx+0x1b8]` = **`0x138 + 8*16` = Slot 8 = `TargetTrigger.get_target()`**（`SelectorTrigger.get_target 0x714AB0`，`Slot: 8`）⇒ **纯读 `m_lastTarget` 缓存**。
`CombatState._NextCombatOrExit 0x71CF80` 同样：`0x71CFF0 call _GetTarget 0x71CEF0` → `0x71D002 call _StartAttack(target, firstAttack) 0x71D0A0`，**全程无 `Search`**。

`Character._SearchAttackTarget 0x703DE0` 的函数体（`0x703DE0`–`0x703FB4`）调用清单：`Unit.get_hasAttack`、`Entity.get_canUseAtkOrCbt`、`Slot146=Character.get_attack`、该能力 `Slot18`、`Character.m_replacement // 0x390` 上的接口方法（接口分派内联序列 `0x703ED5`–`0x703F62`）。**函数体内没有对 `0x714210` 的调用，也没有 `[klass+0x208]` 的虚调用。**

### 2.5 全二进制里 `Search`（Slot 13）的调用点只有 35 处，战斗侧极少 🟢T1

扫全部可执行段 `call/jmp qword ptr [reg+0x208]`：**共 35 处**（另扫 `mov r,[r+0x208]; call r` = **0 处**）。战斗代码里可确证的：

|---|---|---|
| `0xA267A2` | `MultiMeleeAttack.CheckAnotherSpell 0xA265A0`（+0x202） | `rdi = this[0x230]`（**`TargetTrigger`**）→ `0xA26796 xor edx,edx`（**`force=false`**）→ `0xA267A2 call [rax+0x208]`（`Search`）→ `0xA267B0 this.Slot8()`（`get_target`） |
| `0xA50DD4` | `AttachListenerToTileAbility._OnUnitReborn` | 遍历触发器数组：`[rax+0x208]`(Search) + `[rax+0x1f8]`(Slot12=Reset) |

★ 结论：**"每帧索敌"在代码里不存在**；`Search(false)` 是**事件驱动**的（连击判定、单位重生、特定 buff/技能 OnTick 等）。`SelectorTrigger.Search` 的 E8 直接调用者只有 3 处（全是 `*Trigger.Search` 覆写调 base，`xref 0x714210`）。

## §3 Q2 —— 组 / 间隔 / 相位 / 影子 / `delayToBorn` 符号

### 3.1 层级结构与生成顺序 🟢T1

`LevelData` → `waves[] (WaveData)` → `fragments[] (FragmentData)` → `actions[] (ActionData)`；分支另走 `branches[].phases[] (BranchData.PhaseData)`。

| 环节 | 类.方法 + RVA | 说明 |
|---|---|---|
| 波次 | `Scheduler._DealWave 0x62A6E0` → 状态机 **`Scheduler.<_DealWave>d__107.MoveNext 0x630C50`** | `_DealWave` 本身只是 `[IteratorStateMachine]` 构造器 |
| 片段 | `Scheduler._DealFragment 0x62A5F0` → **`Scheduler.<_DealFragment>d__108.MoveNext 0x630740`** | 时间基 `0x63085F call BattleController.get_userFixedPlayTime 0x3565AE0` |
| 分支阶段 | `Scheduler._DealBranchPhase 0x62A440` → **`Scheduler.<_DealBranchPhase>d__109.MoveNext 0x62FD20`** | 独立队列、自己的 `actionBlockTimer` |
| 动作展开 | **`Scheduler._DealAction 0x629EE0`**（普通静态方法，非迭代器） | 见 §3.2 |
| 队列消费 | **`Scheduler.DefaultWaveHandler.<ExecuteActionQueue>d__12.MoveNext 0x62E0A0`** | 见 §3.3 |
| 出怪 | `Scheduler._DoSpawn 0x62B570` → **`Scheduler.<_DoSpawn>d__112.MoveNext 0x6330E0`** | 见 §3.4 |

**生成顺序**：`_DealFragment` 逐 action 调 `_DealAction`（`0x630A2F call 0x629EE0`），**全部写进同一个 `m_actionQueue // 0xB0`**，随后**按 `timeOffset` 排序**（比较器 `Scheduler.<>c.<_DealFragment>b__108_0` 与 `<_DealBranchPhase>b__109_0` **共用同一实现 RVA `0x62F8C0`**，键 = `AItem.timeOffset`），再交给 `ExecuteActionQueue` 顺序等待。
⇒ **"先确定组再依次按固定间隔生成"成立，但"组"就是同一个 `action.count`**；代码里**没有**"wave→fragment→branch→action→group" 这种多一层分组对象。

### 3.2 组内固定间隔 = `i × action.interval`（复核 `04/65`/T-079，✅一致）🟢T1

`Scheduler._DealAction 0x629EE0` 实测指令：

```
0x00629FC1  addss xmm6, dword ptr [rbx+0x24]   ; xmm6  = fragmentPreDelay + action.preDelay(0x24)
0x0062A10C  call 0x184787270                   ; enemyMap 查 action.key
0x0062A115  subss xmm6, dword ptr [rbp-0x11]   ; ★ xmm6 -= EnemyItem.delayToBorn(+0x10)
0x0062A11A  comiss xmm7(=0), xmm6
0x0062A11F  xorps xmm6, xmm6                   ; ★ 负值夹 0
0x0062A130  cmp eax, dword ptr [rbx+0x20]      ; 循环 i < action.count(0x20)
0x0062A159  cvtdq2ps xmm0, xmm0                ; (float)i
0x0062A15C  mulss xmm0, dword ptr [rbx+0x28]   ; × action.interval(0x28)
0x0062A161  addss xmm0, xmm6                   ; ★ timeOffset = base + i*interval
```
⇒ **`timeOffset(i) = fragment.preDelay(0x10) + action.preDelay(0x24) + i × action.interval(0x28) − delayToBorn`（下界 0）**。
`fragmentPreDelay` 的来源：`<_DealFragment>d__108.MoveNext 0x6309F3 movss xmm6,[rax+0x10]`（`FragmentData.preDelay // 0x10`）→ `0x630A2F` 传参。
**"相邻 `timeOffset` 差 = `interval`"** ⇒ 与 `04/65 ⑫`、`03/28 §V2/V3` **完全一致（✅复核通过，无修正）**。

### 3.3 队列消费 = 绝对偏移 + **定帧**等待（★一处修正）🟢T1

`ExecuteActionQueue d__12.MoveNext 0x62E0A0`：

```
首轮: 0x0062E160 xorps xmm6,xmm6            ; prev = 0
      0x0062E163 mov dword ptr [rbx+0x28],0  ; i = 0
      0x0062E189 mov rax,[rax+0xB0]          ; m_actionQueue
每轮: 0x0062E1E9 movss xmm0,[rbx+0x38]       ; 下一个 item.timeOffset
      0x0062E1EE comiss xmm0,xmm6            ; 与上一个比较
      0x0062E334 subss xmm0,xmm6             ; ★ 取差
      0x0062E33A call AsyncUtil.WaitForFixedSeconds 0x35293A0
```
⇒ 等待量 = **相邻差**；**第一条的等待量 = `item[0].timeOffset`（因为 `prev` 初值为 0）** ⇒ 队列语义 = "以 fragment 起点为 0 的绝对偏移量"。
★ **修正 `04/65 ⑫` / `03/28 §V3`**：被调的是 **`AsyncUtil.WaitForFixedSeconds(float) 0x35293A0`**（**定帧**等待），**不是 `WaitForSeconds`**（两处旧文写的都是后者）。这对复刻很关键：间隔按"帧对齐"实现。

### 3.4 「出生相位」：不存在 🟢T1 / 🟡

- `Scheduler` 字段表（`dump.cs 359003`–`359036`）里 **没有任何 ticker / 相位字段**（只有计数器、`m_waveStartTime // 0x88`、`m_fragmentStartTime // 0x90`、队列、列表、协程 id）。
- `Scheduler.<_DoSpawn>d__112.MoveNext 0x6330E0` 的调用清单：`Scheduler._NotCountInTotal 0x62BA80`、`Scheduler.TakeSnapshot 0x628120`、`BattleController.CreateEnemy(…) 0x35454F0`、`Scheduler._AlertSpawnError 0x629610` —— **无 `PeriodicTicker`、无 `get_isReady`、无相位判定**。
- 🟡 保留：`WaitForFixedSeconds 0x35293A0` 内部的取整方向（ceil/floor）未逐指令核 ⇒ "出生时刻"仍可能有 **≤1 帧/次** 的量化抖动。

### 3.5 ★「影子」与 `delayToBorn` 符号：**定稿** 🟢T1

**(a) 符号方向 = 提前（`timeOffset -= delayToBorn`）**，见 §3.2 的 `0x62A115`+`0x62A11A/11F`。
⇒ `delayToBorn > 0` ⇒ 出怪动作**提前** `delayToBorn` 秒入队（减到负则夹 0）。**方向上只能让出怪更早，不可能造成观测偏晚。**

**(b) 值的来源 = prefab 序列化字段（本地表拿不到）** 🟢T1
`Scheduler._CreateEnemyItem 0x629A20`：
```
0x00629B80  call BattleFactory.CreateEnemy(string) 0x6067D0   ; 造一个"模板敌人"（仅为读字段）
0x00629BA5  op_Inequality(template, null) → null 则 LogError("Couldn't load the prefab of enemy key: ")，delayToBorn = 0
0x00629CA9  call RuneManager.PreprocessEnemy              0x929EA0
0x00629D6B  call Enemy.get_delayToBorn()                  0x730550   ★
0x00629D72  movss dword ptr [rbp-0x40], xmm0                          ; ★ 写 EnemyItem+0x10
0x00629DB4  call PoolManager.Recycle(Component)           0x2659010   ; 回收模板
```
`Enemy.get_delayToBorn 0x730550`：
```
0x007305DD  cmp byte ptr [rbx+0x2e0], cl     ; _onlyDelayToBornOnTileStart
0x007305E3  je  0x1807306AA                  ; false ⇒ 直接返回 _delayToBorn
0x0073060F  r8 = [rdx+0x1e8]                 ; Slot 11 ⇒ 当前格 GridPosition
0x00730637  call Map.TryGetTile(GridPosition, out Tile)   0x59E310
0x00730650  call Tile.get_tileKey()                       0x5E8B20
0x00730667  call String.Equals(…, "tile_start")           0x4BF46B0（另有 str 'tile_flystart'）
0x007306AA  movss xmm0, dword ptr [rbx+0x2dc]              ; ★ 返回 _delayToBorn // 0x2DC
```
⇒ **语义**：`_delayToBorn // 0x2DC`（float 秒，prefab 上配）；`_onlyDelayToBornOnTileStart // 0x2E0` 为真时**只有出生格是 `tile_start`/`tile_flystart` 才取该值**，否则 0。1-1 的怪从起点格出生 ⇒ 走生效分支 🟡（未核 1-1 tiles 的 key）。

**(c) 运行期零写点 ⇒ 与 `_preDelay` 同类的"本地缺"字段** 🟢T1
扫全二进制"写 `[reg+0x2DC]`"：**仅 1 处**，且落在 `NoTargetRangedAttack.DoSetData 0xA45F4E`（那是该**能力自己的** 0x2DC，不是 `Enemy`）。
⇒ **`Enemy._delayToBorn` 在托管代码里没有任何写点 = Unity prefab 序列化字段**，与 `AbstractAnimatedAbility._preDelay // 0x180`（`04/71 §4.2`）同一类缺口。**这就把"`delayToBorn` 符号未定稿"结清了，但把"值未知"钉成了 🔴。**

**(d) 「影子」没有独立实体类** 🟡
`find "Shadow"` 在战斗命名空间下未命中 `EnemyShadow` 之类的实体类；`get_delayToBorn 0x730550` 的 **E8 调用者共 5 处**（`_CreateEnemyItem+0x34B`、`Enemy.States.BasicState.OnEnter 0x73C245/0x73C2BF`、`Enemy.States.BasicState._PlayAnimation 0x73C83E/0x73C901`）⇒ `delayToBorn` 是 **`Enemy` 自身在 `BasicState` 里的"出生表现窗口"**，玩家看到的"影子/出生渐变"就是这段时间的动画，**不是另一个实体**。🟡（表现层未逐指令核）

### 3.6 1-1 数据佐证：模拟器的 90 / 360 本来就是"零取整"的正确值 🟢T1

`level_main_01-01.json`：`waves[0].preDelay = 0.0`；3 个 fragment，`preDelay` = **0.0 / 9.0 / 17.0**。
fragment#1 的 `actions[]`（节选）：`DISPLAY_ENEMY_INFO(enemy_1000_gopro_2, preDelay=3.0)`、`SPAWN(enemy_1000_gopro_2, preDelay=3.0, count=1, route=1)`、`STORY(preDelay=3.0)`、`SPAWN(enemy_1000_gopro_2, preDelay=22.0)`、`SPAWN(enemy_1000_gopro, preDelay=12.0)`、`SPAWN(enemy_1000_gopro, preDelay=27.0)`。

按 §3.2 公式（`delayToBorn` 未知记 0）：
- 第 1 只（`enemy_1000_gopro_2`）：`0 + 3.0 + 0×1.0 = 3.0 s` = **90 帧** ⇒ 模拟器 90 ✅
- 第 2 只（`enemy_1000_gopro`）：`0 + 12.0 = 12.0 s` = **360 帧** ⇒ 模拟器 360 ✅

⇒ **调度公式这一层，模拟器与代码逐字一致**；标定表是 **94 / 367**（3.133 s / 12.233 s）⇒ 残差 **+4 / +7 帧** **不来自公式层**。
`count>1` 的组（`fragment#2`：`enemy_1007_slime_2 count=4 preDelay=3.0 interval=9.0`）第 n 只 = `9 + 3 + 9(n−1)` 秒 ⇒ "组内固定间隔"就是这里的 `interval`，**共享同一个 `action.preDelay`**。

### 3.7 出生"早 4~7 帧"的最可能解释 🟡

按排除法：

| 候选 | 判 | 依据 |
|---|---|---|
| **`delayToBorn`（影子→实体）** | ❌ 方向相反 | `0x62A115 subss` ⇒ 只能让出怪**更早**，不可能解释"观测偏晚"；且值未知 |
| **调度相位** | ❌ 不存在 | §3.4：`Scheduler`/`_DoSpawn` 无 ticker/相位 |
| **标定表零点** | ⚠️ 不能排除但不能单独解释 | 费用时钟 Δ=0（`04/54`/`73`）⇒ 若零点整体偏，伤害类应同向偏；实测伤害类正负混杂 |
| **★调度执行链的固有延迟 + 定帧等待的累积量化** | ✅ **最可能** | 1-1 队列按 `timeOffset` 排序后为：`DISPLAY 3.0`、`SPAWN 3.0`、`STORY 3.0`、`SPAWN 12.0`、`SPAWN 22.0`、`SPAWN 27.0`。起点若固定晚 ~4 帧 ⇒ 第一条 +4（94 ✓）；到 12.0 s 那条又多经过 **2 次零长等待**（3.0 那两条 `Δ=0`，每次 `WaitForFixedSeconds` 至少让出一帧）⇒ +4+2~3 = **+6~7（367 ✓）** |

⇒ 一句话：**更像"从战斗开始到 fragment 协程真正跑起来"的起点延迟（≈4 帧）+ 每次 `WaitForFixedSeconds` 的帧对齐（零长等待也要让一帧）**，而**不是** `delayToBorn`、也**不是**时间基零点。🟡（这是推断，不是指令级证明；判据见 §5-5）

## §4 对模拟器的可执行修改建议（明确到"哪一行放哪个条件"）

> 目标：让 `04/73 §3.1` 的 A/B 不再"越加越晚"。

1. **【移 gate：最高优先】把 `enemy_search_phase` 从"攻击推进"移到"重新取目标"**
   - 现状（错）：gate 包住了"已锁定后的攻击/出伤节奏"。
   - 应改为：**只有当该单位"当前没有有效目标"（或目标已死亡/丢失/需要切换）而要走一次 `Search(false)` 时**，才检查相位。
   - 落到行：`ak_sim`（`engine.py`）里现在写成 `if phase_ok(f): <攻击推进>` 的那一处，**拆成两件事**：
     ```
     # ① 攻击推进：永不受相位影响（周期 = m_attackTime // 0x1A8）
     if unit.attack_ready(f):  unit.do_attack(f)
     # ② 重新索敌：只在这一步加闸门
     if (not unit.has_valid_target()) and phase_ok(f):      # phase_ok = (f - unit.spawn_frame - 2) % 3 == 0
         t = select_target(unit)
         if t: unit.set_target(t)
     ```
   - 即**条件从 `phase_ok(f)` 改成 `(not unit.has_valid_target()) and phase_ok(f)`**；`has_valid_target()` 判断目标存活且仍在范围内（对应 `_GetTarget`/`Slot 8` 缓存命中）。
2. **首次入场的第一次取目标用 `force=true`**（`Search` 的 `force` 旁路），除非你要复刻"`_minTargetNum` 不足时 `Search` 也消耗一次节拍"这一副作用（`0x7142FF Next()` 在失败分支**之前**就已执行）。
3. **同步"零长等待也消耗一帧"的规则**，并新增可调项 `scheduler_start_offset`（默认 0；1-1 建议先试 **4 帧**）⇒ 用来吃 §3.7 的 +4/+7；**不要**用改 `preDelay` 的办法对齐（那会破坏与代码公式的一致性）。
4. **新增 `delay_to_born` 参数（默认 0，先不打开）**，并在事件流里把 `spawn_action` 与 `born` 拆成两个事件（`born = spawn_action + delay_to_born`）。只有拿到 prefab 真值后才启用；**当前它对"偏早"的解释力为零（方向相反）**。
5. **间隔实现**：组内第 n 只 = `fragment.preDelay + action.preDelay + (n−1)*interval`（同一 action 共享 preDelay）；等待按 **`WaitForFixedSeconds`（定帧）** 语义，别用连续浮点。
