## 〇、一句话结论

> 明日方舟局内的主随机源是 **`.NET Framework` 的 `System.Random`（Knuth 减法法 / subtractive algorithm）**，不是 Unity 的 xorshift，也不是 LCG。
> 它在客户端里叫 **`LegacyRandom`**，由 `RandomFactory.Create(seed, DEFAULT=0)` 构造；`BattleController.RANDOM_ALGORITHM` 常量正是 `0`。
> 该算法**完全公开且逐位确定**，已复刻并通过验证。

### 1.1 `Sample()` 反汇编（关键 12 行）

```
mov  eax, [rcx + 0x20]        ; inext
inc  eax
cmp  eax, 0x38                ; 56
cmovge eax, edx(=1)           ; if (inext >= 56) inext = 1
mov  [rcx + 0x20], eax
mov  r8d, [rcx + 0x24]        ; inextp
inc  r8d ; cmp r8d,0x38 ; cmovge r8d, 1
mov  rdx, [rcx + 0x28]        ; SeedArray
mov  ecx, [rdx + r9*4 + 0x20] ;   SeedArray[inext]
sub  ecx, [rdx + rax*4 + 0x20]; − SeedArray[inextp]
lea  eax, [rcx + 0x7fffffff]  ;   retVal + MBIG
cmovns eax, ecx               ; if (retVal < 0) retVal += MBIG
mov  [rdx + r9*4 + 0x20], eax ; SeedArray[inext] = retVal
cvtdq2pd xmm0, eax
mulsd xmm0, [0x5FD1170]       ; × 4.65661e-10  == 1.0 / 2147483647
```

`0x38 = 56`、`0x7fffffff = 2147483647 = MBIG`、`4.65661e-10 = 1/MBIG` —— 三处常量把算法钉死。

## 二、算法本体（可直接使用的伪代码）

初始化（`LegacyRandom..ctor(int Seed)`，RVA 0x52FAB60）：

```
MBIG = 2147483647 ; MSEED = 161803398 ; MZ = 0 ; SEED_ARRAY_SIZE = 56

SeedArray[0..55] = 0
subtraction = (Seed == -2147483648) ? MBIG : abs(Seed)
mj = MSEED - subtraction
SeedArray[55] = mj
mk = 1
for i in 1..54:
    ii = (21 * i) % 55
    SeedArray[ii] = mk
    mk = mj - mk
    if (mk < 0) mk += MBIG
    mj = SeedArray[ii]
for k in 1..4:
    for i in 1..55:
        SeedArray[i] -= SeedArray[1 + (i + 30) % 55]
        if (SeedArray[i] < 0) SeedArray[i] += MBIG
inext = 0 ; inextp = 21
```

取样（`_internal_sample`，与上面的 Sample 反汇编对应）：

```
inext++;  if (inext  >= 56) inext  = 1
inextp++; if (inextp >= 56) inextp = 1
retVal = SeedArray[inext] - SeedArray[inextp]
if (retVal == MBIG) retVal--
if (retVal < 0)     retVal += MBIG
SeedArray[inext] = retVal
return retVal

Sample()      = retVal * (1.0 / MBIG)
Next()        = retVal
Next(max)     = (int)(Sample() * max)
NextDouble()  = Sample()
```

> **对模拟的关键提醒**：`Next(max)` 走的是 `(int)(Sample() * max)`，即**先转 double 再截断**，不是取模。任何"用 `%` 复刻随机"的做法都会错。

## 三、种子来源链（谁决定这一局的随机）

```
BattleController.LoadGame(playerDataList, levelData, mapData, difficulty)   [0x354C580]
   └─ call BattleUtil.GenRandomSeed()                                       [0x7BEFA0]  (+0x8B)
         └─ 若缓存字段为空 → SpinWait.GetTime()（系统时间/性能计数器）        [0x4D5DEE0]
   └─ _LoadGameInternal(playerDataList, levelData, mapData, difficulty, int randomSeed)  [0x355BC50]
         ├─ 各 GameMode 的 Init(ref GameModeMeta, ref int randomSeed, …) 可**改写**种子
         │     （GameModeFactory.DefaultGameMode / Act20SideGameMode / … 均有此重写）
         └─ call BattleController.ResetSeed()                                [0x3553700]  (+0x4F5)
               ├─ 通过 m_gameMode（实例偏移 0x190）的虚调用取最终种子
               ├─ call ObscuredInt.op_Implicit(int)                          [0x5402E50]
               │      → 写入 m_randomSeed（ObscuredInt，偏移 0x198，宽 0x14 字节）
               └─ call RandomFactory.Create(seed, DEFAULT)                    [0x5526E70]
                     └─ LegacyRandom(seed)                                   [0x52FAB60]
```

配套事实：

- **`ResetSeed(int newSeed)`**（0x3553550）的调用者只有 4 处（`xref` 实测）：Lua 绑定 `TorappuBattleBattleControllerWrap._m_ResetSeed`、`AutoChessDataCenter.InitData`、`AutoChessGameManager.DoLoadGameInternal`、`GameModeFactory.EnemyDuelGameMode._ResetRandomSeed`。**常规关卡不走这条**，走的是无参 `ResetSeed()`。
- **`GenRandomSeed()` 的唯一调用者**是 `BattleController.LoadGame`（xref 实测 1 处）→ 常规关卡种子就是**时间派生**的、不可预先复现。
- **种子会被写进战斗日志**：`BattleLogger.LogSquadAndRandomSeed(BattlePlayerData, int randomSeed, PlayerSide)`（dump.cs 334018，类 `BattleLogger` = 战斗日志本体）。**这意味着实战的种子是留痕的**，模拟回放某一场时可以从日志取回。
- `s_randomTrivial`（次要/表现层随机）与主随机 **分开两条流**，互不干扰——复刻时不要混用。
- **Lua 层可以直接调用 `ResetSeed`**（存在 Lua 包装类）→ 说明 Lua 有能力干预战斗随机。

## 六、定长 tick 的执行骨架（🟡 骨架已明，逐模块顺序待补）

确定性模拟的第二个要素是"每帧按什么顺序做什么"。已定位三个入口并读出各自骨架：

### 6.1 三个入口（RVA 与职责）

| 入口 | RVA | 职责（据体内调用推断） |
|---|---|---|
| `BattleController.FixedUpdate()` | 0x35487E0 | 常规驱动：判 `isPlaying` / `isPaused` / `DynamicConfig.alwaysMoveNextWhenPause`，对每个 `PlayerSide` 取 `Deck`，再进模块 tick |
| `BattleController.OnTick()` | 0x354F880 | **定点时间推进**：取 `deltaPlayTimeFP` → `FP.FastAdd` 累加播放时间 → `FP.AsFloat()` 供表现层；穿插暂停/对话状态判断 |
| `BattleController.ManualFrameTick(FrameData, bool additionalFrame)` | 0x354CB60 | 手动帧（回放/联机）：`FrameData.DumpToPlayerOpQueue(m_playerOpQueue)` 把该帧输入写入操作队列，再走 `_ApplyGlobalModifier` 等 |

### 6.2 `OnTick` 的关键调用（实证）

```
call BattleController.get_deltaPlayTimeFP()   [0x3562BA0]   ← 每帧定点 delta
call FP.FastAdd                              [0x3D2A010]   ← 定点时间累加（出现两次）
call FP.AsFloat()                            [0x54E1710]   ← 转 float 供 Unity 表现层
call BattleController.get_isPaused()         [0x3564420]
call DialogController.get_isPlaying()        [0x8F2C90]
```

**这就是"1/30 秒步长"在代码里的落地形态**：每逻辑帧把 `s_deltaPlayTimeFP` 用**定点加法**累加进 `s_fixedPlayTime`，再转 float 交给表现层。复刻时这条必须用定点，不能用 float 累加。

### 6.3 `FixedUpdate` / `ManualFrameTick` 的关键调用

- `get_isPlaying()` [0x35644C0]、`get_isPaused()` [0x3564420]
- `DynamicConfig.get_alwaysMoveNextWhenPause()` [0x2B34D80] ← **暂停时是否仍推进逻辑**，属于必须复刻的边界行为
- `Deck GetDeck(PlayerSide side)` [0x3549400] ← 分玩家侧遍历
- `FrameData.DumpToPlayerOpQueue(PlayerOperationQueue)` [0x359A230] ← **帧数据 → 操作队列**，回放/记录通路
- `_ApplyGlobalModifier(ref Modifier, Entity)` [0x3557FD0]、
- `Modifier.NewCharacterLimitDelta(int, Entity, PlayerSide)` [0x5D6790] ← 部署位上限的 modifier 化

### 6.4 还差什么

| 缺口 | 说明 |
|---|---|
| ~~`m_modules`（偏移 0x58）的注册顺序~~ | ❌ **该缺口不成立（2026-09-13 核验，见 `39` 号文档 §五）**：`m_modules` **完全不参与单帧执行**——`IBattleModule` 只有 5 个生命周期方法（`OnGameReset`/`OnGameInit`/`OnGameReady`/`OnGameStart`/`OnGameOver`，Slot 0–4），**没有 `OnTick`、没有 `priority`**；在 `OnTick`/`FixedUpdate`/`ManualFrameTick`/`Update` 内读取该字段的次数 = 0。帧内真正的实体执行顺序由 **`ObjectManager` 的 `PriorityQueue<BObject>`** 决定：`(BObject.priority 降序, instanceUid 升序)`，基类 priority 恒 0 ⇒ **实际即创建序** |

| 帧内"同优先级事件"的排序规则 | `m_eventPool` / `FixedEventHandler` 的排序依据未读 |

## 七、状态哈希算法（✅ 已解出，可复刻）

`HashCodeBuilder`（dump.cs **103520**，TypeDefIndex 1367）：

| 成员 | 说明 |
|---|---|
| `private const float FLOAT_MULTIPLIER = 10000` | 浮点量化倍率 |
| `private uint m_curHash; // 0x10` | 累积哈希 |
| `Clear()` RVA 0x1AF9240 | 重置 |
| `GetCombinedHash()` RVA **0x4EA8B0** | 体内仅 `mov eax,[rcx+0x10]; ret` → **就是返回 `m_curHash`** |
| `Append(int/uint)` RVA **0x1AF8EC0** | 主混合公式 |
| `Append(long/ulong)` 0x1AF8FD0 | 高低 32 位分别并入 |
| `Append(float)` RVA **0x1AF9140** | 量化后并入 |
| `Append(string)` RVA **0x1AF9020** | 逐字符折叠后并入 |
| `Append(char/byte/Vector2/Vector3/…)` | 各自拆成整数分量并入 |

### 7.1 主混合公式（`Append(int)` 逐指令解出）

```
h = m_curHash
m_curHash = ( value + (h << 6) + (h >> 2) + 0x9E3779B9 ) ^ h        // 全程 32 位无符号
```

`0x9E3779B9 = 2654435769` 是黄金比例常量（2³²/φ）。反汇编：

```
mov r9d, [rcx+0x10]      ; h
mov eax, r9d ; mov r8d, r9d
shl eax, 6               ; h << 6
add edx, eax             ; value + (h<<6)
shr r8d, 2               ; h >> 2
add r8d, 0x9e3779b9
add edx, r8d
xor edx, r9d             ; ^ h
mov [rcx+0x10], edx
```

### 7.2 浮点与字符串的并入方式

**`Append(float)`**（0x1AF9140）：
```
mulss xmm6, [0x5D66D64]   ; × 10000.0f  （FLOAT_MULTIPLIER）
cvtss2sd xmm6, xmm6       ; → double
… 取整后 → 走 Append(int) 的同一段公式
```
即 **先单精度乘 10000，再取整**，量化精度 **1e-4**。任何参与哈希的浮点状态（位置、速度、时间）都以此精度参与。

**`Append(string)`**（0x1AF9020）：
```
h = 0
for each char c in s:
    h = (h << 4) + c
    g = h & 0xF0000000
    if (g != 0):
        h ^= (g >> 24)
        h &= ~g                     ; 经典折叠
m_curHash = ( h + (m_curHash << 6) + (m_curHash >> 2) + 0x9E3779B9 ) ^ m_curHash
```

### 7.3 意义与验证状态

- 这三段合起来足以**在 Python 里逐位复刻状态哈希**，从而把"模拟是否正确"从主观比对变成客观判据。
- **但本条无法像随机那样做官方对照**：哈希值只在客户端运行时产生，本地没有可比的现成向量。可用的验证路径有两条：
  1. 解出战斗日志（`battleFinish` 的 `data`，见 `32` 号文档）里的哈希字段，与自算值比对；
  2. 用 `ClientAntiCheatChecker` 的三项抽查（见 `33` 号文档 §7.1）做更细粒度的局部验证。
- ⚠️ **尚未查清**：`Append` 的**调用顺序**（即哈希覆盖了哪些状态、按什么次序）——顺序变了哈希就变。这在 `BattleController` 的 `m_hashCodeBuilder` 使用点里，需后续追。
