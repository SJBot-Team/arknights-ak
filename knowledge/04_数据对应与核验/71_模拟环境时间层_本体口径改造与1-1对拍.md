## §1 一句话结论

**时间层已收口成"唯一换算点"**（`ak_sim/timeline.py`），并用 1-1 标定做了口径反推：
在"逐帧累加（FP）"与"整帧量化（ceil）"两类模型里，**只有整帧量化同时吻合两个单位**
（芬 1.05s→32 帧、猎狗pro 1.4s→42 帧）；结合 `04/69` 的指令级结论
（**不存在秒→帧的换算函数**，而 `m_attackTime`/`m_preDelay` 是**动画播放速率的输入**），
得到解释：**整帧化发生在"动画播放域"，模拟器用 `ceil(BAT×30/(攻速/100))` 等价复现**。
⇒ **`04/36 K-004`「公式层向上取整」被双重否定**（公式层无取整 + 无秒→帧换算），
但其**结果值**在"动画域量化"下依然成立。

| 组成 | 复刻对象 | 要点 |

## §3 ★取整口径的**实证判定**（本任务核心）

### 3.1 方法：用标定表里的**不间断攻击链**当"实机帧差测量仪"
同一目标、连续命中的帧差 = 该单位在实机上的**真实攻击间隔帧数**（来源 `1-1标定.xlsx` → `04/54 §五`）：

| 单位 | 数据表 BAT/攻速 | 标定命中帧 | 帧差 |
|---|---|---|---|
| 芬 `char_123_fang` | 1.05 / 100 | 221, 253, 285, 317, 349 | **32, 32, 32, 32** |
| 猎狗pro `enemy_1000_gopro_2` | 1.4 / 100 | 255, 298, 340 | 43, **42**（稳态取 42） |

### 3.2 各口径预测（`sim\draft\ak_sim\t200_rounding_probe.py`，**19:4x 修正版**）
> ⚠️ **自我勘误**：本脚本首版把 `fp_accumulate` 口径的间隔**先量化成整数帧**再比较，
> 等于把这个口径"退化成 `frame_ceil`"，导致结论偏强。已修正为**用未量化的 FP 间隔**。

| 口径 | 芬(1.05) 实测 [32,32,32,32] | 猎狗pro(1.4) 实测 [43,**42**] | 判定 |
|---|---|---|---|
| `frame_ceil`（`ceil(float32(BAT)×100/攻速×30)`） | **32,32,32,32** ✓ | **42,42** ✓ | ★**两个单位都吻合** |
| `fp_accumulate` **carry=False**（每周期清零） | **32,32,32,32** ✓ | 43,43 ✗ | 单位间不一致 |
| `fp_accumulate` **carry=True**（保留溢出量） | 31,32,31,32 ✗ | **42,42** ✓ | 单位间不一致 |
| `floor` / `round` | 31 ✗ | 42 ✓ | 被否证 |

**关键观察**：`fp_accumulate` 的两个 carry 语义**各只对一半**（芬要 no-carry、猎狗要 carry）
⇒ 单靠"FP 累加比较"无法同时解释两个单位；而 `frame_ceil` 无需 carry 假设即同时吻合。

### 3.3 为什么"FP 累加"会差 1 帧（关键旁证）
`FRAME_TIME_FP = fp.from_float(0.03333330154418945) = 143165440`，于是
**30 帧累加 = 4294963200 = 0.999999046 s < 1 s**（比 1 秒差 256 ULP ≈ 6×10⁻⁸ s）。
⇒ 若按"累加跨阈值"判：`BAT=1.0` 会变成 **31 帧**、`BAT=1.4` 变 **43 帧**（实机 42）。

### 3.4 ★与代码层（`04/69`，T-200a）合起来看：**时间轴的"量化"发生在动画域**
T-200a 的指令级结论（同时提交，见 `04/69`）：
1. 整份 `GameAssembly.dll` 里 **没有**把攻击间隔"秒 → 整数帧"的换算函数
   （三族取整函数的全部调用者已归属，无一处接 `m_attackTime`）⇒ **反证 K-004 的"公式层向上取整"**；
2. `AbstractAnimatedAbility.m_preDelay //0x1A0` 的**唯一写点**是
   `UpdatePlaybackSpeed 0xA6E070` @`0xA6E289`——它被写成 `m_attackTime`（或
   `m_attackTime × m_animScale ÷ _maxAnimScale`）⇒ **这两个量是"动画播放速率"的输入/缓存**，
   **不是**状态机/伤害链上的倒计时。

**两者合起来得到本任务最重要的结论**：
> 攻击的"多少帧一次"**不是**在秒域里取整出来的，而是
> **`m_attackTime` 被当作动画播放速率、动画本身按 30fps 采样/事件帧驱动** ⇒
> 帧数天然是"整帧"的，表现为 `ceil(BAT×30/(攻速/100))`。
> 因此 **`frame_ceil` 不只是经验拟合，它是"动画域量化"在模拟器里的等价实现**（🟡 机制解释，取值 T1-实证）。

⇒ **待补③（FP 秒→帧取整点）的答案**：
- 秒域**没有**取整（`CalculateAttackInterval` 无取整 ✅ `04/68`）；
- 整帧化发生在**动画播放域**（速率缩放后按帧推进）；
- 模拟器侧用 `frame_ceil` 复现该结果，**A/B 开关**保留 `fp_accumulate` 供继续验证。
- ⚠️ **仍缺直接证据**：动画时长/事件帧与 `m_attackTime` 的比例关系（需 prefab/Spine，见 §6 缺口②）。

## §4 前摇（`_preDelay`）：来源链与"真值缺口"

`timeline.windup_fp(unit, interval_fp)` 的优先级：
1. `unit.pre_delay_fp` / `pre_delay_sec` —— **本体真值**（prefab 序列化字段）；
2. `unit._windup_ratio` —— 单点覆盖（标定用）；
3. `WINDUP_RATIO_BY_PROFESSION[职业]` → 默认（干员 0.55 / 敌人 0.25）—— **反推兜底**（🟡）。

**真值为什么拿不到（本任务实测）**：
- `ak\data\gamedata_akgd\character_table.json` 全文只有 **1 处** `"key": "predelay"`（是某个技能/天赋的**黑板键**，不是干员通用字段）；
- `enemy_database.json` / `buff_template_data.json` 里的 `preDelay` 属**技能动作**参数，不是普攻前摇；
- ⇒ 普攻 `_preDelay` **只存在于战斗 prefab 的序列化字段**（`AbstractAnimatedAbility` 上的 `[SerializeField]`），
  本地 `client_res` 只有 `charpack/enm_pfb/scenes/config/anon_tables`，**未备份 battle prefab**。

⇒ **前摇目前只能是"反推值"**（芬的标定反推 ≈ 14 帧：标定 207「进入攻击前摇」→ 221「命中」；
本模拟器用比例 0.55 × 32 ≈ 18 帧，**偏大 4 帧**——见 §6 缺口①）。

### 4.1 ★工具链解锁：客户端 AB **已经能读了**（LZHAM 标记 = 实际 LZ4AK）
本任务实测（`ak\.tmp\t200c_probe_battle_ab.py`、`t200c_dump_attack_mb.py`）：
- 客户端 bundle 的压缩标记是 `CompressionFlags.LZHAM`，但 UnityPy 1.25.3 的 `decompress_lzham` 已"removed by Unity"；
- **实际算法是 LZ4AK**，工作区早有 `ak\code\tools\ak_lz4ak.py`（源自 Ark-Unpacker，BSD-3）；
- 一行注册即可直读：
  ```python
  from UnityPy.enums import CompressionFlags
  from UnityPy.helpers import CompressionHelper as C
  from ak_lz4ak import decompress_lz4ak
  C.DECOMPRESSION_MAP[CompressionFlags.LZHAM] = decompress_lz4ak   # ← 关键
  ```
- 实测：`charpack\char_123_fang.ab`（18,323 B）→ 解压后 44,291 B，**17 个 GameObject**
  （含 `Attack` / `Talents` / `Trigger` / `Default` / `Modes` / `Body` 等）＋ 10 个 MonoBehaviour。
⇒ `04/30` 里标为 🔴 的「**LZHAM bundle 工具链**」**至此解决**（旧说法见 `04/30 §信息获取渠道索引`、`04/15`）。

### 4.2 但仍拿不到 `_preDelay`：两道坎（本任务实测）
| 坎 | 实测证据 | 需要什么 |

| **① 能力 prefab 不在已备份的 bundle 里** | `charpack` 只有角色 prefab（`Attack` 组件的 MonoBehaviour 原始数据 280 B 里只有 `0.02534 / 2.0 / 1.0`，**无 0.4667 这类前摇候选**）；`battle_pack_common.ab` 解出来是 **HUD/UI 预制体**（776 GameObject 全是界面元素）；`enm_pfb_0.ab` 全量 float 扫描 **无 `1.4`/`0.4667`** | 补备份**能力 prefab 所在 bundle**（名字待查：查 `bundle` 清单 / `hot_update_list`） |
