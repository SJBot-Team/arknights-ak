## 〇、一句话结论

> **一场作战完全由客户端本地模拟，服务器只在开始时"放行"、结束时"签收"，中间零参与；关卡的地图、敌人、出怪波次一律不下发，全部来自客户端自己的资源包。**

这条结论对模拟器的意义是决定性的：**模拟器要做的是"客户端"，不是"服务器"**。

## 一、进入关卡前的完整链路

### 1.1 认证前提

- 客户端用 HTTP 头 **`secret`** 携带 token（`util/player_data.py:1105`），无该头时用默认 token `"_"`（`:1100`）。
- token → 用户名：`quote(token, safe="")[:64]`（`util/helper.py:45-46`）。
- 服务监听 `127.0.0.1:8443`（`app.py:112-125`、`conf/config.json:2-3`）。

### 1.2 时序（依赖序；FastAPI 端点并列注册，**代码无强制顺序**，`app.py:72-104`）

| 阶段 | 接口 | 关键内容 |

## 二、`/quest/battleStart`：请求与响应

### 2.1 请求

```python
stage_id = request_json["stageId"]          # bp/bp_quest.py:52  ← 唯一被读取的字段
player_data.extra_save.save_obj["cur_stage_id"] = stage_id   # :53  存进服务器存档
```

**❌ 除 `stageId` 外，代码没有读取请求体里任何其它键**（处理器全文仅 17 行，`bp_quest.py:47-63`，无 `request_json.get(...)` 兜底）。
因此：客户端是否还发了编队/助战/演习标记/种子，**本项目无从得知**，不应臆造字段名。

### 2.2 响应（✅ 逐字段，`bp_quest.py:55-62`）

| 字段 | 值 |
|---|---|
| `result` | `0` |
| `battleId` | `"00000000-0000-0000-0000-000000000000"`（**固定全零 GUID，不代表真的创建了战斗**） |
| `apFailReturn` | `0` |
| `isApProtect` | `0` |
| `inApProtectPeriod` | `false` |
| `notifyPowerScoreNotEnoughIfFailed` | `false` |
| `playerDataDelta` / `pushMessage` | 由装饰器追加 |

### 2.3 **是否下发关卡地图/敌人/波次？→ 明确：没有**

`battleStart` 也不扣理智、不写 `startTimes`（战斗端点零写入，见 §四）。

## 三、战斗中是否通信？→ **没有**

证据：

1. **端点清单里不存在任何"战中"端点**。枚举 `bp/*.py` 全部 240+ 路由后，作战相关写接口只有：`battleStart` 家族、`battleFinish` 家族、`battleContinue`、`saveBattleReplay`。没有"上报击杀/上报波次/心跳/帧同步"这类接口。
2. **服务器对上传的战斗日志只做 debug 打印**（`util/battle_log_logger.py:13-21`），只在 `IS_DEBUG` 下解码并 `logger.debug`，**无任何校验、评分、回放重建或反作弊判定**。
3. **网络配置显式关闭安全通道**：`/config/prod/official/network_config` 下发 `"secure": false`（`bp_config.py:47`）。
4. **反作弊函数存在但零调用**：`validate_is_cheat(is_cheat, battle_id)`（`util/helper.py:279-284`，把 battleId 每字符 `+7` 后 base64）在业务代码中**没有任何调用点**，只有单测引用（`test/test_helper.py:4-8`）。它证明客户端**确实**会产生一个由 battleId 派生的 `isCheat` 类值，但**字段名与所在接口 ❌ 未找到**。
5. 多人玩法走独立服务器（`conf/config.json:13-14` 的 `multiplayer_addr` 127.0.0.1:8543、`icebreaker_addr` :8544），本仓库**没有**这两个服务端的实现。

## 四、`battleFinish`：上传什么、返回什么

### 4.1 上传的 `data`：**hex(AES-128-CBC(PKCS7(JSON)))**

```python
AK_BATTLE_LOG_KEY = "pM6Umv*^hVQuB6t&"                       # helper.py:248（16 字符常量）
t   = player_data["pushFlags"]["status"]                      # :252
key = md5(f"{AK_BATTLE_LOG_KEY}{t}".encode()).digest()        # :253 → 16 字节
blob = bytes.fromhex(raw_data)                                # :255
ciphertext, iv = blob[:-16], blob[-16:]                       # :256-257 → IV 拼在密文尾部
plaintext = unpad(AES.new(key, AES.MODE_CBC, iv).decrypt(ciphertext), 16)   # :259-261
decoded   = json.loads(plaintext)                             # :263
```

| 项 | 值 |
|---|---|
| 传输编码 | 十六进制字符串 |
| 算法 | **AES-128-CBC**（key 是 md5 原始 16 字节） |
| 密钥 | `MD5("pM6Umv*^hVQuB6t&" + str(pushFlags.status))` |
| IV | 密文**尾部 16 字节** |
| 填充 | PKCS#7 |
| 明文 | UTF-8 JSON |

**❌ 明文 JSON 的内部字段结构未找到** —— 服务器解码后只 `json.dumps` 再 `logger.debug`，从不读任何键。

> **这是一个高价值的待解缺口**：这份明文是**游戏自己记录的战斗过程**，若能解出结构，就等于拿到一份"官方权威的对局过程数据"，可作为模拟器的一等回归测试集。解它的路径是现成的（密钥算法已明确），只需要一场真实战斗的 `data` 样本。

### 4.2 响应（✅ `bp_quest.py:73-97`）：**不做任何结算**

16 个字段中 8 个奖励数组**全是字面量空数组**，`expScale`/`goldScale` 是固定常数 `1.2`，`extra.sixStar` 是硬编码示例值（`groupId:"main_15"`）。**不扣理智、不更新通关次数、不解析 battleId**。

🟡 推断：这些字段在真实协议里应是"结构占位 + 倍率"，模拟服务器只求让客户端解析不报错。

### 4.3 `battleContinue`

同样只读 `data`，返回 `{result:1, battleId:全零, apFailReturn:0}`（`bp_quest.py:101-113`）。🟡 触发时机推断为"作战失败后继续/中断续传"，代码未说明。

## 五、`pushFlags.status` 是什么

- 定义：`data/tmpl.json:3013-3019`，值 `1700000000`（一个时间戳样值，全仓库复用的假时间基准，如 `bp_quest.py:174` 的 `allowAskTs`）。同族键 `hasGifts/hasFriendRequest/hasClues/hasFreeLevelGP` 是红点/推送标志。
- **读取**：全仓库仅一处 —— `util/helper.py:252`（战斗日志密钥材料）。
- **写入**：`status` 在本实现中**从未被写入或轮换**（只有 `hasGifts` 在 `bp_account.py:49`、`bp_mail.py:33,46,76,99` 被写）。
- 下发：随 `/account/syncData` 的 `user` 对象整体下发（`bp_account.py:54,68`）。

**为什么用它做密钥盐（🟡 推断）**：它是一个"服务器下发、客户端已持有、且客户端无法在请求里篡改（解密时取自服务器侧 playerData 而非请求体）"的值，因此天然可作共享秘密。目的是**防跨账号/跨会话伪造与重放战斗日志**——即便从客户端二进制里抠出 `pM6Umv*^hVQuB6t&`，仍需知道该账号当前的 `status`。
⚠️ 本实现从不轮换 `status`，故密钥实际退化为全局常量；真实服务器若每次登录刷新，才具备"一次一密"意义。

## 六、战斗回放 `battleReplay`

### 6.1 格式（✅ `util/helper.py:57-69`）

```
base64( ZIP[ "default_entry" → json.dumps(dict) ] )
```

条目名硬编码 `"default_entry"`；包内 JSON 是 ASCII 转义形式（两次 `json.dumps` 都没带 `ensure_ascii=False`）。

### 6.2 上传/下载

| 动作 | 端点 | 请求字段 | 副作用 |
|---|---|---|---|
| 上传 | `POST /quest/saveBattleReplay` | **`battleReplay`**（无 stageId） | stageId 取自 `extra_save["cur_stage_id"]`（即 `battleStart` 时写入的，`bp_quest.py:211`）；若不存在则**空返回不保存**（`:208-209`）；成功后 `dungeon.stages[stageId].hasBattleReplay = 1`（`:217`） |
| 下载 | `POST /quest/getBattleReplay` | **`stageId`** | 返回 `{"battleReplay": …}`（`bp_quest.py:222-232`） |
| 登录时回填 | `/account/syncData` | — | 枚举回放目录，批量置 `hasBattleReplay=1`（`bp_account.py:44-46`） |

落盘路径：`sav/replay/{urlencode(stageId)}.json`（`util/battle_replay_manager.py:37-38`）。

> `battleFinish` **不会**保存回放（其处理器内无 `battle_replay_manager` 调用）—— 回放由客户端**单独**再发一次请求。

## 七、各模式在 battleStart 上的差异

| 模式 | 读取的请求字段 | 响应相对常规的差异 |
|---|---|---|
| **常规 `/quest/battleStart`** | `stageId` | — |
| **危机合约 `/crisisV2/battleStart`** | **`mapId` + `runeSlots`**（⚠️ 不是 `runeLst`） | 只 `{result, battleId}`；**`runeSlots`（节点槽位）→ `runeIds`（符文）的换算由服务器在 battleFinish 做**（查 `mapDetailDataMap[mapId].nodeDataMap[nodeId].runeId`，`bp_crisisV2.py:94-104`），再算 `basic_score_vec` / `bonus_score_vec` / `score_vec` |
| **重置符文 `/recalRune/battleStart`** | `seasonId` + `stageId` + `runes` | 分数在 finish 时按 `recalRuneData.seasons[s].stages[st].runes[r].score` 累加（`bp_recalRune.py:30-40`） |
| **沙盒 V2 `/sandboxPerm/sandboxV2/battleStart`** | `topicId` + `nodeId` + `squadIdx` | ★ **唯一会下发"战斗增益列表"的地方**：多出 `isEnemyRush` / `shinyAnimals` / `shinyUniEnemy` / `lureInsect` / **`extraRunes`**（由 `calc_extra_rune()` 按挑战日与编队携带道具生成，`:40-84`） |
| 沙盒 V2 月战 / 竞速 | `topicId` / `nodeId`+`instId` | 竞速会由**服务器随机决定对手**并下发 `myRacer` + `racers[]`（`:379-430`）——另一个下发实体数据的例外 |
| 沙盒 V3 | `topicId`（nodeId 取自 playerData） | `{battleId, battleShopId}` |
| **肉鸽 `/rlv2/*`** | **不存在 `/rlv2/battleStart`**；用 `/rlv2/moveAndBattleStart`（请求 `to`） | 直接响应只有 `{battleId}`；战斗参数（`type:"BATTLE"`、`chestCnt`、`diceRoll`、`unkeepBuff`、`seed:0`…）出现在 **playerData delta 的 `pending` 事件**里，不在直接响应里 |

❌ `sandboxV5` / `SANDBOX_V5` 在本版本（client 2.7.71）**不存在**，只有 V2/V3。
❌ 多人/联机的实际服务端实现（8543/8544）在本仓库不存在，只有地址下发。

## 八、对模拟的直接启示

| # | 启示 |
|---|---|
| 1 | **模拟器要做"客户端"**：所有局内逻辑自己算，服务器不参与。 |
| 2 | **关卡数据只能从本地资源取**：`stage_table`（关卡索引）→ `level_<id>.json`（LevelData）→ 客户端场景 AB（tile）→ `enemy_database`（敌人基值）。这条链与 `26`/`27`/`31` 号文档完全吻合。 |
| 3 | **战斗日志（`data`）是待挖的宝藏**：算法与密钥已完全明确，只差一场真实战斗的样本就能解出明文结构，从而拿到"官方记录的对局过程"。 |
| 4 | **回放格式已知**：`base64(zip(json))`，且游戏会把回放存在本地 `sav/replay/`（模拟服务器）或客户端自己的存档里 —— 若能取到，就是**操作序列**，可直接作为模拟器的输入与回归用例。 |
| 5 | **"客户端权威 + 事后校验"** 与 `29` 号文档发现的确定性架构（快照/操作队列/状态哈希）互为印证：模拟器只要复刻确定性的四要素（Q32.32、1/30 步长、随机算法与种子、tick 顺序），结果就应与游戏逐位一致。 |
