# 第一部分　三点已确认前提（2026-09-15 用户确认，具有约束力）

## 前提 1：**单位数值必须"全量提取并辨明关联机制"**
- **事实**：**芬的部署费用为 8** —— 因为它的**天赋带"部署费用 −1"**（`character_table.json` 的满潜裸值为 9）。
- **教训**：这是"**单位关联的机制**"，此前未纳入是本方遗漏。
- **约束**：**以后凡涉及单位数值，必须在跑模拟前"全量提取并辨明"该单位的关联机制**
  （**天赋 / 潜能 / 模组 / 技能 / 精英化阶段**等），**不得跳过**。
- **落地**：见第三部分机制 4（反重复）与机制 5（信息链条）—— 单位数值的取值必须走"关联机制全量清单"。

## 前提 2：**帧记数基准**
- **以"进入游戏时的第一帧"为第 0 帧**。
- 即：`帧号 = 0, 1, 2, …`；**1 秒 = 30 帧**；"第 n 秒的第 k 帧" = `帧号 30n + k`（k ∈ [0, 29]）。

## 前提 3：**前 10 秒费用条识别困难的根因（★重要）**
- **游戏底层未知原因**导致 **"费用条满的第 29 帧"与"下一费的第 0 帧"混在一起、难以区分**；
- 因此**标定时改用"游戏运行一段时间后"的费用条**进行标定；
- ⇒ **这是此前费用条识别环节部分困难的根因**。

**⟹ 对本方模拟器的直接推论**：既然"第 29 帧 / 第 0 帧"在实机侧混同，
**费用 +1 的相位定义必须以标定表为准**：标定表"该秒初始费用"对应 **帧 30n 处已经 +1**
⇒ 模拟器应在 `f % 30 == 29` 时增长（即"帧 30n"的切片含本次 +1）。
本方已按此修正 `engine.py::tick()`，修正后费用增长落在**帧 30 / 60 / 90（每秒第 0 帧）**。

# 第二部分　五项工作机制

## 机制 1　**分层汇报总结机制**

**分层结构**（自上而下四层）：

| 层 | 名称 | 内容 | 更新时机 |
|---|---|---|---|
| **L0** | **总目标** | 用户任务的最终目标（模拟环境 + 纯 AI 打图 + 二者互验） | 目标变更时 |
| **L1** | **阶段** | 当前主线阶段（如 P0 工作流重建 / P1 模拟标准化 / P2 事件帧验证） | 阶段开始/结束时 |
| **L2** | **子任务** | 阶段内的具体课题（如"部署动作打通""费用相位对齐"） | 子任务开始/阻塞/完成时 |
| **L3** | **单次验证** | 一次实验：假设 → 操作 → 观测 → 结论 | **每次验证后立即** |

**每层应记录的内容**
- **L0**：目标原文、合规边界、验收口径；
- **L1**：阶段名、进入/退出条件、当前状态（进行中/已完成/阻塞）；
- **L2**：课题名、**假设**、依赖、**当前卡点**、下一步动作；
- **L3**：**时间戳、假设、命令/脚本、原始观测（数值/截图）、结论（成立/否证/待定）、证据文件路径**。

**落地形式**
- **L0/L1** → `management/tasks_registry.md`（台账）顶部"当前阶段"区 + `55_工作前提与五项机制.md`；
- **L2** → 台账"冲突记录"条目 + 对应专题文档（如 `53_PRTS+部署实现_源码剖析.md`）；
- **L3** → **每轮对话末尾的汇报段落** + `.tmp/` 下的原始数据文件 + 专题文档的对应小节。

## 机制 2　**整理查找机制**

**目标**：按主题 / 任务线快速检索既有结论，**避免重复劳动**。

**落地形式**
1. **结论索引表**（`ak/knowledge/04_数据对应与核验/01_结论索引.md`）：一行一条结论，
   字段 = `结论 | 主题线 | 关键参数 | 验证方式 | 证据文件 | 日期`；
2. **目录约定**（`knowledge/04/` 下按序号分文件，文件名自带主题词）；
3. **检索手段**：用 `grep`/`glob` 在 `knowledge/` 与 `sim/`、`code/` 内按关键词搜索；
   常用关键词见索引表末列"检索词"。

## 机制 3　**注意力纠偏机制**

**目标**：当某个小问题耗费过长时间时，主动提示并拉回大目标。

**触发判据（任一满足即触发自检）**
- 同一子问题**连续 ≥ 3 轮**未收敛；
- 单轮内对同一子问题的**实验次数 ≥ 5**；
- 该子问题的投入**与"当次复刻/打图主目标"无直接关系**（如纯界面坐标试探）。

**运作方式**
1. **暂停当前方向**，回答三问：
   - 这个问题**是否阻断**当前主目标？（阻断 → 继续；不阻断 → 降级为待办）
   - 是否有**已知的现成实现**可借鉴（MAA / PRTS+ / AFA / 云迹方案）？
   - 是否有**更省事的替代路径**（如"绿格检测"替代"3D 投影"）？
2. 依结论二选一：**继续（但限定轮数）** 或 **记入待办并转回主目标**；
3. **在汇报中显式说明本次纠偏**（写进 L3 记录）。

## 机制 5　**信息框架优化：信息查找链条**

**做法**：建立工作流，在特定工作中**只提取需要的信息**（当前聚焦的关卡与用到的干员）。

| 11 | **费用 +1 相位** | 引擎 `f % 30 == 29` | [1] 关卡层 | 视频侧实测 +1 在 **游戏帧 29.7±0.5**（同相） |

| 16 | **★②B 敌方远程范围** | `enemy_database.rangeRadius` + 干员 **0.25** 圆 | [3] 单位层 | 远程敌人 = **半径圆**（如 mocock **1.75**）；判据 = `dist ≤ rangeRadius ± 0.25` |
