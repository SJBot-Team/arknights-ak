## §1 一句话结论

**「每个事件的存在时间」在代码层不是一张时长表，而是三层拼出来的：**

1. **整段长度**（"一次攻击流程"多长）= **单个 `FP` 字段 `AbstractAnimatedAbility.m_attackTime // 0x1A8`**，由 `Entity.OnAttributeDirty 0x35FD87E → BattleFormula.CalculateAttackInterval 0x3584F10` 算出、经 `ApplyAttackTime 0xA6CD40` 写入。**这一层是纯攻速决定的，且本轮指令级确认全函数无任何取整/下限夹取**（取整在更下层帧换算，见 §3-⑥）。
2. **段内切分点**（前摇何时结束、何时出伤）= **动画"事件帧"驱动，不是时间字段驱动**。代码对应物是 `AbilityStandard.Event` 枚举（TypeDefIndex **8426**，`ON_ATTACK_CHECK_POINT = 7`）经 **`AbilityStandard.OnEvent 0x34F26A0`** 分发。PRTS 的「事件帧 / OnAttack 事件」与它有**硬对应**。⇒ **`m_preDelay // 0x1A0` 不是"倒计时到点就出伤"的闹钟，它是"等事件帧"的等待窗口**（`_preDelay // 0x180` 的 `[Inspect("waitForAttackEvent", False)]` 标注即此意）。
3. **每帧推进** = **`FP` 定点（Q32.32）累加**，节拍来自 Unity `FixedUpdate` 帧计数 `BattleController.s_fixedFrameCnt // 0x14`（**`uint`**，`get_fixedFrameCnt 0x3563340`）。**不是 `WaitForSeconds`**。

⇒ **"存在时间"在代码里的最短链**：
```
FP 定点量（m_preDelay 0x1A0 / m_attackTime 0x1A8）
  ← 每帧由 FixedUpdate 帧计数推进（BattleController.s_fixedFrameCnt // 0x14, uint）
  ← 终止条件不是"时间到"而是"动画事件帧到达"
       AbilityStandard.OnEvent(ON_ATTACK_CHECK_POINT=7)  0x34F26A0
         └─ ActionUtil.RunActions 0xC837C0 → Nodes.ApplyDamage.Execute 0xBB5A70   ★出伤时刻★
```
**没有 `WaitForSeconds`，没有 `ActionNode` 自带持续时长**——`ActionNode` 只在被事件帧唤醒的那一帧执行一次。

### 2.1 ① 攻击间隔的确切算法（本轮指令级实证）

`BattleFormula.CalculateAttackInterval(FP baseAttackTime, FP attackSpeed)` **RVA `0x3584F10`**，全部指令已读（`0x3584F10`–`0x358504F`，函数体仅 ~80 字节）：

```
0x3584F2E..0x3584F4D  三次 il2cpp_class_init（BattleFormula / FP / TSMath 的 Il2CppClass*）
0x3584F59   mov  rbp,[rip+…]            ; rbp = BattleFormula 的 Il2CppClass*
0x3584F78   mov  rax,[rbp+0xb8]         ; rax = static_fields
0x3584F7F   mov  rcx,[rax+0x68]         ; 静态字段 +0x68
0x3584F86   jne  0x3585037              ; ★非空 ⇒ jmp DelegateBridge.__Gen_Delegate_Imp10074
0x3584FA8   mov  rbp,[rbp+0xb8]         ; rbp = static_fields
0x3584FB6   mov  rsi,[rbp+0x10]         ; arg2 = static[0x10]
0x3584FC1   mov  rbp,[rbp+0x8]          ; arg3 = static[0x8]
0x3584FCC..0x3584FD8   rcx=attackSpeed(rbx), rdx=rsi, r8=rbp
0x3584FD8   call 0x5502C30              ; ★TSMath.Clamp(attackSpeed, static[0x10], static[0x8])
0x3584FF5   mov  rsi,[rax+0xb8]  → [rsi+0x18]   ; rdx = static[0x18]
0x3585010   call 0x54E4080              ; FP.op_Division(clamped, static[0x18])
0x3585032   jmp  0x54E4080              ; FP.op_Division(baseAttackTime, 上一步结果)   ← 尾调用
```

**结论（🟢T1）**：

$$ T_{\text{攻击间隔}} \;=\; \texttt{baseAttackTime} \;\big/\; \Big(\mathrm{clamp}\big(\texttt{attackSpeed},\ \texttt{static[0x10]},\ \texttt{static[0x8]}\big) \Big/ \texttt{static[0x18]}\Big) $$

- `static[0x8] = MAX_ATTACK_SPEED = 600`（作为 `Clamp` 的 **max** 实参 `r8`）
- `static[0x10] = MIN_ATTACK_SPEED = 10`（作为 `Clamp` 的 **min** 实参 `rdx`）
- `static[0x18] = ATTACK_SPEED_DIVIDER = 100`
- **两个 `FP.op_Division`，零个取整/零个 `TSMath.Floor`/`Ceil`/`Round`**。⇒ **K-004 的"向上取整"在本层确实不存在**（`67a §8-3` 判断成立）；间距取整必然在**帧换算层**（PRTS 的"帧对齐"，见 §3-⑥）。
- ⚠️ **新发现（🟡，`67a` 未记）**：`BattleFormula` 有一个**静态字段 `+0x68`**，**非空则整个函数改走 xLua 热更委托 `DelegateBridge.__Gen_Delegate_Imp10074(FP,FP)`（RVA `0x2B4FDC0`）**——即攻击间隔公式**存在 Lua 覆盖通道**。字段名未取（下一步见 §4-1）。

### 2.4 ④ 每帧怎么推进这些计时

- **`FP` 是 Q32.32 定点**：`public struct FP`（TypeDefIndex **32190**）`FRACTIONAL_PLACES = 32`、`ONE = 4294967296`、`_serializedValue // 0x0` 为 `long`。⇒ **与 `04/34` 的定点结论一致** ✅。计时量 `m_preDelay // 0x1A0`、`m_attackTime // 0x1A8` 都是 `FP`。
- **节拍来源**：`BattleController.s_fixedFrameCnt // 0x14`（**`uint`** 静态计数器），取值 `BattleController.get_fixedFrameCnt 0x3563340`（`LoadFromBlackboard` 路径上也读它，`67a §2.1`）。
- **`AttackState.OnTick 0x71AAD0` 本轮读到的调用清单（🟢T1）——它不自己累加时间，只做每帧轮询**：

| 调用点 RVA | 目标（类.方法） | 含义 |
|---|---|---|
| `0x71AB38` | `Character.States.Blackboard.ShouldSwitchToAbnormalState` **`0x71B7C0`** | 是否该切到异常态 |
| `0x71AB62` | `Unit.get_hasAttack` **`0x771B10`** | ①能否攻击 |
| `0x71AB8C` | `Entity.get_canUseAtkOrCbt` **`0x3607D40`** | ①能否攻击/战斗 |
| `0x71ABB6` | `Entity.get_isDialogTarget` **`0x360A8F0`** | 对话中不攻击 |
| `0x71AC2E` | `Character.get_hasReplacement` **`0x706690`** | 替换体判定 |
| `0x71AC77` | `call r8`（**虚分派**） | 🟡 槽名未定 |
| `0x71AB/…` | `Ability.get_isCasting` **`0x34F8300`** | 是否正在施放 ⇒ **攻击态靠"能力是否还在 cast"判断"还在攻击中"** |
| — | `Character.States.Blackboard._NextAttackOrExit` **`0x71B210`** | 起手/退出 |

⇒ **"存在时间"是"忙/闲标志 + 定点量"的组合，不是延时器**：状态机每帧问"这次攻击完了没"（`Ability.get_isCasting 0x34F8300`），计时量的推进在别处（🔴 §4-2）。

### §3-A ❌ 「动画不可压缩 / 后摇以动画结束为界」vs 代码把播放速度一起改

- **PRTS 侧（保留）**：L867「前后摇 = 动画播放开始→事件帧→**动画播放结束**」；L851「抬手动画和攻击动画时长是**无法被压缩**的，所以攻速提高的效果就表现在了攻击后的读秒阶段上」。
- **代码侧（本轮实证）**：`AbstractAnimatedAbility.GetDuration 0xA6D720` 的返回值是 **`m_attackTime // 0x1A8`**（`0xA6D75F mov rax,[rbx+0x1A8]`）——**与动画长度无直接关系**；同时 `ApplyAttackTime 0xA6CD40` 在写入 `m_attackTime` 后 **立即 `call AbilityStandard.DoUpdatePlaybackSpeed 0x34F0810`**（`0xA6CDE2`）⇒ **代码会按新的间隔去改动画的播放速度**。
- **判定**：**以代码为准**。"动画不可压缩"是**观感/表现层**口径（Spine 关键帧与事件帧位置固定），代码层的"时长"是单一 `FP m_attackTime`，并把 playback speed 当**派生量**一起改。两者**不是同一层**，但 PRTS 把它写成"后摇的终点是动画结束"会导出一个**可证伪的错误预测**（见 §4-4 验证方案）。
- **保留理由**：PRTS 的"动画不可压缩"在**表现层确实成立**（事件帧在动画时间轴上的位置固定），因此不能简单判 PRTS 错；正确表述是：**"存在时间"的权威来源是 `m_attackTime`，动画只是它的表现**。

### 本轮工具局限（复用须知）

1. **`read_cpp.py dis` 只接受**十六进制 RVA**，不接受 `类.方法`**（`dis BattleFormula.CalculateAttackInterval` 直接 `ValueError`）。要按方法名反汇编请用 `m`。
2. `call <类.方法>` 目前**只接受精确的 `类.方法`**：`call Character.States.AttackState.OnTick` 报"未定位到"（应为 `call Character.States.Blackboard._NextAttackOrExit` 这类**声明类**名——本例 `OnTick` 实际声明在 `Character.States.Blackboard`）。**建议用 `who <RVA>` 先反查真实声明类**。
3. `who` 对**未索引区**返 `??`/最近前驱（本轮 `0x3DD07D0`、`0x489770` 均未命中）——**不可当结论用**。
4. 抓 PRTS 用 `urllib.request` 兜底成功（`curl_cffi` 在 Anaconda 里**未安装**⇒ 报 `ModuleNotFoundError`，不是证书问题）。**`User-Agent` + `Accept` 齐备即 200**；控制台中文文件名显示为乱码但**落盘路径正确**。
