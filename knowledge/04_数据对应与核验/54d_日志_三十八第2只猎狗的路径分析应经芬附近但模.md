## 三十八、第 2 只猎狗的路径分析：应经芬附近，但模拟器中被月见夜独杀

## 三十九、★★★根因定位：阻挡"停靠位置"偏差导致芬打不到第 2 只

### 39.1 玩家属性核对（先排除了"伤害数值"假设）
| 项 | 值 |
|---|---|
| 月见夜 `profession` / `subProfessionId` | **WARRIOR / lord**（远程近卫） |
| **`atk`** | **569.0** |
| `range_id` / `range_grids` | 3-12 / 8 格 |
| `attack_interval_frames` | **39** |
| `block_cnt` | 2 |

⇒ 模拟器对第 2 只造成的 **569** 伤害**正是满额 atk** ⇒ **伤害计算无误**；
⇒ 因此差异**不在数值**，而在**"谁在何时打得到它"**。

### 39.2 ★单位位置与阻挡关系（帧 440，`pos` 为**定点数 Q32.32**，顺序是 `(col, row)`）

| uid | 单位 | pos（换算后） | state | blocking / blocked_by |
|---|---|---|---|---|
| 1 | **芬** | (col 5.5, row 3.5) = **格(3,5) 中心** | MOVE | **blocking=[3]** |
| 3 | **猎狗（第 2 只）** | (col 4.80, row **4.48**) | **BLOCKED** | **blocked_by=[1]** |
| 4 | 月见夜 | (3.5, 3.5) = 格(3,3) | MOVE | — |

**⇒ 芬确实阻挡了第 2 只**（`blocking=[3]`）；**但敌人停在 (row 4.48, col 4.80)**，
与芬（row 3.5, col 5.5）的**距离 = √(0.7² + 0.98²) ≈ 1.20 格**。

### 39.3 为什么这会导致"芬打不到"
芬的 `range_id = 1-1`、`range_grids = [[0,0],[1,0]]`、朝向"左"
⇒ **攻击范围只有"自身格 + 左邻格"共 1 格**。
而敌人停在 **1.20 格**处 ⇒ **超出范围** ⇒ `pick_operator_target` 返回 None
⇒ **芬完全不攻击它**（这也解释了为何"芬对第 2 只 0 次命中"）。

### 39.4 ★根因与修正方向
**根因：阻挡的"停靠位置"偏松** ——
敌人应在**接触阻挡者时停在相邻格中心附近**（距离 ≈1.0），
而当前实现让它停在 **1.20 格**处 ⇒ **恰好游走出近战范围**。

**修正方向**：
1. 检查阻挡判定与停止条件（`_block_scan`、`BLOCK_SCAN_INTERVAL`、`inertia`）；
   阻挡发生时，应把敌人位置**吸附/推进到"与阻挡者相邻的格中心"**（或至少在 1.0 格内）；
2. 检查**移动步长**：若每帧步长过大，会在"跨过接触点"后才被检测到 ⇒ 停靠位置偏后
   （`move_speed=1.0` 格/秒 ⇒ 每帧 1/30 格 ⇒ 不该产生 0.2 格误差，需核对实际推进逻辑）；
3. 修正后复测：预期"芬对第 2 只产生命中"，且标定「帧 432 芬命中 / 443 芬阻挡 / 464 芬击杀」
   都能在模拟器中找到对应 ⇒ **残余偏差应进一步收敛**。

### 39.5 与既有结论的关系
- 本轮**先排除了"伤害数值"**（月见夜 atk=569 与实测伤害一致），
  再**排除了"芬的索敌规则"**（索敌正常，只是范围内无目标），
  最终定位到**"阻挡停靠位置"** —— 这是一个此前完全没被注意到的机制细节。
- 该发现也说明：**"以事件精确帧判定"能逐层排除假设**（数值 → 索敌 → 位置/碰撞），
  这正是目标③所要求的方法论。

## 四十、★★★阻挡判定改为「4 邻接」：平均偏差 3.93 → 2.93 帧

### 40.1 根因（上一轮定位）
```python
BLOCK_RADIUS = 0.7071
if d <= BLOCK_RADIUS + 0.5:      # ⇒ 阈值 1.2071（欧氏距离）
def dist_to(...):  math.hypot(...)   # ★精确欧氏距离
```
敌人格 (4,4)、芬格 (3,5) 是**对角格**（格距 √2≈1.414），
但**精确欧氏距离 1.20 < 1.2071** ⇒ **被误判为阻挡** ⇒ 敌人停在"距芬 1.2 格"处
⇒ **游走出近战 1 格范围** ⇒ `pick_operator_target` 返回 None ⇒ **芬不攻击它**。

### 40.2 修正
阻挡判定改为「**格坐标 4 邻接**」：
```python
orr, occ = o.grid()
if abs(orr - r) + abs(occ - c) > 1:
    continue            # ★对角格不算相邻 ⇒ 不阻挡
d = e.dist_to(o)        # 仅在 4 邻接内比较距离，取最近者
```
⇒ 敌人会继续移动到"与阻挡者**正交相邻**"（距离 ≈1.0）才被阻挡。

## 四十一、阻挡判定两版对比；真正卡点：芬为何不攻击"被阻挡的敌人"

### 41.1 两版对比（同一标定）

| 版本 | `dmg 猎狗←月见夜` | `kill 猎狗` | `dmg 猎狗←芬` | 平均偏差 | 最大 |
|---|---|---|---|---|---|
| **格坐标 4 邻接** | **`[438]`（1 次，与实机一致）** | 465 | 无 | **2.93** | 7 |
| **欧氏距离 ≤ 1.0** | `[438, 478]`（2 次） | 479 | 无 | 3.93 | 15 |

### 41.2 两版各自暴露的问题

**（A）4 邻接版**：逐帧追踪显示敌人**一路走进芬所在的格子**
（`pos` 从 (4.91,4.32) → (5.00,4.07) → **(5.00,4.00) = 格(3,5) 中心**，与芬重叠、欧氏仅 0.70）
⇒ 虽然"被阻挡"（`blocked_by=[1]`）且"月见夜只打 1 次"（与实机一致），
但**停靠位置物理上不合理**，且它在 **465 消失（漏怪）** 而非被击杀。

**（B）欧氏 ≤1.0 版**：敌人应在接近到 1 格时停下（帧 435 欧氏 1.01 → 下一帧跨过 1.0）
⇒ 它**确实停住**（月见夜得以在 478 再打一次），但**芬依旧不攻击它**。

### 41.3 ★结论：真正卡点是「芬为何不攻击被阻挡的敌人」
两版**都没有让芬打出任何一次命中**（`dmg 猎狗←芬` 键始终为空），
而标定明确显示实机中**芬打了它**（帧 432 命中 / 443 阻挡 / 461 被击 / 464 击杀）。

⇒ 说明问题**不在阻挡半径的取值**，而在**"芬的索敌为何看不到这个被阻挡的敌人"**：
可能原因（下一轮逐一核查）：
1. **`pick_operator_target` 的范围判定**用的是 `range_grids`（相对格）**且依赖朝向**——
   若朝向/相对格换算与"敌人的实际位置（可能在格内偏移）"不匹配，
   就会出现"**视觉上相邻、但格判定不算在范围内**"；
2. **索敌要求"敌人在范围内"用的是格坐标**（`int()` 截断）——
   敌人在格内偏移时可能被算到**相邻格**，从而落在 `range_grids` 之外；
3. 近战索敌还应包含"**被自己阻挡的敌人**"这一强制项（AK 中被阻挡者必为攻击目标）；
4. 也可能是**阻挡关系建立后、索敌在其之前执行**（同帧顺序问题）。

### 41.4 下一步（明确）
1. **核查 `pick_operator_target` 的范围判定**：
   - 打印"芬在各帧的候选敌人、其格坐标、`range_grids` 展开后的绝对格集合"，
     直接看"被阻挡的第 2 只为何不在集合里"；
2. **加入"被自己阻挡的敌人必为攻击目标"**（若 AK 语义如此，这既能修好本例，也更符合游戏直觉）；
3. 确认后选定阻挡半径（倾向"欧氏 ≈1.0~1.2"这一物理合理区间，避免"走进同格"）；
4. 复测：预期 `dmg 猎狗←芬` 出现、`kill 猎狗` 变为"被芬击杀"、
   标定「帧432/443/461/464」全部可对齐 ⇒ **目标 平均 ≤2 帧、最大 ≤5 帧**。

## 四十二、★★★真因：route4 寻路偏离直线（索敌与范围数据均无问题）

### 42.1 攻击范围表（数据本身正确）
```
1-1  = {direction:1, grids:[{row:0,col:0},{row:0,col:1}]}                      ← 2 格
1-2  = {direction:1, grids:[{row:1,col:0},{row:0,col:0},{row:0,col:1},{row:-1,col:0}]}
3-12 = {direction:1, grids:[8 格]}                                            ← 远程
```
⇒ **`1-1` 就是"自身格 + 朝向 1 格"（标准近战）**，本方的 `range_grids=[[0,0],[1,0]]` **无误**。

### 42.2 索敌实现（也正确）
```python
def enemies_in_range(self, u):
    cells = self.cells_in_range(u)     # range_grids 按朝向展开
    return [e for e in ... if e.grid() in cells]     # 用格坐标判定
def pick_operator_target(self, u):
    ...  # 优先级：被自己阻挡 > 剩余距离小 > 创建早
```
⇒ "按格判定"是 AK 的常规做法；**"芬（朝左）打不到正下方 (4,5) 的敌人"完全符合数据**。

### 42.3 ★真因：敌人在"错误的位置"被阻挡
- **route4 是 `(row6, col4) → (row0, col5)` 的直线**；
- 参数化：`row: 6→0`、`col: 4→5` ⇒ **当 row=3 时 t=(6−3)/6=0.5 ⇒ col = 4.5**
  ⇒ **敌人应在格 (3,4)** —— **正是芬（朝左）攻击范围内的格**；
- **但实测它停在 `pos=(5.00, 4.00)` 即格 (4,5)**（芬的**正下方**，不在朝左范围内）
  ⇒ **寻路结果偏离了 route4 的直线**。

### 42.4 为何会偏离（待核）
很可能与**寻路实现**有关：
1. 关卡 `routes` 中含 `visitEveryTileCenter: false`、`visitEveryNodeCenter: false`、`allowDiagonalMove: true`
   —— 语义上应"沿直线走、不强制过格中心"；
   若本方把它实现成"**格中心节点序列**"，路径就会变成阶梯状 ⇒ 位置系统性偏移；
2. `navmap`/`next_node` 的生成方式（是否把"格中心"当作必经点）；
3. `move_speed=1.0` 格/秒 ⇒ 每帧 1/30 格；若沿阶梯走，横向/纵向分量会被分解 ⇒ **到达次序改变**。

### 42.5 下一步
1. **打印 route4 实际经过的格序列**（模拟器中逐帧 `grid()` 去重），与"直线应为 (6,4)→(5,4.x)→…→(3,4.x)→…→(0,5)"对照；
2. 检查 `navmap`/`next_node`/`_enemy_move` 是否强制"过格中心"；
3. 修正为**直线寻路**（不强制过格中心）后复测：

## 四十三、★★★根因确认：寻路走「L 形」而 routes 要求「直线」

### 43.1 逐格实测（第 2 只，uid=3，route4）

| 帧 | 格 | pos (col,row) | 状态 |
|---|---|---|---|
| 360 | (6,4) | (4.50, 6.49) | MOVE |
| 377 | (5,4) | (4.50, 6.00) | MOVE |
| 409 | (4,4) | (4.50, 4.99) | MOVE |
| 415 | (4,4) | (**4.55**, 4.84) | MOVE ← **开始横移** |
| 430 | (4,4) | (**4.82**, 4.45) | MOVE |
| 445 | (4,4) | (**5.00**, 4.07) | MOVE ← **横移到 col=5.0** |
| 450 | **(3,5)** | (5.00, 4.00) | **BLOCKED** |

### 43.2 判读
- 前段（帧 360~409）：**col 恒为 4.50**（正是"格 4 的中心"）⇒ **沿格中心竖直向上**；
- 后段（帧 415~445）：**col 由 4.50 横移到 5.00**（row 只从 4.84 到 4.07）
  ⇒ **横向分量远大于纵向** ⇒ **典型的「L 形路径（先列后行）」**；
- 最终在 **(3,5)** 被阻挡 —— 而 **(3,5) 是芬所在格**（重叠）。

### 43.3 route4 的正确语义
关卡 `routes[4]`：`startPosition={row:6,col:4}` → `endPosition={row:0,col:5}`，且：
- **`allowDiagonalMove: true`**（允许斜向）
- **`visitEveryTileCenter: false`**、**`visitEveryNodeCenter: false`**（**不强制过格中心**）

⇒ 语义是"**从起点直线走向终点**"：
`row 6→0`、`col 4→5` ⇒ **row=3 时 col=4.5** ⇒ **经过格 (3,4)**
—— **正是芬（朝左）攻击范围内的格** ⇒ **按正确寻路，芬本应能打到它**。

### 43.4 结论
**根因：本方寻路实现成了「L 形（先对齐列、再走行）」，未按 routes 的"直线/斜向"语义**，
导致：
1. 敌人**沿格中心竖直行进**（col 固定在 4.5），直到接近终点才横移；
2. 因而**不会经过 (3,4)**，而是在 **(3,5) 与芬重叠**处才被阻挡；
3. **芬（朝左）的攻击范围 `{(3,5),(3,4)}` 里没有它** ⇒ 芬不攻击它
   ⇒ 标定「帧432 芬命中 / 443 芬阻挡 / 461 猎狗命中芬 / 464 芬击杀」全部缺失。

### 43.5 修正方向（下一轮）
1. **重写敌人在 route 上的推进**为"**朝"当前目标点"直线插值**"：
   - 目标点：`endPosition`（或检查点序列的下一个），**不强制经过格中心**；
   - 每帧按 `move_speed × FRAME_TIME` 沿"到目标点"的单位向量推进；
   - 抵达目标点（或检查点）后切换下一目标；
2. **保留** `visitEveryTileCenter` / `visitEveryNodeCenter` 为可配置项（默认 false），
   以兼容确有"必须过格中心"的关卡；
3. **修正后复测**：预期敌人经过 **(3,4)** ⇒ 被芬阻挡在 **(3,4) 附近** ⇒
   `dmg 猎狗←芬` 出现、`kill 猎狗` 变为被芬击杀、标定「帧432/443/461/464」全部可对齐；
4. 目标 **平均 ≤2 帧、最大 ≤5 帧**。
