## 〇、结论速览

| 问题 | 结论 |
|---|---|
| 多敌同帧被同一干员阻挡的顺序 | ✅ **已辨明**：按 **`(floor(距离² / 0.001), instanceUid)` 升序**，即"最近优先；距离² 落入同一 0.001 桶时 **instanceUid 小者（先创建）优先**" |
| 候选集来自物理 broadphase 的顺序是否影响结果 | ✅ **不影响**（最终是全序排序） |
| 阻挡位不足时先释放谁 | ✅ 取 `m_blockedEnemies[Count-1]` ⇒ **最后被挡住的先被释放** |
| 索敌排序是否确定 | ✅ **确定**（`PriorityQueue` 是**有序插入的 List**，不是二叉堆） |
| 仇恨是否每帧重算 | ✅ **不是**（`UpdateHatred` 的调用者只有 2 处） |
| 仇恨同组"按创建时间先者优先" | 🟡 **结果正确，机制说法错误**：同组内的实际决定字段是 **`instanceUid` 升序** |

## 一、★ 多敌同帧被同一干员阻挡（用户场景）

**场景**：许多敌人挤在同一格/同一区域，此时向该处部署一个多阻挡位的我方单位。

### 1.1 完整链路（每步带 RVA）

```
Character._SearchBlockee                        0x703FC0     ← 虚方法（Slot 214）
   └─ TPhysicManager.QueryEnemy(TCircle, List)  0x7F0270     ← 物理圆查询，收集候选
   └─ FilterUtil.FilterWithVolume(...)          0x6BF800     ← 按"体积"排序筛选
   └─ 对返回列表逐项 _AddBlockee                 0x6FF840
         └─ BlockBalancer.CalculateBlockOffset(m_blockedEnemies, 新敌, 自己)   0x7C1050
         └─ m_blockedEnemies.Add(敌)                          ← 纯追加
```

- 阻挡容器：**`Character.BlockedEnemyManager.m_blockedEnemies : List<Enemy>`（偏移 0x18）**
- `Character.get_blockedEnemies()` **0x705700** 直接返回该 List
- `BlockedEnemyManager.Add` **0x71BB10** 是纯追加
- 每 **3 帧**执行一次（`Character.FIND_BLOCKEE_TICK = 3`，见 `36` 号文档）

### 1.2 排序规则（核心结论）

**排序键 = `( floor(距离平方 / 0.001), instanceUid )` 升序**

| 层级 | 依据 | 证据 |
|---|---|---|
| 主键：距离 | 权重 = **`FP(距离平方)`**（正数），越小越优先 ⇒ **最近优先** | `Character._CheckBlockable` RVA **0x701260** |
| 分组：距离桶 | `bucket = TSMath.Floor(weight / s_curSmallEnoughGap)`；两个 bucket 用 `MathUtil.Equals` 比较，相同才进入下一级 | `WeightedTarget.CompareTo` RVA **0x4553F60**（`FP.op_Division` 0x54E4080 + `TSMath.Floor` 0x5502D90 + `MathUtil.Equals` 0x54E76D0） |
| 分组阈值 | `FilterWithVolume` 用 **`DEFAULT_SMALL_ENOUGH_GAP` = `FP.EN3` = 0.001** | `FilterUtil..cctor` 0x6C9BE0（`statics[0x10] = FP.EN3`）；`FP..cctor` 定义 `EN1=1/10, EN2=1/100, EN3=1/1000, EN4=1/10000` |
| 次级键：并列打破 | **`Entity.CompareTo`（RVA 0x35F7BD0）= `BObject.instanceUid`（偏移 0x18）的 `UInt32.CompareTo`** ⇒ **uid 小者（先创建）优先** | `WeightedTarget.CompareTo` 0x4553F60 |

**⚠️ 关键澄清**：并列打破用的是 **`instanceUid`，不是 `createdTime`**。两者在多数情况下同向（uid 随创建自增），但机制上不同——**同帧内创建的两个敌人 `createdTime` 完全一样，此时起决定作用的是 `instanceUid`**。

### 1.2.1 体积装不下者：**跳过，不中断**

`FilterWithVolume`（0x6BF800）按上述顺序取候选时：

```
while (累积体积 < maxVolume):
    item = queue[index++]                  # 按 (bucket, uid) 升序
    if (item.volume 装不下):  continue      # ★ 跳过，不中断
    result.Add(item.target)
```

⇒ **装不下的大体积敌人只被"跳过"，后面的小体积敌人仍可能被挡**。这解释了"一个挡位干员挤在一堆敌人里，仍能挡住其中某个小怪"的现象——**不要实现成"遇到装不下就停止扫描"**。

（注意与 §1.5 区分：§1.5 讲的是**运行期体积超限后释放谁**，这里是**选择阶段的取舍**。）

### 1.3 为什么顺序重要（副作用链）

1. **`_AddBlockee` 在追加之前先算阻挡偏移**：`BlockBalancer.CalculateBlockOffset(当前 m_blockedEnemies, 新敌, 自己)`（RVA 0x7C1050）
2. 该函数会遍历**已被挡住的敌人**，用它们的**稳定阻挡位置**算修正向量（见 `37` 号文档）
3. ⇒ **先被挡住的先落位**，后面的敌人以先者的 `F` 点为基准计算 → **顺序直接决定最终坐标布局**

### 1.4 容器清空重建的时机

以下路径会调用 `_ClearAllBlockees`（RVA **0x7017E0**）整表清空重建，从而**重置阻挡顺序**：
- `Character.OnTick`（+0x20D）
- `OnBlockModeChanged`
- `OnFinish`
- `DoFakeDeath`
- `Blackboard.OnEnter`

⇒ 任何改变阻挡模式/状态的事件都会重置顺序，模拟时必须一并复刻。

### 1.5 阻挡位不足时释放谁

`Character.TryPickOneToRemoveIfVolumeExceeded` RVA **0x71BEE0** 取 **`m_blockedEnemies[Count-1]`**
⇒ **最后被挡住的敌人先被释放**（LIFO）。
调用方：`Character.UpdateBlockees` RVA **0x6FED20**。

## 二、索敌（目标选择）的排序

### 2.1 链路

```
TargetSelector.FindTargets_DISPOSE           0x6DFDD0
 └─ RangeSelector.DoFindTargets_DISPOSE      0x6D86D0
     └─ Range.FindTargets_DISPOSE(pos, TargetOptions, validator)   0x6B0090   ← 候选集
         └─ 虚调用 OnPostFilter(List<Entity>)   （如 AdvancedSelector.OnPostFilter）
             └─ FilterUtil.Filter(cands, source, maxNum, FilterType)   0x6BFC40
```

### 2.2 确定性结论

- **`PriorityQueue<T>` 不是二叉堆**（dump 104641 仅一个字段 `List<T> m_list`）：
  - `Add` **0x42C88A0** = 有序插入（线性扫描找位置后 `Insert`）
  - `RemoveLast` **0x42C9060** = `RemoveAt(Count-1)`
  ⇒ **索引 0 = 权重最小 = 优先级最高**；**不存在"相等权重弹出顺序不确定"的问题**
- `WeightedTarget.CompareTo` 内含**显式三级 tiebreak**：**先 `priorWeight` → 再按 `weight` 分桶 → 再 `target.CompareTo`**
- ⇒ **全部 79 个 `FilterType` 的排序都是确定性的**；唯一的不确定性来自**权重本身含随机数**的那几个（`RANDOM` / `HP_NOT_FULL_RANDOM` / `STAY_STILL_RANDOM` 等）
- `HATRED_DES` 权重 = `-hatred`（`_Filter_HatredDes` 0x6C67C0 + `FP.op_UnaryNegation` 0x54E4490）⇒ 弹出权重最小 = **仇恨最大者优先**

### 2.3 仇恨的更新时机（重要）

- `Character.get_hatred()` **0x7067C0** = **纯字段读** `m_hatred`（偏移 0x350）
- `Character.UpdateHatred()` **0x6FEFA0** 的 `xref` **只有 2 处**：`OnAttributeDirty`（+0x25E）与 `_BuildAtInternal`（+0x59D）
- ⇒ **仇恨不是每帧重算**。模拟时必须复刻"什么时候会变脏"——否则"同帧内改仇恨是否立刻生效"会判断错。

## 三、仇恨"同组"的真实机制

### 3.1 分组实现

`WeightedTarget.CompareTo`（**0x4553F60**）：

```
bucket_a = floor(weight_a / s_curSmallEnoughGap)
bucket_b = floor(weight_b / s_curSmallEnoughGap)
if MathUtil.Equals(bucket_a, bucket_b):        # 同组
    return this.target.CompareTo(another.target)   # ← 决定字段是 instanceUid
else:
    return compare(bucket_a, bucket_b)
```

### 3.2 分组阈值的来源

`s_curSmallEnoughGap` 由 `FilterUtil.Filter(..., FilterType)`（**0x6BFC40**）设置：

- **只有 2 个分支传显式 gap**：@0x6C01BB 用 `DISTANCE_WEIGHT_SMALL_ENOUGH_GAP`、@0x6C02FE 用 `HATRED_WEIGHT_SMALL_ENOUGH_GAP`
- 其余 **17 个分支**走无 gap 重载 ⇒ 用 `DEFAULT_SMALL_ENOUGH_GAP`
- `FilterWithVolume` 也直接用 `DEFAULT_SMALL_ENOUGH_GAP`

常量实证（`FilterUtil..cctor` 0x6C9BE0）：`statics[0] = statics[8] = FP(0.1)`、`statics[0x10] = FP.EN3`
`FP..cctor`（0x54E3960）：**`EN1=1/10, EN2=1/100, EN3=1/1000, EN4=1/10000`**
⇒ **`DEFAULT_SMALL_ENOUGH_GAP = 0.001`**

### 3.3 "按创建时间先者优先"——结果对，机制错

- 同组内的实际决定字段是 **`instanceUid` 升序（小者先）**，**不是 `createdTime`**
- 但 `hatred` 本身含 `Clamp(createdTime, 0, 10000) × 1000`，所以**同组 ≈ 同 createdTime**，`instanceUid` 只是同帧内的细化
- ⇒ 社区说法"同组按创建时间先者优先"**在经验上成立，但机制表述不准确**；精确表述是"**仇恨值落入同一 0.001 桶后，按 instanceUid 升序**"

## 四、更正：`PriorityQueue` 不是二叉堆

本项目早前（同日）曾据 `PriorityQueue.Add` 反汇编中的 `jle` 判断其为"二叉堆、相等时不上浮、相等权重顺序不确定"。**该判断错误**：

- `PriorityQueue<T>`（TypeDefIndex 1391）**唯一字段是 `List<T> m_list`**
- `Add`（0x42C88A0）**不是堆上浮**，而是**有序插入**：线性扫描找到第一个"不大于"的位置后 `Insert`
- `RemoveLast`（0x42C9060）= `RemoveAt(Count - 1)`
- 索引 **0 = 权重最小 = 优先级最高**

⇒ **排序是确定且稳定可复现的**。我此前那段 `jle` 的解读把"有序插入的扫描终止条件"误读成了"堆上浮的停止条件"。

## 六、对模拟的意义

1. **同帧多敌阻挡是"完全可预测"的**：实现 `(floor(d²/0.001), uid)` 升序即可，无需猜测物理引擎的投递顺序。
2. **不需要复刻 Unity 物理 broadphase 顺序**（候选集顺序被排序完全覆盖）。
3. **阻挡顺序 → 坐标布局**：因为 `_AddBlockee` 会先算阻挡偏移，模拟时必须**按同一顺序逐个追加并逐个算偏移**，不能先批量算再排。
4. **阻挡位不足时是 LIFO 释放**，不是 FIFO。
5. **仇恨不是每帧重算**，必须复刻"变脏"触发点，否则同帧内的仇恨变化时序会错。

## 附：本次核验暴露的 `read_cpp.py` 局限（后续复用须知）

1. `call 0x18xxxxxxx` 是 **VA**，`who` 必须减 `0x180000000`（例：`call 0x1854e4420` → `who 0x54E4420` = `FP.op_Implicit(float)`）；直接喂 VA 会报 `can't be fetched`。
2. `who` 在高 RVA **常错标**：`0x4F10D70` 被标成 `SteamNetworkingMicroseconds.CompareTo`（实为 `FP.CompareTo` 的 Int64 实现 0x4CDB540）；`0x4EA8B0` 被标成 `IReplacement.get_totalVolume`（实为 `BlockedEnemyManager.get_totalVolume`）。**高区段标签必须交叉验证**。
3. `mov r8, [rip + …]` 指向的 `0x74xxxxx / 0x75xxxxx / 0x76xxxxx` 内容是**元数据 usage 占位 token**（如 `0x600000CB`），**不是可反查的指针**——这是"`FilterType → gap` 映射"卡住的直接原因。
4. `xref` 只能扫 `E8` 直接调用：**虚调用、委托调用、hotfix 桥调用一律查不到**（`_SearchBlockee` 是 Virtual Slot 214、`UpdateHatred(float)` 的 xref 为 0 处，都是这一类）。
