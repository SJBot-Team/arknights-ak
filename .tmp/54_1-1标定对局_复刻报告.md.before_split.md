## 八、★费用差异完全定位（2026-09-15 续）

复刻时观察到费用"恒定偏少"（3~13s Δ=−1、14~18s Δ=−2）。经排查，**由两个独立的"差 1"叠加而成**：

### 8.1 差异一：费用 +1 的**相位晚 1 帧**
```
模拟器（不部署时的实测）：
   费用 10 → 11 发生在 **帧 31**
   费用 11 → 12 发生在 **帧 61**
   ⇒ +1 出现在 30n+1 帧

标定表："该秒初始费用" 的三行分别是 0s=10 / 3s=5 / 6s=8 …
   ⇒ 其"该秒起点"对应 **帧 30n**（0s→帧0、3s→帧90、6s→帧180）
```
⇒ **模拟器比标定晚 1 帧**。也就是说：**在"第 n 秒的第 0 帧"，费用应已增长**，
而模拟器要到"第 1 帧"才增长。
**修正方向**：费用增长判定应为 `frame % 30 == 0`（而非当前行为）。

### 8.2 差异二：**芬的费用**（数据 9 vs 标定 8）
`character_table.json` 的满潜费用：

| 干员 | 潜能0 | 潜能4 | 潜能5/6（满潜） |
|---|---|---|---|
| **芬** `char_123_fang` | 11 | 10 | **9** |
| **月见夜** `char_283_midn` | 16 | 15 | **14** |

- **月见夜 = 14** ⇒ 与标定表 **−14 完全一致** ✓；
- **芬满潜 = 9**，而标定表为 **−8** ⇒ **差 1**。
- 标定表自身是自洽的（10−8+3 = **5**，正是 3s 的"该秒初始费用"）⇒
  **标定现场的芬确实是 8 费**（可能该账号的芬并非满潜、或存在其他减费来源）。

### 8.3 两个差异恰好解释全部现象
| 区间 | Δ | 成因 |

| **3~13s** | **−1** | **费用相位晚 1 帧** |

## 十、★★重大发现：游戏内**直接显示计时器**与**相位**（帧级识别的最强通道）

在检查 1-1 标定视频的右下角区域时（ROI 约 y 770~900、x 1560~1920）发现，
**游戏本身就在界面上显示两个可直接读取的量**：

| 元素 | 位置（帧坐标，估） | 含义 |
|---|---|---|
| **「⌛ 00:00:00」/「⌛ 00:00:10」** | ≈(1575~1700, 810~830) | **游戏内计时器**（时:分:秒 或 分:秒:帧，待定） |
| **「/30」+ 白色填充条** | ≈(1735~1880, 810~822) | **费用条相位**（分子即 tick，分母 30） |
| **费用数字** | ≈(1860~1900, 770~800) | 当前费用 |

**实测两帧**：
- **视频帧 621**：计时器 **00:00:00**、费用 **2**、剩余可放置 **7**；
- **视频帧 700**：计时器 **00:00:10**、费用 **2**、剩余可放置 **7**。

### 10.1 由帧 621 得到的结论（与标定表互证）
- 标定表：**帧 10 部署芬，费用 10 → 2**（芬 = **8 费**）；
- 视频帧 621 实际显示 **费用 2**、**计时器 00:00:00** ⇒ **正是"开局极早期（<1 秒）完成部署"**；
- ⇒ **完全印证用户所说**：「**「0 帧选中」和「游戏开始时 0 帧暂停」仍需通过宏实现**」
  —— 这段标定正是**开局 0 帧暂停 + 立即部署**的产物；
- ⇒ **视频帧 621 ≈ 游戏帧 10**（对应标定表 0 秒第 10 帧）。

### 10.2 待澄清：计时器格式与"视频帧 ↔ 游戏帧"映射
按"1 视频帧 = 1 游戏帧"（视频 fps=30）推算：
- 帧 621 ⇒ 游戏帧 ~10；帧 700（+79 视频帧）⇒ 应约为游戏帧 89 ⇒ **计时器应显示 ~2 秒**，
  而实测显示 **00:00:10**。
⇒ 两种解释：
1. **计时器格式为「时:分:秒」**，则"00:00:10"= 10 秒 ⇒ 与"79 视频帧 = 2.6 秒"不符；
2. **计时器格式为「分:秒:帧」**，则"00:00:10"= 0 分 0 秒 **10 帧** ⇒ 与"1:1 映射"不符（应为 89 帧）。
⇒ **必须用"逐帧扫描计时器"来确定真实映射**（下一轮首要任务）。

### 10.3 为什么这是"帧级识别"的最强通道
1. **计时器是游戏自己写的数值**，比"数费用条像素"（6px/帧、且满条与下一费 0 帧混同，见用户第 3 点）
   **更直接**：它给出的就是"游戏已经过的时间"；
2. **相位「/30」直接给出 tick**（分子），可与本方 `pixel_map` 查表**互相校验**；
3. 三者（**计时器 / 相位 / 费用**）同时可读 ⇒ **可用于"费用条满时"的帧识别**（费用条满无法用像素增量，
   但计时器与相位仍在走）—— 正对应目标②"探索费用条满后的帧识别"。

## 十五、★视频读取技术修正 + 相位检测的局限（2026-09-15 续）

### 15.1 ★必须**顺序读取**视频（关键修正）
**症状**：以步长 1 逐帧扫描时，"费用条填充"读数**恒为 0**、费用数字跳变

修正后数据立刻稳定：
```

帧 625~730：三项全部恒定  ⇒ [暂停中]（暂停约 105 帧 ≈ 3.5 秒）

## 二十七、★用户补充的机制：远程攻击的"弹道"必须建模

### 27.1 用户原话（2026-09-15）
> 「远程攻击需要考虑**是否为存在弹道的远程攻击**。如果为弹道，
> **子弹出现的位置（同干员不同皮肤可能不同）**、**子弹和敌人的追击过程**均需要被考虑。」

### 27.2 对模拟器的直接含义
| 类型 | 时序 |
|---|---|
| **近战**（如芬） | 出手 →（**前摇**）→ **立即命中** |
| **远程·无弹道** | 出手 →（前摇）→ 立即命中 |
| **远程·有弹道**（如月见夜可能属此类） | 出手 →（前摇）→ **生成子弹**（**起始位置依干员/皮肤**）→ **子弹飞向目标（追击过程，含飞行时间）** → **到达才结算命中** |

⇒ 因此 **"远程命中"的时刻 ≠ "出手时刻"**，而是**晚一个飞行时间**，
且该时间**与距离相关**（敌人移动时还需**追踪**）。

### 27.3 标定表里的直接证据
| 标定帧 | 事件 |
|---|---|
| 432 | 猎狗pro 2 ｜ **芬 命中**（近战） |
| **438** | 猎狗pro 2 ｜ **月见夜 远程命中** |

⇒ 同一次交战中，**"远程命中"比"近战命中"晚 6 帧**。
若两者出手时刻相近，则 **6 帧 ≈ 弹道飞行时间**（可作为弹道速度的标定锚点）。

### 27.4 数据层调查结果（`sim/draft/probe_projectile.py`）
| 检查项 | 结果 |
|---|---|
| 干员表直接字段 | ❌ **无 `projectileId`**（仅有 `rangeId`＝攻击范围） |
| **`skill_table.json`** | ✅ **含 `projectile` 738 处**（如 `projectile_delay_time:0`、弹道 id） |
| **`character_table.json`** | ✅ 含 20 处，形如 `{"key": "projectile", "value": "projectile_chr_orchd2_t"}` ⇒ **弹道挂在技能/天赋的 blackboard** |
| 皮肤表 | ⚠️ `skin_table.json` 不在 `gamedata/`（文件名/位置待查） |
| **模拟器** | ❌ **完全未处理弹道**（`projectile`/`bullet`/`pending_damage` 均 0 处） |

⇒ **结论**：**普攻弹道（若存在）与前摇一样，数据表不直接提供** ⇒ 必须按用户提示建模；
技能弹道则可通过 `blackboard.projectile` 关联到弹道 id。

### 27.5 建模方案（下一轮实施）
1. **新增"投射物"实体**：`{src, dst, pos, speed, born_frame, payload}`

   - **飞行**：每帧朝"目标当前位置"推进（**追踪**）；
   - **到达**：`dist ≤ 阈值` 时**结算伤害**并从场上移除；
2. **接入点**：`_do_attack` 中判断"本次攻击是否带弹道"：
   - 带弹道 ⇒ **生成投射物**（伤害延后到到达帧结算）；
   - 不带 ⇒ 立即结算（现状）；
3. **参数来源**：
   - **弹道速度/延迟**：优先取 `blackboard.projectile_delay_time` / 弹道表；
     普攻若查不到 ⇒ 由标定反推（**当前锚点：6 帧**）；

4. **对轴验证**：用"帧 438 月见夜远程命中"与"帧 432 芬命中"的 6 帧差校准飞行时间，

# ② _do_attack：远程且开启弹道 ⇒ 伤害入队延迟结算（否则立即结算）
if self.projectile_enabled and self._is_ranged(src):
    n = self._projectile_frames(src, t)                         # 飞行帧数
    self.pending_hits.append({'f': self.frame + n, 'tgt': t, 'dmg': dmg,
                              'src': src, 'born': self.frame})
    self.logs.append(OpLog(self.frame, 'projectile', {...}))
    continue

# ③ tick：到期结算
self._tick_pending_hits()

# ④ 关键参数与方法
PROJECTILE_SPEED_CELLS_PER_FRAME = 0.1667      # ≈1 格 / 6 帧（由 1-1 标定反推）
_is_ranged(u)      # 按 rangeId 判定（芬 1-1 近战；月见夜 2-3 远程）
_projectile_frames(src, tgt)   # round(格距 / 速度) ⇒ 随距离变化，体现"追击"的时序后果
_tick_pending_hits()           # 目标已死则子弹消散（不结算）
```

**要点与取舍**：
- **起始位置/发射点偏移**：本方当前取"单位中心"，**参数化保留**（用户指出"同干员不同皮肤可能不同"，
  后续可按干员/皮肤配置发射点偏移）；
- **飞行时间依距离**：用发射时刻的格距计算，**体现了"距离越远、命中越晚"**；

## 三十一、★★修正"前摇含在攻击周期内" —— 前段偏差降到 1~7 帧

### 31.1 问题发现（由逐帧事件明细）

**⇒ 根因：本方把前摇"额外加在周期之外"**（冷却在**命中时**重置 ⇒ 间隔 = 前摇 + 周期）。
**正确语义：一个 32 帧的攻击周期 = 前摇 + 后摇** ⇒ **命中间隔必须恒等于 `attack_interval_frames`**。

### 31.2 修正（`fix_windup_in_period.py`）

- **干员侧与敌人侧同时修正**；并在 `_windup_frames` 的 docstring 中写明该语义要求。

### 31.3 复测结果（严格口径）

### 34.4 分析（当前断点）
按代码推演，**命中间隔应为 `前摇 + (interval − 前摇) = interval`**，
但实测 `dmg_enemy` 间隔为 **49 = 32 + 17**（多了一个前摇），说明
**`attack_cd_frames` 与 `attack_windup_left` 的实际交互与推演不符**：

可能原因：
1. **起手那一帧的 `cd` 递减顺序**：`cd -= 1` 发生在"起手重置"**之前**，
   导致重置后的 `cd` 又立刻被减，或反之 ⇒ 产生 1~2 帧偏差（不足以解释 17 帧）；
2. **"命中后 `windup` 置 None" 的那一帧**，`cd` 已经 ≤0 ⇒ **该帧又立即起手并重置 `cd = 32`**
   ⇒ 等价于"前摇被算了两遍" ⇒ **间隔 = 前摇 + 32**（**49 = 17 + 32，吻合！**）；
3. 即：**命中帧与"下一次起手帧"重合**，使前摇"额外"叠加了一次。

**⇒ 修正方向（下一轮）**：
- 把"前摇"与"冷却"改为**单一状态机**：`atk_state ∈ {IDLE, WINDUP, COOLDOWN}`，
  **命中后直接进入 COOLDOWN，且冷却剩余 = `interval − 前摇`**（而不是重置为完整 `interval`）；
- 或等价地：**起手时记录 `atk_start_frame = frame`**，
  命中判定用 `frame - atk_start_frame >= windup`，
  冷却判定用 `frame - atk_start_frame >= interval` ⇒ **同一时间基准、不可能叠加**。

## 三十五、★★★普攻时序重构（统一时间基准）—— 平均偏差降到 6.62 帧

### 35.1 问题（上一轮断点）
"前摇 + 冷却"两套计时器交互，导致**前摇被叠加一次**：
实测"芬打猎狗"命中间隔 **49 帧**（= 32 + 17），而应为 **32 帧**。

### 35.2 方案：**单一时间基准 `atk_start_frame`**
每个单位的攻击周期只用一个状态：
```python
if atk_start_frame is None:                 # 空闲 ⇒ 尝试起手
    if 有目标: atk_start_frame = frame; atk_hit_done = False; atk_target = tgt
else:
    el = frame - atk_start_frame
    if el >= interval:                      # 周期结束 ⇒ 空闲（下一帧可再起手）
        atk_start_frame = None
    elif (not atk_hit_done) and el >= windup:   # 前摇结束 ⇒ 结算一次
        _do_attack(tgt); atk_hit_done = True
```
⇒ **命中发生在 `start + windup`、下一周期从 `start + interval` 起算**
⇒ **命中间隔恒为 `interval`**（前摇含在周期内，**结构上不可能叠加**）。

- 前段（帧 360~409）：**col 恒为 4.50**（正是"格 4 的中心"）⇒ **沿格中心竖直向上**；

### 43.3 route4 的正确语义
关卡 `routes[4]`：`startPosition={row:6,col:4}` → `endPosition={row:0,col:5}`，且：
- **`allowDiagonalMove: true`**（允许斜向）
- **`visitEveryTileCenter: false`**、**`visitEveryNodeCenter: false`**（**不强制过格中心**）

⇒ 语义是"**从起点直线走向终点**"：

### 43.4 结论
**根因：本方寻路实现成了「L 形（先对齐列、再走行）」，未按 routes 的"直线/斜向"语义**，
导致：
1. 敌人**沿格中心竖直行进**（col 固定在 4.5），直到接近终点才横移；
2. 因而**不会经过 (3,4)**，而是在 **(3,5) 与芬重叠**处才被阻挡；
3. **芬（朝左）的攻击范围 `{(3,5),(3,4)}` 里没有它** ⇒ 芬不攻击它
   ⇒ 标定「帧432 芬命中 / 443 芬阻挡 / 461 猎狗命中芬 / 464 芬击杀」全部缺失。
